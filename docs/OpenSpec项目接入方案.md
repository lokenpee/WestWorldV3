# OpenSpec 项目接入方案

状态：已确认，执行进度见[接入任务](../openspec/changes/adopt-openspec/tasks.md)。接入范围为现有全部规格及开发治理；游玩功能随需求确认后开发。

讨论需求从[需求池](../openspec/需求池.md)登记和交接；字段变化、数据流转、触发逻辑及可实施条件由[仓库指令](../AGENTS.md)维护，并体现在项目工作流模板中。

## 1. 交付目标

统一使用 OpenSpec 管理需求、规格、实施任务和变更归档。现有14份文档、技术资源、架构决策与验收材料全部完成职责适配，每条有效规则只有一个维护位置。

用户每次提出需求后，能够在实施前看到：

1. 需求的含义，以及使用前后的行为区别。
2. 哪些规格条款变化，哪些模块和关联流程受到影响。
3. 每个模块怎么改，涉及哪些数据、接口、界面和智能体行为。
4. 用什么样本、操作和预期结果验收。
5. 新增业务名称的含义、用途和必要性。

其他 AI 从仓库入口进入后，能够依靠这些文档找到有效规格、相关技术契约、任务顺序和验收方法，完成实施与交接。

## 2. 完整接入与规格归属

首次接入盘点全部现有要求，建立完整的能力目录和条款对应关系。已经确认的有效要求进入对应规格；已确认而尚未交付的目标进入变更目录，写明方案、差异规格及任务。游玩已有会话要求一并登记，其业务规则随需求确认补齐。

初次整理逐条核对规格、已接受决策、代码和验收证据。代码说明实际行为，已确认要求说明预期行为；两者有差异时记录具体问题，由用户确认需要选择的行为。已接受的要求继续有效，实现缺陷按要求修复。

当前规格的建立与验收结果分开登记。每项能力注明实现位置和检查记录，用户自测结论引用实际确认记录。历史测试记录保留日期、版本及适用范围。

|---|---|---|---|

| 世界资产整理 | world-organization | 代码整理、人工确认队列、AI整理与报告 | world、assets |

| 模型配置与调用 | model-access | 服务配置、调用、探测、请求预算、用量和错误反馈 | models |
| 智能体会话与工具 | agent-session | 按书会话、工具权限、提交确认、历史和压缩 | agents |
| 并行执行与恢复 | task-recovery | 资源锁、跨任务依赖、多标签执行权、取消和恢复 | 共享存储及相关任务模块 |

| 游玩会话 | play-session | 已有按书窗口、消息、工具、恢复和压缩要求；纳入待开发变更 | 现有游玩入口及会话基础 |

代码位置中的功能目录均位于 `src/features/`（功能源码目录），共享存储位于 `src/lib/storage/`（共享存储源码目录）。规格按能力组织，同一能力可以涉及多个代码模块。

并行与恢复的共用规则由其规格负责；其他能力引用该规则，并补充自身特有的结果。界面、数据和工具的详细定义放在下表规定的位置。

### 2.2 现有材料的适配方式

下表中的编号对应 `docs/v2/`（现有规格目录）中的00至13文档。文件和有效技术内容保留，重复行为条款转为对 OpenSpec 规格的引用。

| 材料 | 接入后的唯一职责 | 适配动作 |
|---|---|---|
| 00 阅读入口与术语 | 总入口、文档归属、统一业务名称和条款映射 | 链接全部能力、技术契约、当前变更和验收入口 |
| 01 产品需求 | 产品定位、用户目标和能力导航 | 具体行为与验收要求归入能力规格，原条款保留定位和链接 |
| 02 架构与技术规格 | 当前架构、模块依赖、运行环境和技术约束 | 对齐当前实现及已确认架构，引用行为规格 |
| 03 数据与存储 | 数据含义、存储结构、约束、升级和备份映射 | 与结构文件逐项分工，业务含义在正文，精确结构在指定结构文件 |
| 04 流程接口与算法 | 算法、接口和流程的技术实现约束 | 产品行为引用能力规格；字段及工具引用各自契约 |
| 05 AI与会话 | 提示词组装、运行方式、上下文和会话技术设计 | 工具定义引用11，产品行为引用对应能力规格 |
| 06 界面与交互 | 页面布局、控件、文案和交互细节 | 业务条件引用能力规格，操作参数引用09 |
| 07 验收与兼容缺陷 | 缺陷回归场景和兼容性验证方法 | 预期业务结果引用规格；实际执行结果引用验收记录 |
| 08 追溯与验证记录 | 证据索引、来源版本及历史执行记录 | 区分历史证据和当前检查，链接当前验收结果 |
| 09 操作与自动触发 | 用户操作及自动触发的输入、读写、反馈和恢复契约 | 统一链接行为、数据和工具定义 |
| 10 字段流转与状态转移 | 跨模块数据流、状态转换和具体示例 | 字段结构引用03，触发参数引用09 |
| 11 AI工具返回与回放 | 工具参数、返回、错误、提交确认和回放 | 提示词及实现引用同一份工具契约 |
| 12 验收覆盖矩阵 | 规格到测试及人工验收的覆盖索引 | 链接测试、人工步骤和结果，具体结果在对应记录维护 |
| 13 流程变更与冲突对照 | 现有历史变更与冲突处理记录 | 接入后保留历史用途，新变更统一进入 OpenSpec |
| 技术资源 | 指定的结构文件、提示词、样例和回放 | 资源映射逐项指出当前来源、适用要求和历史材料 |
| 架构决策 | 重要方案的背景、选择、替代方案和后果 | 引用规格与设计，当前有效规则由对应规格维护 |
| 人工验收材料 | 可操作的样本、步骤和实际验收结果 | 按变更引用，验收结果保持单一记录位置 |

正文和结构文件涉及同一规则时，明确到具体字段或条款的归属。例如，字段类型以指定结构文件为准，字段在何时更新以数据流契约为准；规格引用这两处。

旧条款的编号保留映射，方便原引用继续定位。全文旧状态说明、失效链接及资源映射随接入同步清理。一次变更影响多份材料时，在该变更任务中列出全部更新项。

### 2.3 游玩能力的扩展方式

游玩会话作为首个能力入口，后续根据已确认需求拆出独立能力。共用的会话、模型调用、工具执行、存储和恢复规则继续复用；每个新能力负责自己的业务输入、处理和结果。

接入时先整理以下接口契约，写入现有会话、数据和工具文档，并关联待开发任务。字段沿用已有定义，缺少的业务选择由需求确认补齐。

| 接口职责 | 契约必须明确的内容 |
|---|---|
| 创建与恢复会话 | 书籍与会话身份、上下文来源、消息顺序、恢复结果，以及不存在或恢复失败时的处理 |
| 发送消息与接收执行状态 | 输入、所属会话与请求身份、回复和工具执行状态、取消、错误，以及切书后的结果归属 |
| 提供与调用业务工具 | 工具名称及用途、参数和返回结构、可读写对象、所属书籍、校验、提交确认与重复请求处理 |
| 保存与恢复业务结果 | 状态由哪个模块维护、保存时点、失败后保留内容、恢复入口、备份范围及结构变更处理 |
| 组装与压缩上下文 | 各能力可提供的信息、读取范围、摘要与原始记录关系、容量处理及失败恢复 |

接口在相关技术契约中维护唯一声明或结构定义，规格引用该定义，实施代码和测试对照同一契约。工具清单登记每项能力的名称、职责、依赖、读写范围及实现入口；新增工具沿用该清单的既有组织方式。

后续开发 Agent 可以根据已确认需求，自行创建或拆分能力规格、源码模块和工具配置，选择内部实现方式，并更新总入口、依赖关系及测试。拆分时保留原条款到新位置的对应关系，共用规则继续引用原维护位置。这里的 Agent 指负责开发的 AI；应用中的游玩智能体使用已登记的工具及权限。

扩展按以下顺序进行：定位已有能力和共用接口 → 判断需求规模 → 编写相应变更材料 → 在已确认范围内实现与登记 → 验证接口和业务场景 → 同步规格。新增玩法、改变共享接口语义、扩大工具读写范围或改变保存规则，按中型或大型变更处理；内部文件拆分和配置选择由开发 Agent 在授权范围内完成。

### 2.4 仓库指令与 OpenSpec 的统一规则来源

`AGENTS.md`（仓库指令）集中维护开发治理规则，包括需求分级、确认条件、文档归属、验收、归档和 Git 授权。OpenSpec 的项目配置、工作流和模板引用这些规则，并提供相应产物结构；产品行为由能力规格维护，技术细节按2.2节归属。

接入按下表同时处理已有规则和新入口，逐项核对一致后切换。

| 现有约定 | 适配结果 |
|---|---|
| 按旧施工计划逐步实施 | 改为按当前 OpenSpec 变更任务执行；旧计划保留历史及任务去向 |
| 做之前提交行动计划 | 按需求分级执行：小修改简述处理方式，中大型需求审核书面方案；已有明确授权继续执行 |
| 文档描述当前状态 | 当前规格与技术正文描述有效状态；提案保存目标变化，归档与验收记录保存历史证据 |
| 一个事实一个权威来源 | 治理规则在仓库指令，业务规则在规格，技术定义按归属表；其他位置引用 |
| 用户自测与提交推送 | 按分级规则提供检查和自测；提交推送保留用户明确授权条件 |
| 工具自带的探索、实施、同步与归档流程 | 项目入口先读取仓库指令；各操作遵循同一分级和完成条件 |

仓库自有规则放在初始化脚本生成区块之外，生成区块只保留通用内容或导航。配置和模板需要规则内容时从权威来源读取或生成，并检查一致性。更新初始化工具后复核受影响入口。

规则有冲突时，先定位对应条款和用户已确认的决定，修正引用或旧条款；涉及尚未确认的业务取舍时，只请用户判断该分歧。接入验收核对仓库指令、项目配置、工具工作流、旧文档入口和任务清单，确保同一需求得到相同的执行要求。

## 3. 单次需求的文档要求

中型和大型需求使用变更目录。用户确认的需求原意放在提案中，用稳定编号关联规格条款、实施任务和验收场景；沿用已有编号，新增要求在所属规格内编号。小修改按3.2节简化处理。

| 产物 | 必须写清楚的内容 |
|---|---|
| proposal.md（变更提案） | 用户需求、当前与目标行为、影响模块、文档变化、术语变化、待用户选择的问题 |
| specs/（差异规格） | 新增、修改或移除的要求；触发条件、处理结果、失败与恢复场景；关联原条款 |
| design.md（实施设计） | 模块协作、数据读写、接口及工具契约、界面反馈、提示词影响、实施顺序和兼容处理 |
| tasks.md（实施任务） | 按依赖排列的具体任务，每项关联需求、修改位置、完成条件及检查方法；链接自动检查与用户验收结果 |

提案首页提供下列影响表。受影响的条款分别列行，文件定位包含章节或编号；无变化但需要回归的模块列明原因。

| 需求及原话 | 当前行为 → 目标行为 | 规格与技术文档变动 | 影响模块及原因 | 实施任务 | 验收场景 |
|---|---|---|---|---|---|
| 需求编号与用户描述 | 用户可观察的变化 | 具体文件、条款、修改内容 | 直接影响与关联影响 | 任务编号和处理方式 | 样本、操作、预期结果及证据位置 |

影响分析检查产品行为、数据与备份、模块接口、页面操作、任务状态、并发与恢复、模型提示词、工具读写和测试。中型需求记录直接影响和必要关联，大型需求逐项列出检查结论；无影响项目可以合并说明依据。

每个验收场景写明前置条件、输入或样本、操作步骤、预期界面反馈、预期数据结果，以及适用的失败恢复结果。AI内容效果使用固定小说样本和可核对依据，验收对象包括事实保留、人物区分和事件关联等实际需求。

其他 AI 的阅读顺序为：仓库指令 → 总入口 → 当前变更提案 → 相关规格与技术契约 → 实施设计 → 任务和验收。恢复工作时从任务状态及检查证据继续，缺少业务选择时提出具体问题。

### 3.1 业务名称和范围确认

- 页面、规格和验收使用统一术语。已有名称直接复用，必要英文附中文含义。
- 新增业务对象、状态、入口或功能名称，在提案中写出中文名称、含义、用户如何使用，以及它解决哪项需求，随方案一起确认。
- 数据、接口和代码中的技术标识映射到已确认的业务名称。内部变量和函数的命名由实施者选择。
- 实施中发现需要新增功能、改变业务规则或扩大影响范围时，先更新提案、规格、设计和任务中的受影响部分，取得用户确认后继续该部分工作。
- 用户确认后，提案和任务链接确认记录，并标明确认对应的文档版本或 Git 提交；后续行为变化重新确认变化部分。
- 验收时逐项核对新增界面入口、业务状态、数据对象和模型工具，均可追溯到已确认要求。

### 3.2 不同规模的修改

按行为影响、数据风险和模块关联程度分级，代码行数只作参考。开发 Agent 先给出级别及一句理由，按下表执行。

| 级别 | 判定与例子 | 需求材料与确认 | 实施和验证 | 完成记录 |
|---|---|---|---|---|
| 小修改 | 错别字、普通按钮文案、间距、保持功能含义的展示调整；业务条件、数据及接口保持原意 | 简述改哪里、怎么改、如何查看结果；用户明确指令已给出具体目标时直接执行 | 修改对应位置；按需查看页面或执行相关检查 | 更新存在精确文案或样式约定的权威条款，在交付说明记录检查结果；使用 Git 差异及后续提交追溯，无需新建变更目录 |
| 中型需求 | 已有功能的局部行为调整或逻辑修复，如改变搜索排序、修正恢复判断；影响范围清楚 | 简短提案、差异规格和任务；提案用小表写清影响、处理和验收，行为或方案取舍确认后实施；技术实现复杂时补设计 | 相关模块和受影响调用处一起修改，针对性测试，提供用户自测步骤 | 自测通过后同步相关规格与技术契约，归档变更 |
| 大型需求 | 新增用户功能、跨模块流程、数据迁移、共享接口语义或工具写权限变化 | 完整提案、差异规格、实施设计和依赖任务；确认整体范围、方案、术语和验收标准；重大跨功能选择补架构决策 | 按依赖推进，验证跨模块数据、正常路径和失败恢复，提供完整人工验收 | 用户自测通过后核对全部受影响材料，合并规格并归档 |

分级还应遵循：

- 改提示词可能改变模型判断或工具行为，按实际影响判为中型或大型；涉及删除、权限或确认含义的文案也按行为影响判级。
- 逻辑修复恢复已确认要求时，引用原要求并补回归场景；业务要求保持原意，更新需要补充的场景和技术说明。
- 实施中出现更大范围的数据、接口或业务影响时，先升级级别、补齐材料，仅对新增取舍请求确认。
- 同一需求的多个小改动合并登记；按整体影响判级。小修改属于已有变更时，直接记入其任务。
- 小修改由 Agent 完成针对性检查并交付可查看结果，用户按需复核；中型、大型需求保留明确的用户自测结论。

OpenSpec 的产物依赖按所选工作流校验。标准工作流要求的文件使用符合本级别的最小内容；若需要简化产物组合，在接入时配置并验证项目工作流。小修改使用同一分级规则的简化路径。

## 4. 唯一开发流程

统一按3.2节分级。中型和大型需求使用以下完整流程；小修改执行“明确目标与处理方式 → 修改 → 针对性检查 → 更新相关文档并交付”，用户按需复核。

需求讨论 → 确认范围、方案与验收标准 → 实施 → 自动检查 → 用户自测 → 同步规格并归档。

| 环节 | 完成条件 |
|---|---|
| 需求讨论 | 需求原意明确，现有材料已检查，需要用户判断的问题具体可选 |
| 方案确认 | 用户能查看影响表、行为差异、实施方案、术语变化和验收场景；确认记录可定位 |
| 实施 | 按任务顺序修改，任务勾选有对应成果；行为变化先更新方案并确认 |
| 自动检查 | 与变更相应的类型、静态、业务、浏览器或构建检查通过；记录命令、结果及适用版本 |
| 用户自测 | 提供可运行入口、样本、步骤和预期结果；用户给出验收结论，失败项返回对应任务 |
| 同步与归档 | 用户自测通过，差异规格并入当前规格，相关技术文档更新，引用和覆盖关系核对通过，归档变更 |

任务完成、自动检查通过和用户自测通过分别登记。接入时保留已有检查与人工验收的真实状态。新需求的主规格在自测通过后同步；实施期间的目标要求保存在变更目录中。

提交和推送遵循用户明确授权，提交说明包含版本号与改动。归档记录与发布记录通过版本或提交关联。

OpenSpec 工作流提供产物和操作入口，按仓库指令中的分级和通过条件执行；自动检查负责验证能机器核对的格式、链接、覆盖及行为，人工确认由用户完成。

## 5. 目录与配置

```text
AGENTS.md                         开发治理规则的唯一维护位置
openspec/
  config.yaml                     项目上下文、规则引用和产物要求
  specs/<能力>/spec.md             当前有效行为及验收场景
  changes/<需求>/
    proposal.md                   需求、影响和确认依据
    specs/<能力>/spec.md           本需求的行为差异
    design.md                     实施设计
    tasks.md                      实施任务与检查、验收入口
  changes/archive/                已完成变更
docs/
  v2/00-阅读入口与术语.md           全部文档的统一阅读入口
  v2/01至13及resources/            按职责适配后的产品和技术材料
  decisions/                      重要架构决策
  acceptance/                     人工验收步骤及结果
  分阶段实现与人工验收计划.md        接入后保留历史记录及新入口链接
```

项目配置使用 OpenSpec 的 context（项目上下文）和 rules（产物要求）表达约束，内容按下表配置。具体字段及格式在接入时按所选版本验证。

| 配置内容 | 要求 |
|---|---|
| 项目上下文 | 产品定位、实际技术栈、模块目录、统一阅读入口、文档归属及仓库指令中的分级规则 |
| 提案要求 | 用户原意、行为前后对照、影响表、术语变化及确认记录 |
| 规格要求 | 中文业务描述、稳定条款编号、可执行场景、精确技术契约引用 |
| 设计要求 | 模块处理、数据流、接口工具、UI反馈、失败恢复、兼容影响 |
| 任务要求 | 需求与验收关联、依赖顺序、文档同步、自动检查和用户自测 |

配置引用权威文档，保持规则在指定位置维护。初始化后的工具工作流也指向同一分级流程，并核对同步、归档的执行条件。游玩扩展读取共用接口契约和能力目录，按需求登记新的能力、工具和依赖。

## 6. 接入步骤与验收

| 步骤 | 工作与交付 | 验收方式 |
|---|---|---|
| 1. 全量盘点 | 阅读14份文档、资源映射、决策、代码与验收记录；列出有效要求、实现差异和状态冲突 | 每项现有要求有来源、归属、状态和证据；业务分歧交用户确认 |
| 2. 建立规格 | 初始化 OpenSpec，建立完整能力目录；当前要求进入规格，待开发目标进入变更；整理游玩共用接口与扩展规则 | 全部有效要求可定位；需求编号及原链接可追踪；游玩接口职责、能力登记方式和待开发要求可查 |
| 3. 文档适配 | 按归属表更新旧正文、资源映射、术语与状态；重复规则转引用 | 每个规则只有一处正文维护；规格、技术契约及样例一致 |
| 4. 统一任务和指令 | 将旧计划未完成项转入变更任务，保留检查和验收证据；按2.4节统一仓库指令、配置、工作流和导航 | 中大型活动任务从 OpenSpec 进入；小修改遵循同一分级规则；旧计划仅指向新位置及历史记录；各入口执行条件一致 |
| 5. 检查交接材料 | 核对条款覆盖、链接、术语及任务验收关联；分别用文案修改、局部逻辑调整、新功能和游玩能力拆分走查 | 仅凭材料能正确判级、定位模块、选择产物和验证方法；游玩拆分能复用接口并登记依赖 |
| 6. 真实需求试运行 | 选择用户接下来确认的一个范围适中的需求，执行完整流程 | 用户可在实施前审阅影响和效果；实施后逐项自测；规格同步及归档完整 |

接入完成的判定：现有全部规格和资源都有明确归属；全部活动任务使用统一流程；待确认问题有具体位置和影响；用户已审阅文档对应关系与完整需求样例。真实需求试运行按该需求自己的范围和验收结论交付。

方案文件负责接入设计。接入任务开始后由 OpenSpec 任务清单登记执行进度；治理规则落到仓库指令，配置和日常阅读入口引用该位置。接入完成后，本方案保留为接入记录，日常规则以生效入口为准。
