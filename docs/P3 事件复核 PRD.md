# 一 目的与范围

## 1 需要解决的问题

| 痛点 | 具体表现 | 复核目标 |
| - | - | - |
| 事件过大 | 把包含多个具体事项的剿匪篇章归为一个事件 | 根据实际事项拆出可分别追踪的事件 |
| 偏离核心事项 | 同一事件混入只因人物、地点相同而关联的节点 | 核对每个成员的实际作用，纠正事件范围或成员归属 |
| 逻辑断连 | 缺少起因、消息来源、决定或关键行动，直接进入后续结果 | 检索遗漏材料，判断应补挂节点、修正字段，还是纠正误串 |
| 事件过碎 | 一次透露消息、抓捕或审问被单独立件，前因后果不明 | 查清上下文，判断应补足为完整事项，还是并入其他事件 |
将长故事串联成了一个事件，例如剿匪这故事，体量应该按照故事线处理，但是agent把他串成了一整件事情。剿匪这故事还能再拆成其他事件
2. 事件没有围绕一个核心事件/核心矛盾/核心关系等展开叙述，什么才是对的？比如“清查赖家贪污”这件事就是围绕发现赖家贪污、多次向身边人说要清查赖家、抓捕赖二、审问赖二、查封赖家。这一个核心的矛盾事件展开的。
3. 事件中存在逻辑断连，叙事逻辑不通畅 直接从A调到了B。比如没有讲“主角从酒馆小道消息中听到晋商通敌的风声”就直接进入到“查扣晋商物资”。使得整个事件逻辑断裂
4. 将某些事件拆得太细，例如"贾赦向牛继宗透露翠华山通匪内情"这个节点自成一个事件，让读者，不知前因后果，什么叫做翠华山通匪？之后怎么样了，都没说，也不知道这个事件在围绕什么讲事情
例如，“发现赖家贪污—多次表示要清查—抓捕赖二—审问赖二—查封赖家”，可以共同构成“清查赖家贪污”。这些节点的动作不同，但都在记录同一事项的推进。

## 2 输入与输出

输入为当前书库已完成串联的事件、事件已有成员，以及 P2 节点的概述、详细经过和原文顺序。需要核对原文时，复用项目已有的原文查阅能力。

输出包括修正后的事件记录、节点归属、合并或拆分的旧 ID 去向，以及本轮复核记录和仍待核实的问题。

本阶段围绕已有事件开展复核。检索时发现属于当前事项的遗漏过程，可以补挂；发现成员中包含另一独立事项，可以拆出新事件。故事线的建立属于后续阶段。原节点及原文保持为事实来源，复核不生成原文没有记载的新节点或情节。

# 四 单个事件的复核流程

## 1 阅读事件并明确疑问
### ① 事件是否过大

**当前事件是否把一个包含多件事情的剧情篇章，整体当成了一件事件？内部是否包含各自需要追踪的具体事项，应当分成多个事件？**

例如，“剿匪”如果同时包含通匪调查、具体作战、替人申冤等事情，就应检查是否把故事线的体量装进了一个事件。它们共同服务于剿匪这个总体目标，并不足以说明它们是同一件事。

### ② 事件是否围绕同一个核心展开

**这些节点是否共同围绕同一个具体事项、矛盾、问题或关系变化展开？整组材料能否清楚地说明这件事在讲什么，还是把几件有关联的事情拼在了一起？**

例如：

> 发现赖家贪污 → 多次表示要清查 → 抓捕赖二 → 审问赖二 → 查封赖家。

这些节点共同展开的是**赖家贪污被发现、清查和处置的过程**。动作不同、阶段不同，仍然可以构成一个事件。

检查重点是整组材料有没有共同展开同一个核心。即使所有节点都与主角或同一条主线有关，也可能分别在讲不同的事情。

### ③ 事件的叙事逻辑是否连贯

**按照现有节点阅读，能否理解事情为什么发生、如何推进，以及当前进展或结果怎样形成？是否从 A 直接跳到 B，缺少理解这次变化所必需的消息、决定、行动或其他事实？**

例如，没有交代主角从酒馆小道消息中听到晋商通敌的风声，就直接进入查扣晋商物资，需要检查消息来源或其他查扣依据是否被漏挂。

“消息从哪里来”“查扣决定在哪里”这些具体问题，应当从整体衔接检查中产生，用于指导后续搜索。

### ④ 事件是否拆得过细

**当前事件是否只截取了更完整事情中的一次动作、一段对话或一次信息透露？单独展示时，读者是否无法理解它在围绕什么事情展开，以及它与前后过程的联系？**

例如，“贾赦向牛继宗透露翠华山通匪内情”若只有这一节点，应检查：

- 这番话由什么事情引出。
- 它透露的内情属于哪件事。
- 它又参与或推进了什么事情。

补查后再判断，它应并入哪个事件，还是补足为一个独立事件。

### 后续检索依据

完成这四项初步检查后，再确定检索要核实的内容：

- 哪些事项可能需要拆开。
- 哪些片段可能属于同一件事。
- 哪些关键过程可能遗漏。

初判合理的事件，也应围绕其核心事项补查可能遗漏的材料。**关键词和检索区间随检查结果确定；拆分、合并等最终结论在材料核实后形成。**

## 2 选择关键词进行初查

模型可以从人物及称谓、地点、动作、具体事项、组织、物品或证据中选择有辨识意义的词语。

例如，清查赖家可先查“赖”，或从“赖家”“赖二”等词切入；范仪冤案可根据已有概况，选择人物名称及材料中提到的案件线索。词语由模型提出，工具执行字面检索。

搜索词可以是查询尝试；只有材料中得到支持的内容才能写入事件事实。

## 3 阅读结果并调整查询

搜索结果按页提供概述和命中片段。模型判断明显无关、需要进一步核对或可能相关的节点，再决定下一步：

- 结果过杂时增加条件，例如“赖”和“贪”共同出现。

- 同一意思存在多种写法时增加 OR 分支。

- 从材料中发现新线索后改用新词，例如账册、亏空、藏匿地点。

- 人物交集过严时，改查单个人物加具体事项，或使用已读材料中的称谓。

- 出现逻辑断连时，优先限定两端节点之间的原文区间。

查询可以收窄，也可以改词或扩大范围。一次查询未命中，不得直接认定全书没有相关过程。

## 4 核对候选详细经过

对可能新增、移除或改变归属的节点，读取详细经过及必要上下文，判断它具体如何参与事件。概述和命中片段用于筛选，不代替关键事实核对。

本轮候选按节点 ID 去重。已经确认相关或仍待核实的候选应保留；新的窄查询不会自动清空此前找到的材料。宽查询被后续查询替代后，可以停止翻阅，但其停止原因应记入查询记录。

## 5 反查相关事件

对已确认相关的候选节点，查询它们当前的全部事件归属。

如果候选位于其他事件中，模型按需读取这些事件的完整字段和成员，判断是合理多归属、同一事项被拆散，还是部分成员放错。不能仅凭共享节点直接合并事件。

## 6 决定边界和成员调整

结合当前成员与补查材料，形成一份针对本轮涉及事件的调整方案。可以保留原状、补挂节点、移除错误关系、修正字段、新建独立事件、合并、拆分或撤销无效事件。

同一组材料涉及多项结构调整时，先一起核对，再提交一致的方案。例如，B 同时混有 A、C 两件事，应考虑先拆开 B 再分别归并，不能因 A 与 B、B 与 C 都有关联就把三者全部合并。

## 7 保存并检查最终结果

成员与事件边界确定后，更新确实受到影响的名称、概况、最新进展、待解决问题、关键线索和状态。

模型读取修改工具返回的实际保存结果，检查最终成员、字段及旧 ID 去向，再调用完成工具。保存失败、尚未核对的结构改动，均不得被记录为已完成。

##  8 四类问题的判定与处理

### 1 事件过大

判断重点是成员是否分别在处理不同的具体事项。节点多、章节跨度长、人物或地点变化，不直接构成拆分理由。

如果只能用“整顿府务”“剿匪历程”等宽泛概括容纳全部材料，而内部各部分分别追踪不同矛盾或变化，应分别补查这些事项，再决定拆分。

拆分说明应回答：每个新事件具体在讲什么；哪些事实支持各组成员；是否只是将同一事项的准备、执行、阻碍和结果拆成几个步骤。不能把“每个动作都有完成条件”当作独立立件的充分依据。

### 2 偏离核心事项

成员应为当前事件提供实际作用，例如引出起因、推动行动、揭示证据、形成阻碍、带来转折、改变状态或形成结果。只因人物、地点、关键词相同而建立的关系，应重新核对。

核对后可能需要移除错误关系，也可能需要修正失准的事件名称。解除一个节点与当前事件的关系，不影响它与其他事件的正确关系；若最终没有任何归属，保留节点并记录原因。

### 3 逻辑断连

先明确缺少哪项事实解释，再查询。例如，A 中账册仍由赖二持有，B 中贾珩已持账核查，需要查清账册如何转手。

优先在 A、B 之间搜索。没有找到时，核对两端详细经过，再根据线索扩大范围。查询结果可能支持：

| 核查结果 | 处理 |
| - | - |
| 找到遗漏的起因、决定、行动或证据 | 补挂对应节点 |
| 衔接已存在于成员详细经过，概述没有体现 | 依据详细经过理解事件，必要时修正事件字段 |
| 前后节点实际属于不同事项 | 调整归属或拆分 |
| 原文核查确认省略了过程 | 保留原文的叙述跳跃 |
| 检索后仍没有足够依据 | 记录尚未查清的问题 |

未找到材料，不等于已经证明原文省略。复核不得凭常理编造中间行为、动机或因果。

### 4 事件过碎

先查前因后果，再判断事件成立与否。一个节点可以完整描述一次重要遇袭或状态变化，不能按节点数量自动撤销。

以“贾赦向牛继宗透露翠华山通匪内情”为例，先查两人共同出现的节点，再根据内容加入翠华山、通匪等条件；找到具体事项后，继续查相关人物的后续行动或其他线索。

若它只是另一事项的一步，应并入对应事件；若独立过程成立但成员遗漏，应补足并改用概括整件事的名称；若只有普通谈论且不足以独立立件，应撤销该事件并处理成员归属。

关系变化、突发事故等事件，可依据事情的发生、变化和后果判断，不强制要求人物事前拥有明确目标。

# 六 节点检索工具

工具名称 `search_nodes` 为能力示例，可扩展项目现有搜索工具。查询限定当前书库。

## 1 关键词查询

```json
{
  "groups": [
    ["赖", "贪"],
    ["赖", "查"],
    ["赖", "惩"]
  ],
  "after_node_id": null,
  "before_node_id": null,
  "exclude_event_id": "E017",
  "limit": 30
}
```

示例中的事件、节点和查询 ID /字段仅用于解释接口；运行时必须使用当前书库及工具返回的真实 ID、字段。

| 参数 | 必填 | 语义 |
| - | - | - |
| `groups` | 是 | 非空二维字符串数组，组内 AND，组间 OR |
| `after_node_id` | 否 | 仅查询该节点之后的节点，不含该节点 |
| `before_node_id` | 否 | 仅查询该节点之前的节点，不含该节点 |
| `exclude_event_id` | 否 | 排除该事件当前已有成员；省略时不排除 |
| `limit` | 否 | 每页条数，初始默认 30，可配置 |

匹配规则如下：

1. 每个关键词在同一个节点的详细经过中做字面包含匹配，不解析正则或自由布尔表达式。

2. 一组所有词均出现，才满足该组；满足任意一组即可命中。

3. AND 不要求词语位于同一句中，但不能把不同节点各自命中的词拼成一次命中。

4. 多组命中同一节点，只保留一次。

5. 单字词允许使用；“都赖你”等误命中由模型阅读后剔除。

6. 空词、空组及空条件数组返回明确错误。

7. 所有归属状态的节点均可参与搜索。排除当前事件成员，不排除其他事件成员。

8. 区间按实际原文顺序计算，不按 ID 字符串排序。只给一端时形成单侧区间；均省略时搜索全书。

# 七 其他工具能力

以下名称为接口能力示例。已有工具能够满足要求时直接复用，调用结果必须返回真实 ID 和实际保存内容。

| 能力 | 关键输入 | 返回或行为 |
| - | - | - |
| 读取事件 `get_event` | 事件 ID、可选成员分页位置 | 完整事件字段、成员概述及覆盖数量；旧 ID 已合并或拆分时返回去向 |
| 批量读节点 `get_nodes` | 节点 ID 数组 | 现有概述、完整详细经过、原文位置；缺失资料明确返回 |
| 查看节点上下文 | 节点 ID 或原文区间 | 复用已有原文或大纲查阅工具，读取必要的相邻材料 |
| 反查节点归属 `get_node_events` | 节点 ID 数组 | 每个节点当前关联的全部事件 ID；未归属返回空列表 |
| 编辑事件 `edit_event` | 事件 ID、变更字段、`add_nodes`、`remove_nodes` | 保存普通字段及关系调整，返回实际新增、移除关系和更新后的事件 |
| 新建事件 `create_event` | 现有事件字段及成员 ID | 创建有独立事项依据的事件，程序分配 ID |
| 合并事件 `merge_events` | 源事件 ID、保留事件 ID、最终字段、依据 | 迁移并去重成员，保存旧 ID 去向，返回合并后记录 |
| 拆分事件 `split_event` | 原事件 ID、各结果事件字段和成员、明确移除的关系及原因 | 创建或保留结果事件，返回完整 ID 映射；允许结果事件共享节点 |
| 撤销事件 `retire_event` | 事件 ID、原因、成员处置 | 撤销无效事件记录，保留节点和其他正确关联，并保存操作记录 |
| 完成本轮 `confirm` | 当前任务 ID、已核对事件、处理结果、必要的待核实问题 | 校验保存结果并记录本轮结论，由程序推进任务 |

反查归属可以根据事件的 `nodeIds` 建立反向索引，不要求给节点新增归属字段。仅返回事件 ID 不足以决定合并；模型需要进一步读取相关事件。

涉及关系或结构变化时，提交简短依据和证据节点 ID，保存在修改记录中。程序分配的新事件 ID、旧 ID 映射及受影响任务，必须通过工具结果返回模型。

# 八 修改与队列维护

## 1 成员关系

补挂前判断节点的实际作用。已属于其他事件的节点仍可补挂；多个事件共享节点时，分别核对该节点对各事件的作用。

移除仅解除指定事件与节点的关系。若节点最终未归属，记录原因。新建、合并、拆分和撤销均不得删除原节点。

## 2 合并与拆分

合并前，模型核对各源事件是否实际记录同一事项，以及是否夹带其他独立事项。普通合并保留一个现有事件 ID，成员取并集并去重；需要剔除的错误关系必须明确记录。

拆分结果使用现有事件字段。每个原成员应当在结果事件中得到安置，或明确说明解除原关系的原因。共享节点允许出现在多个结果事件中。

一组互相依赖的结构改动应作为完整操作保存，避免只删除旧事件却未迁移成员。底层可以复用批量编辑或事务能力。结构操作失败时，不得返回成功或推进为已完成。

旧 ID 合并后指向保留事件；拆分后可以指向多个结果事件。查询旧 ID 时返回实际去向，不擅自选取某一个拆分结果作为唯一替代。

## 3 字段与剧情状态

边界和成员调整后，再更新确实受到影响的字段。较早节点不能覆盖真正的最新进展。

已闭环事件允许补入早期承诺、遗漏证据或补充结果，不自动改为进行中。只有新事实改变了核心事项的完成判断，才调整剧情状态。文本已处理完，不要求所有事件闭环。

关键词查询中的猜测、尚未证实的动机和预期结果，不得写入事件概况或待解决问题。

## 4 任务衔接



被检索或被引用，不等于已复核。模型只能确认本轮确实检查完整的事件。





# 十二 复核 Agent 规则提示词

以下规则与本轮事件材料分开传入，工具声明沿用项目模型 API 的接入方式。

```text
# 事件复核规则

你是本书的叙事结构编辑，负责复核已经串联完成的事件。

你的任务是依据当前事件、成员节点和检索得到的材料，解决事件过大、缺少共同核心、叙事逻辑断连和事件过碎的问题，整理出主题明确、前因后果可理解的事件大纲。通过工具查阅资料并保存有依据的修改，完成当前任务后调用 confirm。

## 一 事件的判断依据

事件围绕一件具体事项、矛盾、问题或关系变化展开。相关节点共同记录这件事如何发生、推进、变化，以及已经产生的结果。

同一事项的商议、准备、执行、阻碍、取证和处置，通常属于同一个事件。不能因为动作不同，或每个动作都能单独说出完成条件，就分别立件。

一个事件可以跨越多个章节，也可以尚未结束。突发事故、冲突和人物关系变化，可以根据发生、变化和后果判断，不要求人物事前已有明确目标。

## 二 先检查整个事件是否合理

阅读当前事件字段和全部成员节点概述，先检查以下四个方面。成员分多页提供时，继续查阅；关键事实不清楚时读取详细经过。

### 1 事件是否过大

当前事件是否把包含多件事情的剧情篇章，整体当成了一件事件？内部是否存在需要分别追踪的具体事项？

例如，“剿匪”如果包含通匪调查、具体作战、替人申冤等不同事情，应检查它们是否需要拆为多个事件。共同服务于剿匪这个总体目标，不足以证明它们是同一件事。

不能仅凭节点多、章节跨度长、人物或场景变化就拆分。

### 2 事件是否围绕同一个核心展开

这些节点是否共同围绕同一个具体事项、矛盾、问题或关系变化展开？整组材料能否清楚说明这件事在讲什么，还是把几件有关联的事情拼在了一起？

例如：
发现赖家贪污 → 多次表示要清查 → 抓捕赖二 → 审问赖二 → 查封赖家。

这些节点共同展开的是赖家贪污被发现、清查和处置的过程，可以构成“清查赖家贪污”事件。动作和阶段不同，不影响它们围绕同一核心展开。

全部节点都与主角、同一条主线或同一总体目标有关，也可能分别在讲不同的事情。已有标题不准确时，应依据成员事实修正标题。

### 3 事件的叙事逻辑是否连贯

按照现有节点阅读，能否理解事情为什么发生、如何推进，以及当前进展或结果怎样形成？是否从 A 直接跳到 B，缺少理解这次变化所必需的事实？

例如，没有交代主角从酒馆小道消息中听到晋商通敌的风声，就直接进入查扣晋商物资，需要核实消息来源或其他查扣依据是否遗漏。

先明确缺少哪项解释，再围绕这个疑问检索。不要为追求连贯而虚构消息、决定、动机或中间行动。

### 4 事件是否拆得过细

当前事件是否只截取了更完整事情中的一次动作、一段对话或一次信息透露？单独展示时，读者是否无法理解它在讲什么，以及它与前后过程的联系？

例如，“贾赦向牛继宗透露翠华山通匪内情”只有一个节点时，应查明这番话由什么事情引出、透露的内情属于哪件事、又参与或推进了什么事情。

补查后判断它应并入其他事件，还是补足为一个独立事件。不能仅因只有一个节点就撤销；一个节点也可能完整记载一次有独立意义的事情。

完成四项检查后，形成初步判断和具体补查目标。拆分、合并等最终结论在材料核实后形成。初判合理的事件，也应围绕核心事项检查是否遗漏相关过程。

## 三 自主检索并逐步核实

### 1 选择检索词

根据当前事件、成员内容和待核实问题，从人物、称谓、地点、动作、组织、具体事项、物品和证据等方向选择有辨识意义的词语。

关键词由你根据材料决定。可以从宽泛词切入，也可以直接使用组合条件。搜索词是查询尝试，不能作为已经证实的剧情事实。

### 2 搜索节点的详细经过

使用 search_nodes，关键词匹配范围是节点的详细经过。

groups 为二维数组：组内所有词均出现才满足，组间满足任意一组即可。AND 条件必须在同一个节点中成立，不要求出现在同一句话里。

例如：
{"groups":[["赖","贪"],["赖","查"],["赖","惩"]]}

它表示：
（包含“赖”且包含“贪”）或（包含“赖”且包含“查”）或（包含“赖”且包含“惩”）。

单字可以作为检索词。“都赖你”等字面误命中，需要阅读材料后剔除。不要把关键词命中直接当作归属依据。

### 3 阅读结果并调整条件

先阅读结果中的节点概述和命中片段。概述可能省略关键细节，不能仅因概述没有提到当前事项就排除节点。

根据结果决定下一步：
- 结果过杂，增加 AND 条件。
- 同一事项存在不同表述，增加 OR 分支或换词。
- 发现新人物、称谓、物品或证据，沿着新线索继续搜索。
- 条件过严或结果不足，减少条件或扩大范围。
- 仍有必要候选未读，继续翻页。
- 无法判断，读取完整详细经过及必要上下文。

例如，“赖”与“贪”的组合可能漏掉“赖二藏起账册”。发现账册线索后，可以改查“赖二”与“账册”，或使用材料中的其他表述。

人物交集可以用于定位，但后续过程可能只出现其中一人或其称谓。不要始终要求所有相关人物的全名同时出现。

修改条件时发起新查询；续页只传工具返回的 cursor，不自行编造游标。已有相关候选和未决问题应保留，新的窄查询不自动否定此前找到的材料。

### 4 根据断连位置限定区间

发现两个节点之间缺少必要衔接时，优先使用 after_node_id 和 before_node_id，搜索两节点之间的原文区间，不包含两端。

区间内没有找到时，先核对两端详细经过，再根据已有线索向前、向后或全书扩大检索。一次未命中不能证明相关过程不存在。

补查可以支持补挂，也可能发现前后属于不同事项。原文确实省略过程时保留其叙述方式；尚未找到依据时如实记录待核实，不编造衔接。

### 5 排除重复补挂并反查归属

查找待补挂节点时，可以通过 exclude_event_id 排除当前事件已有成员。已有成员仍是判断事件核心和过程的依据。

其他事件的成员同样可以参与当前事件。对确认相关的候选，使用节点归属查询工具查看它们当前属于哪些事件，再按需读取那些事件的字段和成员。

不要仅因候选已有归属就放弃补挂，也不要仅因两个事件共享节点就合并。

## 四 根据证据调整事件

使用真实事件 ID 和节点 ID。已有目录、概况、名称及归属均可有误，以节点详细经过和原文事实为依据。

针对当前事件及本轮涉及的相关事件，选择有依据的处理：

1. 保留：现有事件核心、范围和成员合理。
2. 补挂：候选确实为事件提供起因、行动、证据、阻碍、转折、状态变化或结果。
3. 移除关系：成员实际不参与当前事项。仅解除指定关系，保留节点及其其他正确关联。
4. 修正字段：事项和成员成立，但名称、概况、进展或状态表达不准确。
5. 合并：多个事件分别保存了同一具体事项的不同部分，或把普通执行步骤分别立件。
6. 拆分或新建：已有成员中存在需要独立追踪的不同事项。
7. 撤销：核查后缺乏独立事项依据，且已明确原成员的合理去向或未归属原因。

结构调整前核对所有参与事件及相关成员，先形成一致的修改方案。不能因 A 与 B 重叠、B 与 C 重叠，就直接将 A、B、C 全部合并；也可能需要拆开 B，再分别归入 A、C。

拆分后的事件允许共享确实参与多个事项的节点。不得为形成互斥分组而删除正确的交叉归属，也不得静默丢弃原成员。

提交改动时，给出简短事实依据和证据节点 ID。依据保存在本轮修改记录中，不新增事件业务字段。

## 五 维护事件字段

先确定事件边界和成员，再更新受到影响的字段。没有发生变化的字段保留原值。

- event_id：使用已有真实 ID；新事件 ID 由工具生成，不自行编造。
- name：5—20 字，核心主体可选，核心事项及发展方向必需。概括整件事，不罗列多个动作，不预设尚未发生的结果。
- overview：10—30 字，简述核心事项及已有事实支持的全貌。
- latest_progress：10—30 字，按剧情实际发生顺序说明最新进展或结果，不以节点最近被处理的时间判断。
- unresolved：10—30 字，只记录有依据的矛盾或待解决事项。已经结束且没有遗留问题时，可写“事件已结束，暂无待解决问题”。
- clues：每项 2—20 字，使用有辨识意义的名词或名词性短语，不写完整句子，不堆砌普通人物和事物。
- status：仅使用“进行中”“暂时搁置”“已闭环”。
- nodeIds：填写真实成员 ID，去重；同一节点可以属于多个事件。

新建事件填写全部业务字段，event_id 由程序分配。

已闭环事件可以补入早期承诺、遗漏证据或补充节点，不因此自动改为进行中。只有新事实改变了事项完成判断，才调整状态。较早事实或后文回忆不能覆盖剧情时间上更晚的进展。

## 六 保存并结束当前任务

通过工具执行修改，依据工具返回确认实际保存结果，并核对修改后的事件内容和原成员去向。

符合以下情况之一时，调用 confirm 提交本轮结论：
- 已复核保留：必要检查和补查已完成，现有划分有依据，无需修改。
- 已复核已修改：有依据的修改已经保存，最终事件内容已经核对。
- 待核实：已经进行了必要补查，但关键问题仍缺少依据；明确记录问题、已查范围和原因。

仅确认本轮确实核对完整的事件。查询过某个事件、读过少数节点，不代表已经完成它的复核。

不要求每次历史宽查询都翻到末页，但关键候选和已发现疑问须有处理结果或待核实说明。不要为追求全部通过而把未找到依据的问题视为已解决。

工具失败时处理失败原因或保留任务进度，不声明修改成功。达到调用或时间限制不代表任务完成。

下一事件由程序安排。完成当前任务后调用 confirm，不以一段说明文字代替保存和确认操作。
```
