# P3 事件串联｜设计补全版



## 一、目标与边界

- 输入：P2 已整理的节点及其 `id / name / process / new_facts / clues`（字段不一定真实，以实际项目为准）；P3 已有事件及节点归属。
- 输出：事件记录、事件与节点的多对多关联、未归属节点及原因、事件状态和可追溯依据。
- 每次只让 Agent 判定**当前节点**；程序负责队列、候选检索与任务推进。
- 一个节点可同时推进多个事件；一个节点也可以暂时不归属。
- **闭环是剧情状态，不是禁止继续添加成员的锁。** 旧事件可补进较早的起因、证据、回忆和补充节点。
- “故事线过大、事件颗粒度不对、重复立件”等结构调整，主要放到批次复核，不要求逐节点 Agent 立即整理全书。

## 二、事件与节点的最小数据约定

### 1. 事件

| 字段                | 说明                                |
| ----------------- | --------------------------------- |
| `event_id`        | 稳定 ID；合并时保留可追溯的旧 ID 映射（由后台代码自动赋予） |
| `status`          | `进行中 / 暂时搁置 / 已闭环`                |
| `name`            | 事件名称                              |
| `overview`        | 事件概况                              |
| `latest_progress` | 按**剧情发生顺序**判断的最新进展，不是最近处理的节点      |
| `unresolved`      | 当前未解决的问题；已解决时允许明确写已解决             |
| `clues`           | 特征性实体 / 关键线索；用于检索，但不是唯一依据         |
| `nodeIds`         | 成员节点编号列表                          |



### 3. 事件状态的实际作用

- **进行中**：事项尚有明确可追踪的推进目标；候选排序优先。
- **暂时搁置**：事项尚未解决，但已较长时间没有新进展；仍保持可检索。它只是检索优先级/整理状态，不表示小说中有人正式放弃。
- **已闭环**：有事实依据表明核心事项取得了明确阶段结果；允许继续关联此前遗漏或之后补充的节点。
- 闭环事件新增节点时，**不自动重新打开**；只有新事实证明核心事项仍未完成或出现实质性续进，才考虑改状态。若出现不同目标，优先考虑独立新事件。
- 三种状态都参与候选检索；状态仅用于排序和说明，不能作为检索硬过滤条件。章节间隔长也不能自动判定已闭环。

## 三、任务队列与提示词组装器

1. 第一阶段生成按小说**章节、节点顺序**排列的节点 ID 队列。每轮只取一个当前节点任务。
2. 读取当前节点的完整概览及真实 ID，调用后文节拍概览装载器和排序召回事件装载器，分别取得后文列表、候选事件及相关历史节点。
3. 提示词组装器填入各区块变量，**将 `{后文节拍概览}` 紧接在当前节点后面**，再放候选事件与相关历史节点。
4. Agent 按需查阅或补查，决定当前节点归入已有事件、新建事件或保留未归属；前两种可同时发生。
5. `confirm` 在当前节点已形成明确处理结果并保存后推进下一任务，不提前完成后文节点。
6. 中断后从未完成任务继续；每轮按当前节点重新装载资料，再由提示词组装器配置上下文。
### 当前节点装载器
由程序调用，获取当前任务的节点，拼装此次要传入的当前节点的内容

### 后文节拍概览装载器

由程序调用，负责取数和排版。

- **输入**：当前节点 ID、读取数量（默认 5，可配置；接口字段名以项目实际为准）。
- **取数**：按全书原文顺序，取当前节点之后连续 5 个节点，可跨章节；不包含当前节点，不足 5 个时取实际数量。
- **输出**：逐条拼成“节点 ID＋概览”的文本列表，作为变量 `{后文节拍概览}` 的值。
- **数据来源**：复用节点数据表已有的节点概览字段。某条概览缺失时保留其 ID，并显示“概览缺失”，不跳过它补取第六条；没有后续节点时显示“无后续节点”。

变量值的格式如下，运行时使用真实节点 ID 和概览：

```text
- <节点 ID>：<概览>
- <节点 ID>：<概览>
```



### 提示词组装器

**各装载器负责准备内容，提示词组装器统一配置模型上下文中的区块、顺序和变量位置。** 两个装载器分别完成自己的取数、筛选或排序、格式化，再提供以下变量：

| 内容来源      | 装载完成的内容                  | 输出变量       |

| 当前节点装载器   | 当前节点概览                   | {当前节点概览}   |

`{当前节点概览}` 包含当前节点真实 ID 及现有完整概览。`{后文节拍概览}` 紧接其后，随后放置 `{排序召回事件}`；每个变量的内容由对应装载流程提供。后文的使用范围在下方规则提示词中简要说明。

#### 二、先把两张表整理成检索材料

这一阶段由代码完成，不调用聊天模型，也不增加业务字段。

##### 1. 为所有节点：准备文本和实体两份材料

节点文本

拼接：

```
涉及人物
概述
详细经过
关键线索

```

字段之间用换行分隔，空字段跳过。



##### 节点实体

分别取得： 


| 类型   | 当前节点字段          |
| ---- | --------------- |
| 涉及人物 | `actorIds`      |
| 地点   | `locationNames` |
| 线索   | `clues`         |


##### 2. 每个事件：准备事件文本

拼接：

```
name
overview
latest_progress
unresolved
clues 关键核心线索
```

这五项就是事件的检索正文。


##### 3. 事件的实体：从成员节点取得

事件本身没有人物、地点字段，就读取它的 `nodeIds`，从 `nodes` 表找成员节点。

| 类型   | 事件这一侧的取得方式                      |
| ---- | ------------------------------- |
| 涉及人物 | 合并成员节点的 `actorIds`，去重           |
| 地点   | 合并成员节点的 `locationNames`，去重      |



##### 4. 从 `nodeIds` 生成反向查询索引

遍历所有事件的 `nodeIds`，在内存中生成：

```
节点 ID → 包含这个节点的事件 ID 列表
```

例如，一个节点同时属于两个事件，这个节点就对应两个事件 ID。

这份对应关系完全由 `events.nodeIds` 生成。它是为了快速查找的索引，**不需要新增关系表，也不成为第二份归属数据来源**。

#### 三、把句子变成可以检索的词项

这是全文检索真正开始之前必须完成的一步。

##### 1. 采用中文分词器

可以使用 Jieba 的搜索模式。它接收中文句子，输出切分后的词项，并支持自定义词典。[fxsjy/jieba: 结巴中文分词 · GitHub](https://github.com/fxsjy/jieba?utm_source=chatgpt.com)

例如：

> 贾珩命人封存赖家账册，并传唤赖二。

配置小说专名词典后的分词结果可以类似：

```
贾珩 / 命人 / 封存 / 赖家 / 账册 / 并 / 传唤 / 赖二
```

这是分词示意，具体结果取决于分词器和词典。

词典中的小说专名从已有字段取得：

- `actors` 中的名称。
- `locationNames`。
- 节点和事件 `clues` 中的特征性名称。

节点文本和事件文本必须使用**同一套分词规则与词典**。

##### 2. 清理分词结果

第一版明确采用：

- 去掉标点、空白。
- 过滤一份固定的小型功能词表，例如“的、了、和、及、并”。
- 保留“不、未、拒绝”等影响含义的词。
- 当前节点作为查询时，词项去重。
- 事件作为被检索文档时，保留各词项的出现次数。

原始句子不修改。过滤只发生在词法检索材料中，向量模型和重排模型仍然使用完整文本。

##### 3. 为事件建立词项索引

程序保存：

```
某个词项 → 哪些事件包含它 → 在各事件中出现几次
```

同时统计：

- 事件总数。
- 每个词出现于多少个事件。
- 每个事件分词后的长度。
- 全部事件的平均长度。

这就是倒排索引及 BM25 需要的统计量。查询文本也要先分词，再利用词项查询索引。[www.elastic.co](https://www.elastic.co/docs/solutions/search/full-text/how-full-text-works?utm_source=chatgpt.com)

词典发生变化时，相关文本需要重新分词，不能让查询侧与索引侧一直使用不同版本。

### 四、执行四路召回

先给出字段对应关系，再分别说明计算方法。

|路线|当前节点提供什么|检索对象是什么|
|---|---|---|
|**A．事件全文检索**|当前节点文本分词后的词项|事件五个文本字段形成的词项索引|
|**B．事件向量检索**|当前节点完整文本的向量|事件五个文本字段形成的向量|
|**C．事件实体匹配**|当前节点的人物、地点、线索集合|从事件及其成员节点生成的实体集合|
|**D．历史节点反查**|当前节点文本与实体集合|历史节点，命中后通过 `nodeIds` 反查事件|

每一路最终最多提供 **30 个事件**。

##### A．事件全文检索：计算共同词项的匹配分

用当前节点分词后的词项查询事件索引，找到至少包含一个共同词项的事件。

然后用 BM25 计算分数。它考虑：

1. 这个词在多少个事件中出现：越普遍，区分能力越低。
2. 这个词在某事件中出现几次：重复会加分，但增幅逐渐减小。
3. 事件文本长度：对长文本进行长度修正。

具体计分：

\[ S_{\text{词法}}(E)= \sum_{t\in Q} \ln\left(1+\frac{N-df(t)+0.5}{df(t)+0.5}\right) \frac{tf(t,E)(k_1+1)} {tf(t,E)+k_1\left(1-b+b\frac{|E|}{avgLen}\right)} \]

其中，`Q` 是查询词项，`N` 是事件总数，`df` 是包含这个词的事件数，`tf` 是该词在事件中的次数，`|E|` 是事件文本分词后的长度。第一版参数可设 `k₁=1.2、b=0.75`。

按这个分数降序取前 30。

例如，“贾珩”出现在很多事件中，贡献较小；“赖家账册”只出现在少量事件中，贡献较大。

##### B．事件向量检索：计算完整文本的语义相似度

事件建立或文本更新时：

1. 拼接事件的五个文本字段。
2. 调用 embedding 模型，把文本转换成向量。
3. 缓存“事件 ID → 向量”。

处理当前节点时：

1. 把当前节点完整文本转换成查询向量。
2. 与各事件向量计算余弦相似度。
3. 按相似度降序取前 30。

公式为：

\[ S_{\text{向量}}(E)= \frac{v_{\text{当前节点}}\cdot v_E} {\|v_{\text{当前节点}}\|\|v_E\|} \]

查询和事件必须使用同一个 embedding 模型。

这一条补充不同表达之间的语义联系，例如“追问款项流向”和“查明银钱去向”。事件向量提前生成，处理新节点时通常只需要计算当前节点的查询向量。[Sentence Transformers documentation](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html?utm_source=chatgpt.com)

##### C．事件实体匹配：比较明确的人物、地点与线索

使用第二节准备好的实体集合。

匹配规则固定为：

- 人物：人物 ID 相同即命中，不区分此次作为行动者还是对象。
- 地点：规范化后的地点名称相同即命中。
- 线索：规范化后的完整线索条目相同即命中。

这里不自动把“账册”和“账本”认定为同一词；这种差异由其他检索路线补充。

###### 实体权重

计算每个实体出现于多少个事件，出现得越普遍，权重越低：

\[ w(x)=\ln\left(1+\frac{N-df(x)+0.5}{df(x)+0.5}\right) \]

`df(x)` 按**包含该实体的事件数**统计。一个人物在同一事件的十个成员节点中出现，仍只算这个事件一次。

###### 事件实体分数

\[ S_{\text{实体}}(E)= \frac{\sum_{x\in F_Q\cap F_E}w(x)} {\sqrt{ \left(\sum_{x\in F_Q}w(x)\right) \left(\sum_{x\in F_E}w(x)\right) }} \]

`F_Q` 是当前节点实体集合，`F_E` 是事件实体集合。没有共同实体或者集合为空，分数记为 0。

按分数降序取前 30 个正分事件。

这样既使用共同实体，也对集合大小做了修正。你不用额外提供“主要人物层级”，人物的常见程度从事件库里统计。

##### D．历史节点反查：先找节点，再得到事件

这一路使用两种历史节点检索。

### 第一步：历史节点的文字匹配

每个历史节点拼接：

```
name + summary + clues
```

使用第三节相同的分词方法，建立历史节点 BM25 索引。

拿当前节点的查询词项检索，得到历史节点排名。这里的文档数量、词频等统计，按**历史节点库**计算。

第一版不把历史节点的 `process` 全文放入这个索引；当前节点的 `process` 仍然参与查询。

### 第二步：历史节点的实体匹配

比较当前节点与各历史节点的：

```
actorIds + targetCharacterIds
locationNames
clues
```

匹配规则和归一化方式沿用 C 路，只是这一次实体频率按历史节点统计，得到另一份历史节点排名。

### 第三步：合并这两份节点排名

使用下一节说明的排名融合规则，将历史节点的文字排名与实体排名融合，得到每个历史节点的综合检索分。

保留命中词项、共同实体及节点 ID，作为后续依据。

### 第四步：通过 `nodeIds` 反查事件

对命中的历史节点，读取第二节生成的反向索引：

```
命中的历史节点 ID → 包含它的事件 ID
```

一个节点属于两个事件，就分别给这两个事件提供候选依据。

同一个事件命中多个历史节点时：

\[ S_{\text{历史}}(E)= \max_{n\in E.nodeIds}S_{\text{历史节点}}(n) \]

**取最佳命中节点的分数，不把所有成员分数累加。**

然后按事件分数排序，取前 30 个事件。

这里必须注意顺序：**先把历史节点汇总成事件，再限制事件数量。** 不能先取 30 个历史节点，再去重成事件，否则这 30 个节点可能大部分属于同一个大事件。

没有归属事件的历史节点，按历史节点综合分另取前 5 条，放入未归属历史节点列表。

# 五、融合四路事件排名，选出最多 40 个

现在有四份事件排名：

- A：事件全文检索。
- B：事件向量检索。
- C：事件实体匹配。
- D：历史节点反查。

将候选按 `event_id` 合并。四路各 30 个，合并前最多 120 个，去重后通常更少。

由于四路分数尺度不同，使用**排名融合（RRF）**：

\[ S_{\text{融合}}(E)= \sum_{r\in\{A,B,C,D\}} \frac{1}{60+\operatorname{rank}_r(E)} \]

某事件没有进入某一路，该路贡献为 0；名次从 1 开始。RRF 用排名融合不同检索结果，常数这里取 60。[Elasticsearch Reference](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion?utm_source=chatgpt.com)

实现时固定三条规则：

- 一个事件在每一路最多计分一次。
- D 路内部的文字、实体匹配已经融合，外层只算一个 D 路。
- 不再额外叠加“命中几个节点”“共有几个人物”等奖励，避免重复加分。

按融合分降序，取前 **40 个事件**。不足 40 个就使用实际数量。

# 六、为这 40 个事件准备重排材料

## 1. 选择代表成员节点

不能只写“选择相关成员”，选择过程也要固定。

针对每个候选事件：

1. 读取它的 `nodeIds`。
2. 从 D 路已经计算的历史节点分数中，找到这些成员的分数。
3. 按分数降序，选前 3 个有正向命中的成员。
4. 如果完全没有命中成员，则补充原文中最早和最近出现的成员作为背景，最多 2 条，并明确标为背景成员。
5. 去重后，按原文顺序展示。

因此，这一步直接复用已有的历史节点检索结果，**不用再调用一次聊天模型挑节点，也不用新增锚点字段**。

## 2. 组装每个候选事件的文本

每个候选的重排文档包含：

```
事件名称：name
事件概况：overview
最新进展：latest_progress
待解决问题：unresolved
核心线索：clues

代表成员：
节点 ID + summary
节点 ID + summary
节点 ID + summary
```

不附全部成员节点，不把完整 `nodeIds` 列表塞进模型上下文。

## 3. 调用重排模型

传入：

|参数|内容|
|---|---|
|查询文本|当前节点的 `name + summary + process + clues`|
|候选文档列表|上面组装好的最多 40 份事件文档|

重排模型对“当前节点与某个候选事件”成对评分。这一步使用完整文本，可以结合具体行为、对象及事件目标评估相关性。[Sentence Transformers documentation](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html?utm_source=chatgpt.com)

实现时保留候选数组下标与 `event_id` 的对应关系。模型返回某个候选的分数后，通过下标准确映射回事件。

最后：

1. 按重排分数降序。
2. 同分时用前面的融合分打破平局。
3. 取前 **10 个事件**。

**最终顺序由重排分数决定，不再把 BM25 分、余弦分、实体分直接加进去。**

# 七、最终返回什么，怎样放进提示词

每个候选事件返回：

|内容|来源|
|---|---|
|`event_id`|事件表|
|`name、overview、latest_progress、unresolved、clues、status`|事件表原值|
|最终重排分数|重排模型|
|命中的检索路线|A/B/C/D 检索记录|
|命中词项、共同实体|检索记录|
|代表成员节点 ID 与概览|通过 `nodeIds` 查到的节点|

这些命中信息属于装载器的返回结果，**不要求新增到事件表**。

格式化成候选卡片时，可以这样呈现：

```
事件 ID：实际 event_id
事件名称：……
状态：……
事件概况：……
最新进展：……
待解决问题：……
核心线索：……

相关成员节点：
- 实际节点 ID：概览
- 实际节点 ID：概览

命中依据：命中“赖家、账册”；历史节点中存在对应的清查承诺
```

“命中依据”由真实的命中词项、实体、节点概览组成，不让装载器凭空生成“已经证明是同一事件”这样的结论。

事件卡片与未归属历史节点列表统一成为 `{排序召回事件}` 的值，再交给提示词组装器：

```
【排序召回事件开始】
{排序召回事件}
【排序召回事件结束】
```

后文节拍概览仍由自己的装载器提供，不混入历史检索。

# 八、索引何时建立、何时更新

不需要每处理一个节点，都重新调用模型计算所有事件向量。

|数据发生什么变化|要更新什么|
|---|---|
|新建事件|事件文本索引、向量、实体集合、成员反向索引|
|修改事件五个文本字段|更新对应文本索引；文本变化时重新计算该事件向量|
|修改 `nodeIds`|更新事件实体集合和成员反向索引|
|新的历史节点可用|加入历史文字、实体索引|
|修改节点内容或人物关联|更新该节点索引，以及受影响事件的实体集合|
|合并或删除事件|删除旧索引记录，按最新 `event_id、nodeIds` 重建对应关系|
|只修改 `status`|更新展示值，不移出检索范围|
|分词词典变化|用一致版本重新分词、更新词法索引|

事件库为空时，返回空事件列表，不调用重排模型；历史未归属节点仍可单独检索。

正常处理一个节点，模型侧主要是**生成当前节点的查询向量，以及对候选事件进行一批重排**。分词、倒排查询、实体比较、关系反查、排名融合，都由普通代码完成。

文本超过所选模型的输入长度时，需要按句切块处理；同一个事件在多个文本块上的分数取最大值，再排序。不能静默截掉超限内容后，把漏检解释成不存在相关事件。

## 五、Agent 工具设计（在原方案上补齐）
（字段不一定真实，以实际项目为准）工具能复用项目已有的就复用

| 工具              | 关键输入 / 行为                                                                                     |
| --------------- | --------------------------------------------------------------------------------------------- |
| `create_event`  | `name、overview、latest_progress、unresolved、clues、member_node_ids`；默认包含当前节点，也可回收已处理的历史节点；返回新 ID |
| `edit_event`    | `event_id` + 可选修改字段；**显式支持 `add_nodes` / `remove_nodes`**，每个新增关系记录具体作用；可改状态并提供依据节点            |
| `get_event`     | `event_id`，返回完整字段和可按需获取的成员节点 ID / 详情                                                          |
| `get_node`      | `node_id`，返回原节点材料，必要时查看详细原文或上下文                                                               |
| `search_events` | 按事项/线索补查**全库**事件，不因闭环而排除，支持两种检索：事件id+相关字段直接检索，关键词检索（只检索名称，概况）                                 |
| `search_nodes`  | 补查已处理节点，尤其包括未归属节点和早期承诺，支持两种检索：节点id+相关字段直接检索，关键词检索（只检索名称，概况，详细经过）                              |
| `confirm`       | 记录当前节点已处理；仅选择未归属时必须附 `unassigned_reason`；不推进后文节点的任务                                                      |

**关于删除和合并：** 逐节点 Agent 可报告“疑似重复事件 / 需要拆分”，但不要默认允许它在处理当前节点时直接删除任意旧事件。实际合并、拆分和成员迁移优先放入第七节的复核任务，避免局部判断污染全书关系。

`confirm` 的有效完成条件：当前节点**至少归入一个事件**，或被明确标记“未归属且有原因”。归入可同时涉及旧事件和新事件；重复提交同一节点不应造成重复关系。

## 六、逐节点处理链路

1. 从 P2 队列取当前节点，取得当前节点的完整材料。
2. 后文节拍概览装载器、排序召回事件装载器分别装载好内容，提供 `{后文节拍概览}` 和 `{排序召回事件}`。
3. 提示词组装器统一配置上下文，按“当前节点—后文节拍概览—排序召回事件”的顺序填入变量，交给 Agent。
4. Agent 判断当前节点；资料不足时，使用现有工具查阅详情或补充检索。
5. 保存当前节点的归属、新建事件或未归属理由，按需更新事件字段。前两种结果可同时发生，也可依原规则追溯关联历史节点。
6. `confirm` 完成当前任务后进入下一节点，重新装载并组装上下文。


**特殊情况：**

- 第 150 章发现与第 10 章未归属节点有关：新建/找到事件后，**同时关联两个节点**，不需重新运行第 10 章任务。
- 已闭环事件找到补充节点：仍允许关联；先判断只是补证据，还是说明旧结论需修正。
- 节点同时推进两件事：建立两条独立的事件—节点关联及不同作用说明。
- 某节点只有喝茶、场景过渡等内容：保留未归属，`confirm` 记下原因，不建空事件。

## 七、批次复核（独立于逐节点串联）

不要求每个节点都执行全书整理。建议按章节批次或约 30～50 个节点做一次定向复核，并在全部节点处理完后整体复核一次；频率可视测试调整。

复核重点：

1. **重复事件**：不同事件是否处理同一核心事项，需合并并迁移成员关系。
2. **过大事件**：是否把整条故事线当成事件；能否拆出各自目标和完成条件。
3. **未归属节点**：是否与后续事件构成起因、伏笔、证据或结果。
4. **遗漏的交叉归属**：一个节点是否实际推动多个事件，却只关联了一个。
5. **过早闭环**：是否尚无明确结果就被判为已闭环；不能把已闭环直接当作不再可关联。

复核时优先根据可疑事件/节点做局部比对，**不把所有节点和事件一次塞给模型**。合并/拆分须记录原事件 ID 的对应关系，避免丢失引用。

## 八、验收用例与效果指标

至少用以下情况做一组人工核对样例：

| 测试用例 | 预期结果 |
|---|---|
| 早期允诺清查赖家，百章后正式行动 | 召回旧事件，不能重复立件 |
| 早期节点未归属，后续形成明确案件 | 找回旧节点，追溯关联新/旧事件 |
| 已闭环案件又出现补充证据 | 仍可添加关联，不强制改变状态 |
| 审问赖二发现官员勾结 | 一个节点可同时推进两个事件 |
| 贾珩在府中喝茶且无剧情作用 | 标记未归属并记录原因 |
| 只因主角相同而检索到大量事件 | Agent 能拒绝错误候选，必要时二次检索 |
| 两个名称不同的事件实为同一事项 | 批次复核能发现并提出合并 |
| 当前为查案准备，后续节点继续执行同一调查 | 能用后文理解事项范围，避免把每个步骤单独立件 |
| 后文节拍概览中已出现查案结果 | 本轮仍只保存当前已达进展，后文节点保持待处理 |
| 后续 5 个节点切换到其他故事线 | 不因相邻而强行合并，也不因暂时中断而关闭当前事件 |

重点观察：`Recall@10`（正确事件是否进入候选前 10）、实际关联正确率、重复立件数量、早期伏笔回收数量、错误闭环及其纠正情况。先建立人工样例基线，再决定是否需要更重的重排模型；**不要先凭感觉定 RRF 权重或模型阈值**。 对后文窗口，使用同一批样例对比“不加后文 / 加后续 5 个概况”，检查错误拆分是否减少，同时检查错误合并、遗漏独立事件和提前写入后文结果是否增加；不要仅以事件总数减少判断有效。

# 事件串联提示词

## 一、身份与定义

你是本书的叙事结构编辑。依据小说原文，将分散的剧情节点整理为可追溯的具体事件。确认整理分配完后直接调用confirm工具结束任务

**节点**：从小说中提取的单一剧情节点，由下方直接提供。

**事件**：围绕同一项具有独立叙事意义的事情，由起因、行动、变化和结果构成的可追踪过程。
事件也可以描述重要人物之间的关系变化。例如人物的结识、误会与和解、情感确认、婚约争取等。相关节点需要共同推进一段具体的关系变化，而非仅仅涉及相同人物。

事件不一定始于明确的目标。某些突发事件也具有独立叙事意义，例如遇袭、意外、重大冲突等。只要能够识别事情的发生、发展及其造成的结果，同样可以构成事件。
事件须满足：

1. **事项明确**：能够回答“正在发生或处理什么事情”。
    
2. **具有独立性**：不是另一件事的普通执行步骤或局部结果。
    
3. **进展可追踪**：能够识别起因、重要变化和阶段结果，允许尚未结束。
    

事件可以跨越多个章节，相邻节点也可能推进不同事件。

例如，贾珩与凤姐商议清查赖家贪污→抓捕赖二→审问赖二→赖奶奶向贾母求情→查抄赖家，由节点共同构成“贾珩清查赖家贪污”事件。

又如，范仪诉冤→贾珩允诺→御前陈情→朝廷议定查办，共同构成“贾珩为范仪争取朝廷查办冤案”事件。

## 二、任务

后文节拍概览用于辅助判断当前节点的作用和事件边界，相邻不等于同一事件。本轮不提前关联或完成后文节点，也不把后文结果提前写入事件字段或闭环状态。

针对当前节点，选择以下处理方式：

**1. 归入已有事件**

将节点归入其实际推动的已有事件，说明该节点的具体作用，并根据新增事实选择性更新事件字段，无须强行修改所有字段。
需要完成：

- 将节点关联到对应事件。
    
- 说明当前节点对该事件的具体作用，例如提供起因、推动行动、揭示矛盾、构成阻碍、带来转折或形成阶段结果。
    
- 根据新增事实，判断是否需要修改事件名称、事件概况、事件最新进展、待解决问题及核心关键线索。
    
- 如果新增节点没有改变某个字段的内容，可以保留原值，不必强行更新。
  **一个节点可以同时归入多个事件。** 但必须分别说明该节点对每个事件的实际推动作用。

**2. 新建事件**

当节点引入需要独立追踪的新事项时，新建事件并填写全部字段，说明立件理由。
需要完成：

- 创建事件。
    
- 将当前节点归入新事件。
    
- 填写事件名称、事件概况、事件最新进展、待解决问题及核心关键线索。
    
- 说明新事件的核心事项，以及为什么需要独立追踪。
    

如果当前节点同时推动已有事件和新事件，应同时建立相应归属，不必二选一，也就是说一个节点可以即归属某个事件，又可新开启一个事件

**3. 保留未归属**

当节点既未推动已有事件，也不足以构成独立事件时，保留为未归属节点，说明原因，完成本轮处理。后续发现新的关联时，可以重新归属。直接调用confirm工具结束任务

同一节点可以同时归入多个事件，包括已有事件和新事件。


## 三、Q&A

**Q1：什么时候归入已有事件？**

当节点陈述的事实、人物行为或关系变化，能够实际推动该事件的发展时，应将其归入该事件。

这种推动可以表现为：

- 引出事件的起因或目标。
    
- 为实现目标采取行动。
    
- 揭示新的关键事实或线索。
    
- 形成阻碍、冲突或转折。
    
- 改变事件当前状态。
    
- 产生阶段结果或最终结果。
    

归属的关键是节点与事件之间存在实际的剧情推进关系。

**Q2：什么时候新建事件？**

当节点引入具有独立叙事意义的新矛盾、目标或状况变化。

判断重点是：**两个事项能否分别说清核心目标及独立的完成条件？**

：**只要核心事项足够独立、可以持续追踪，已有一个明确起因/承诺节点也可以立件，不要求当下已有结局。**

判断是否需要新建事件，重点考虑：

1. 是否出现了新的核心矛盾、目标或具有独立意义的状况变化。
    
2. 这件事情能否独立于其他事件进行追踪。
    
3. 是否能够判断其后续发生了什么变化，以及何种事实可以表明它取得了阶段结果。
    

不得仅因出现新人物、新地点、新对话或新信息就创建事件。
也不得仅因为某节点与已有事件无关，就强制为其创建新事件。

例如，审问赖二时发现官员与赖家勾结，可以另建“追查官员与赖家勾结”事件。审问节点同时归入“清查赖家贪污”和“追查官员勾结”，分别推动两件事。

**Q3：什么时候保留未归属节点？**

当节点只是日常行为、场景过渡或普通对话，没有实际推动已有事件，也没有形成值得独立追踪的事项时。

例如：

- 贾珩在府中喝茶。
    
- 贾珩前往皇宫。
    
- 贾珩与丫鬟闲聊。
    

如果这些行为没有其他剧情作用，可以保留未归属，并说明理由。但若喝茶时发现有人下毒，或闲聊中获得关键证据，则应按实际剧情作用重新判断。

**Q4：人物关系事件如何划分？**

围绕一段具体的关系变化划分，例如相识、误会与和解、争取婚约等。连续推进同一矛盾的节点可以合并；形成新的独立矛盾时可以另立事件。不得把两个人物贯穿全书的所有互动合并为一个笼统的感情事件。

## 四、字段要求

- **事件名称（5—20字）**：核心主体（可选）＋核心事项＋发展方向。描述整件事，不预设尚未发生的结果。禁止一个标题讲多件事
- 贾珩清查赖家贪污 （可行）
- 贾珩为范仪争取朝廷查办冤案（可行）
- 贾珩追查官员与赖家勾结（可行）
- 牛继宗质问贾赦，贾赦透露云光通匪断言贾珩必死（否决：没有讲清事件的核心）
- 贾珩入主宁国府，贾族迎候并推举族长（否决：逐项罗列动作，未概括核心事项）
    
- **事件概况（10—30字）**：简述事件的核心事项及已知全貌。应随着已知事实增加而适当完善，但不得虚构尚未发生的情节。
    
- **事件最新进展（10—30字）**：简要说明按照小说剧情的实际时间顺序，该事件目前已经推进到什么阶段，取得了什么进展或结果。
    
- **待解决问题（10—30字）**：简要说明事件仍然存在的矛盾、尚未实现的目标，或后续需要追踪的事项。
只记录有事实依据的未解决问题，不得凭空制造新的矛盾。
如果事件已经完成，且没有遗留问题，可以填写“事件已结束，暂无待解决问题”。
如果只是达成阶段目标，但仍存在明确的后续问题，应如实说明。
    
- **核心关键线索（每项2—20字）**：记录具有辨识意义的核心实体或关键线索。
只能使用名词或名词性短语，不得使用完整句子。
可以包括：
- 关键人物。
- 关键组织或家族。
- 具体地点。
- 重要物品或证据。
- 案件名称。
- 其他具有辨识意义的特殊实体。
例如：范仪冤案、范仪、赖家、赖二、赖家账册、特殊石头。
优先选择能够辨别当前事件的特殊线索，避免堆砌所有出现过的人物和普通事物。

新建事件必须填写全部字段；已有事件仅更新确实发生变化的字段。

## 五、核心规则

1. **事实优先**：已有目录、摘要和归属可能有误，以小说原文为准，不得虚构人物动机、因果或结局，使用真实编号。
    
2. **避免过度拆分**：同一事项的商议、准备、执行、阻碍和结果通常属于同一事件，不按动作分别立件。
    
3. **避免过度合并**：不能将整条漫长故事线合并为一个事件。例如“剿匪行动”是一个很长的故事线，不应该设为一个事件其中包含“调查官员通贼”“替匪首申冤”等事件可以分别追踪。
    
4. **允许多归属**：同一节点确实推动多个独立事件时，应分别关联并说明作用。
    
5. **允许未归属**：不能为了完成分类而强行归属或创建事件，未归属并说明理由同样视为处理完成。
    
6. **按事实维护状态**：只更新需要变化的字段；较早节点不能覆盖事件的最新进展，已达到阶段目标的事件不必无限延续。
