## 1. 当前项目范围

WestWorld 是基于小说资产的本地 AI 互动小说/文字冒险产品，目标是玩家能够自由行动、改变原著、创造新故事线，世界状态持续有效，AI 以作家方式维持剧情质量。

**已完成的上游能力，不要重新规划：** 小说导入、人物、地点、关系、原著事件节点、事件线/时间线整理等资产工作。游戏侧只需要**读取和映射**这些数据；缺少开局时间点状态或依赖信息时，才讨论如何接入与补足。

技术约定：现有本地存储；`pi-ai` 做模型统一调用，`pi-agent-core` 做 Agent 循环，`TypeBox` 定义工具和结构化协议，Prompt 以 `.md` 管理。**不要假定三 Agent 的游戏游玩闭环已经写好。**

## 2. 已明确的目标职责

- **现场导演 Agent**：每次玩家输入都先经过它。负责合理性审核、一次申诉、查证本局状态、判断行动结果、NPC 反应、编排即时场景、识别是否造成**重大宏观剧情影响**。导演此时只报告是否需要重规划，并非负责自己重写整条未来大纲。
- **编剧 Agent**：负责未来篇章方向、伏笔、人物弧光、长期矛盾和宏观改稿。初始化时可参与，平常仅在**导演判定重大偏离**时调用；无权推翻已成立事实。
- **写手 Agent**：根据导演给出的场景执行框架产出正文，负责文学表达；不需要长期独立的世界记忆，不擅自改变关键结果。
- **世界引擎/数据库**：原著资产（Canon）只读；本局已发生事实（State）不可任意篡改；尚未发生的剧情计划（Plan）可调整。持久化世界变化、任务版本、回合快照及回滚。

用户特别强调：**想要极高自由度，但不能靠海量 Prompt 穷举行为；AI 必须像作家一样提前规划、铺垫、改稿，同时保证长期事实不丢失。**

## 3. 最新确定的 MVP 交互流程（最重要）

1. **游戏开局：** 从小说**第一章**原著主角当前所在位置和已知世界背景进入；生成并显示环境、背景和人物等**开场白**。
2. **玩家输入：** 可写单个行动、一系列操作，也可提出包含 NPC 动作、未来剧情方向的整段剧情。玩家提出别人的反应≠该反应直接成为事实。
3. **导演审核合理性：** 检查在当前世界条件下是否可以尝试；合理则继续；明显不合理则**撤回玩家这条消息**，允许对**同一条消息申诉一次**。
4. **申诉：** 玩家补充理由。通过则由导演结合原消息和补充理由改写为可执行输入，**代玩家送回正常流程**；不通过则拒绝并关闭该条消息的申诉入口，玩家重新输入。审核失败不产生世界状态变化。
5. **导演即时编排：** 查询当前人物/地点/物品/事件，判断实际成功、失败或部分成功以及 NPC 的即时反应，输出下一段正文应体现的场景与行动链。**允许尝试≠保证行动成功。**
6. **重大影响检测：** 导演判断实际结果是否足以影响宏观剧情/原著重要事件。普通动作细节、地点或表达的小改动（只要关键结果不变）**不触发**编剧；破坏关键前提则触发。导演只作影响判定和上报，不负责本次宏观改稿。
7. **下游并行：** 写手每回合生成正文；若需要编剧，**编剧重规划与写手生成并行**，而非让编剧先写完再让写手写。
8. **回合锁定：** 玩家发送后新回合输入被锁。写手生成完后**可以先显示正文**，但是**编剧若还在规划就必须继续锁定输入**；编剧也完成并保存后才进入下一回合。无编剧任务则写手完成即可解锁。失败需可重试恢复，不能永久死锁。
9. **玩家改写：** 点击**最后一条 AI 回复**右下角菜单「改写」，描述改写方向。**恢复到本轮玩家行动之前**的世界状态、记忆和编剧计划，废除旧正文/旧任务/旧变更；经过导演审核和即时编排，必要时再次触发编剧，并交写手生成新正文。MVP **只允许改写最后一条 AI 回复**，不支持回溯任意远的历史。
10. **继续游戏：** 下一轮同样执行上述流程。

## 4. 决定性的产品原则

1. **既成事实优先。** 皇帝被杀如果只是可尝试的行动，可能失败；一旦实际成功并结算，就不能为了按原著发展而把皇帝写活。
2. **原著不是强制轨道。** 玩家完全离开《红楼梦》的原有舞台去乡村生活，也应能展开新的故事，而非被导演拖回主线。
3. **偏离不等于重大改稿。** 要看关键结果和事件前提是否变化，而不是拿文本与原著逐字比较。
4. **一次拒绝、一次申诉。** 申诉失败限制的是这条被撤回的消息，用户仍可重新输入新消息。
5. **编剧不在每回合同步链。** 只有重大变化或开局规划才调用；写手与编剧可同时工作，但本轮未完成不能解锁。
6. **改写必须整体回滚。** 包括正文、事实、NPC 状态、剧情计划和派生任务；不能只重写一句话，留下旧世界线污染。
7. **已经发生的事实需要程序保存和查询。** Agent 自带会话/上下文不等于稳定长期记忆。

## 5. 开发排期口径（读取主需求的 P0/P1/P2）

- **P0：完整交互 SOP + 基本状态闭环。** 第一章开局、自由输入、合理性审核/撤回/一次申诉、导演实时编排、重大影响标记、写手+条件触发的编剧并行、输入锁、最后一轮改写、存档/恢复/测试。
- **P1：宏观创作能力强化。** 长期计划、人物认知与动机、事件因果和伏笔管理、动态路径、新篇章、合理的触发阈值与导演—编剧交接。
- **P2：后台持续演化。** NPC 和事件后台调度、多故事线并行、长期记忆检索、大跨度时间推进、性能/质量评测和多轮分支回溯。

注意：**P0 能偏离原著继续游玩**，但无需达到 P1 的长篇复杂编剧质量和 P2 的全世界后台推进程度。

## 6. 重要边界与尚未定案的问题

这些问题应在接下来**一项一项讨论**，不可假装已决定：

1. 导演如何区分「合理可尝试」「玩家声称已成功」「玩家要求创造 NPC 行动」以及「修改世界规则」？多动作输入是全部审核还是部分通过？
2. **导演给写手的结构化场景执行单**到底有哪些字段？如何限制写手的关键事实创造权，又不影响文学自由？
3. 导演基于**实际结算结果**判断重大剧情影响的具体标准、所需查询、漏判兜底是什么？
4. 编剧最小计划在**开局**应该规划到哪里、产生什么结构；剧情偏离之后应返回怎样的计划变更？
5. **回合事务设计**：世界状态何时正式提交；写手和编剧基于哪个版本读取；并行编剧失败、页面刷新、改写取消旧任务等如何保证一致性？
6. 文本已显示、编剧尚未完成、输入锁定这一状态如何反馈给玩家；失败重试如何解锁？
7. 人物长期认知、后台事件、上下文压缩、世界调度等以后再详细设计；当前不要把讨论拖向全量工程实现。

## 7. 推荐新窗口接续顺序

**第一步：** 阅读主需求文档第 3 节的 MVP SOP，确认是**现在要设计的产品交互**，不要退回到“要几个 Agent”的泛讨论。

**第二步：** 优先细化**「导演输出的场景执行单」**（输入、输出、字段、哪些是确定事实、哪些是写手可自由表达、重大影响标记如何交给编剧）。这是串联世界状态、编剧、写手的关键协议。

**第三步：** 再讨论回合锁与回滚事务的具体运行机制，尤其是写手/编剧并行和改写产生的旧任务作废。

**第四步：** 最后进入合理性审核策略、宏观影响阈值和世界状态检索策略等具体设计。每定一项，再回填主需求。
