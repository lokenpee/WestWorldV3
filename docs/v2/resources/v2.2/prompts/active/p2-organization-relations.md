# 第三步：整理人物关系

- 输入 `work.data` 已包含当前人物必要介绍和全部当前关系的精简概览：`targetId`、`targetName`、50字以内 `identity`、双向 `forward`/`reverse` 标签、`state`、方向是否存疑 `unclear`、`fingerprint` 和已核对 `checked`；不含证据原文。`unlinkedRelations` 是尚未关联到人物的原始关系，不是已有人物对的待核对状态。
- 先整体判断全部关系，再决定保持、规范化、查证或待核对；不要按每两个人拆成独立任务。默认依赖这份完整概览，不要为了确认每条关系反复读取整份列表。标签明确、没有“未知”、没有方向存疑、也没有双向矛盾或身份冲突的关系，默认直接视为保持，不查询证据。`unclear` 缺失或为 `false` 不等于绝对正确：发现双向矛盾、身份冲突或其他明确疑点时仍要查证。
- 普通去重、同义规范化、清理称谓、删除冗余“未知”可以直接提交，不需要原文证据。只合并能确定的同义关系，不把职务、朋友、同僚、亲属等不同维度强行合并；“未知”是合法结论，不要为了清理而猜测。
- 只有实质矛盾、方向错误、新增具体关系或改变辈分/身份时才需要查证。查询证据必须用 `query_relation_work` 的 `targetIds` 指定疑问人物对，并把 `"evidence"` 放进 `fields` 数组（例如 `fields:["targetId","evidence"]`）；不要传 `evidence:true`，也不要无 targetIds 全量查证据。多组疑点需要同类字段时，用一次 `query_relation_work` 传多个 `targetIds` 批量查询；只有单个疑点需要完整人物对视图时才用 `get_character_relation`。能查到原文时，在 `changes[].evidence` 提供 `chapterIndex` + 引文；查不到或引文不够逐字时，系统会把它保存为“未核实”并列入待核对，不会因此拒绝其他正常修改，也不需要为同一项反复搜索原文。
- 关系方向相对当前人物：`forward` 是当前人物相对目标，`reverse` 是目标相对当前人物。贾珩查问赖家时，贾珩一侧是“查问者”，赖家一侧是“被查问者”。省略 `directionUnclear` 表示保持原存疑状态；只有明确确认方向时才传 `false`。
- 删除整组关系属于高风险操作，必须有逐字原文，或可追溯的冲突/识别错误 `basis`（原始关系编号、相关人物对读取记录、资产识别冲突）。没有依据时不要删除，保留原关系并标记 `uncertainPairs`。
- 人物身份不能单独证明具体关系：例如“鸳鸯是贾母的丫鬟”不能推出“贾珩与鸳鸯是族中长辈/晚辈”；“林黛玉是表小姐”不能推出她与贾珩是族亲。引文必须直接支持判断，能找到一句原文不等于这句话支持结论。
- 先形成稳定判断，再提交。已确定、待核对、保持不变要分开：已确定用 `changes`，待核对用 `uncertainPairs`（`targetId` + 原因），保持不变不提交。程序会把“未提交修改”记为本次未修改，不表示已逐对确认；没有明确依据时不要声称某对关系正确。
- 修改较多时按实际情况分批，用 `done=false` 保存后继续；不设固定数量，避免每 1～2 对提交一次。合法项会先写入，未提交项在 `failed` 中返回 `targetId`、`code`、`action`：`recoverable=true` 先重新读取该人物对再重试；`repeated=true` 表示同一错误已重复，停止该项并标记待核对。不要重复已成功的项。
- 同一人物对原则上只提交一次；再次修改必须有新信息。相同失败没有新依据时停止原样重试，把该项标记待核对并继续其他工作。
- 同一提交不要重复 `targetId`；某个人物对冲突时只重新读取该对。没有需要修改的关系时提交空 `changes` 和 `done=true`；有 `uncertainPairs` 也可以结束，程序会记录待核对状态。本工作项不使用 `submit_result`，也不发额外结束总结。
