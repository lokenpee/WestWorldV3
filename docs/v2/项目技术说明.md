## 游玩 MVP · 导演与写手

REQ-039（关联 REQ-034），2026-11-26 第四稿，待确认。导演准备开局、裁定玩家行动，并按发生顺序交给写手本场可见的动作、回应及停笔位置。写手将这场戏写成正文，程序一起保存裁定与正文。历史摘要按需处理已结算回合。编剧及其大纲接口暂缓，首期请求、存档和备份均无需编剧结果。开局首次确认时固定所选卡，生成失败可按该卡重试。保存回合时，程序同时记下导演决定让玩家接话的位置。整书导出拟沿用现有导入容量限制，在交付文件前校验。现有游玩页是占位入口。拟接入选包、包内新建或继续存档、传统聊天、一次申诉与末轮改写。每次新建存档时保存一份游戏可读的书中资料。续玩时从这份资料和本局当前生效的回合中取材。节点详情内的人工阅读器负责「查看原文」，章节及节点引文不进入游戏和模型工具。正式入口使用本机存储服务，验收同时覆盖 IndexedDB。[产品需求与游玩用语](../../openspec/changes/play-three-agent-mvp/proposal.md#terms) · [运行顺序](../../openspec/changes/play-three-agent-mvp/design.md) · [存储契约](../../openspec/changes/play-three-agent-mvp/storage.md) · [资料装载](../../openspec/changes/play-three-agent-mvp/context-loader.md) · [各角色的提示词与返回结果](../../openspec/changes/play-three-agent-mvp/agent-contracts.md)

## P3 事件工具

REQ-032 的第二阶段拟改为每次处理一个已审事件，然后核对相关故事线的分界、逐线核对进展。进入第二阶段仍受第一阶段验收开关控制。单件能否开线已有用户结论：原文已提出可跨事件追踪的问题即可建立故事线，其余可保留独立。事件已证实归入一条线时，其他可能归属在报告记录查证范围和证据缺口，其余任务核完后可完成全书。拟议的工具参数、数据读写、失败恢复、逐任务提示词及同书请求样例集中从[故事线方案](../../openspec/changes/recast-p3-storyline-workflow/proposal.md#agent-方案材料)进入。下方是第一阶段当前生效的工具。

每种任务各暴露六个工具。三个搜索工具都使用 `groups: string[][]`；每组至少一个非空词，组内全中，组间任一组命中。节点编号与事件编号都是字符串。传 `return_fields` 时编号始终返回。复核允许按范围搜节点；串联由后台用当前任务限定前序搜索范围。[声明](../../src/features/story/eventToolsSchema.ts) / [读取与保存](../../src/features/story/eventWorkflow.ts) / [模型回包](../../src/features/story/eventToolReply.ts)

| 工具与模式 | 请求参数 | 模型实际收到的结果 |
|---|---|---|
| `get_nodes` · 两者 | `node_ids: string[]`，`return_fields?: string[]`。可选 `name, summary, detail, quote, source_position, event_ids`。串联可读前序、当前和后文概览覆盖的最多 5 个节点；复核可按全书编号读取。 | `items` 默认每项为 `node_id, name, detail`；有未找到或不可见编号才附 `not_found_ids`。`detail` 取库内 `process`。 |
| `get_event` · 两者 | `event_id: string` | 返回 `event_id, name, overview, latest_progress, unresolved, clues, status, members`。`members` 按书中顺序列出 `node_id, name`。未找到返回 `{event_id,status:"not_found"}`。 |
| `search_events` · 两者 | `groups`；`return_fields?` 可选 `name, overview, latest_progress, unresolved`。用名称和概况匹配。 | `items, total, truncated`；默认每项 `event_id, name, overview`，最多 100 项。 |
| `search_prior_nodes` · 仅串联 | `groups`；`return_fields?` 同 `get_nodes`。只搜当前节点之前的详细经过，含已有归属节点。 | `items, total, truncated`；默认每项 `node_id, summary`，按从近到远返回最多 20 项。 |
| `search_nodes` · 仅复核 | `groups`；`after_node_id?, before_node_id?, exclude_event_id?` 是字符串或 `null`；`return_fields?` 可选 `name, summary, detail, event_ids, source_position`。搜索详细经过，开区间，按需排除指定事件的成员。 | `items, total, truncated`；默认每项 `node_id, name, summary`，最多 100 项。 |
| `edit_events` · 两者 | `changes: Operation[]`，至少一项。操作参数见下表。 | `ok, created, updated`。串联另有 `current_node_assigned`。复核发生删除或产生未归属节点时附 `deleted_event_ids`、`unassigned_node_ids`。 |
| `confirm` · 串联 | `result:"completed"`；当前节点没有归属时须给非空 `unassigned_reason`。 | `{confirmed:true,result:"completed"}`。 |
| `confirm` · 宏观 | completed 确认本组；处理转回时可附 reason。pending_review 须带 pending_issues，每项含 issue、checked_scope、reason。 | 确认本组后重新选组，单组确认不计入逐件主审。 |
| `confirm` · 微观 | completed 只确认当前一件的当前版本。pending_review 同上。return_to_macro 须带 event_ids、evidence_node_ids、reason。 | 转回时优先调度指出的结构疑点；完成宏观后重新主审有影响的存续事件。 |

### 编辑操作与字段

| `op` | 必填 | 可选 | 实际效果 |
|---|---|---|---|
| `create` | `fields, reason` | `evidence_node_ids` | 程序分配事件 ID，`fields` 包含全部七个字段。 |
| `update` | `event_id, fields, reason` | `evidence_node_ids` | 至少提交一个变化字段。`nodeIds`、`clues` 都按完整数组替换。已装载的最新完整成员可直接用于替换。 |
| `delete` · 仅宏观复核 | `event_id, reason` | `evidence_node_ids, replacement_event_ids` | 替代 ID 指向本次操作结束后仍存在的其他事件。 |

| 工具字段 | `storyEvents` 中的字段 | 类型与含义 |
|---|---|---|
| `name / overview / latest_progress` | `title / summary / latestProgress` | 非空字符串，分别为事件名、概况、截至当前的进展。 |
| `unresolved` | `unresolved` | 字符串，填写本事件的遗留问题，闭环无遗留可填空串。 |
| `clues` | `clues` | 非空字符串构成的数组，数组可以为空。 |
| `status` | `status` | `进行中`、`暂时搁置`、`已闭环`。 |
| `nodeIds` | `nodeIds` | 非空、去重的成员编号数组；程序按书中顺序保存。串联保留已有成员，只能增加当前或更早的节点。 |

一次 `edit_events` 的所有操作在同一事务中保存。同任务同调用键重试会核对原参数，再从回执投影短结果。`created` 项含 `event_id, name`，`updated` 项含 `event_id`。实际有成员变更时附 `added` 或 `removed`，只有保存值与提交值不同才附 `saved_fields`。`pipelineRuns` 记录完整操作与快照，整理详情以本地代码比较字段和成员。错误包含 `ok:false, tool, code, reason, taskId, mode, part, hint`，按情况附 `operationNumber, fields` 等。参数错误按实际 `op` 报告字段位置。[校验、事务、幂等](../../src/features/story/narrativeTools.ts) / [成果计算](../../src/features/story/eventTaskOutcome.ts)

例如，`E1` 已含当前节点时，更新进展的调用和模型回包可以是：

```json
{"changes":[{"op":"update","event_id":"E1","fields":{"latest_progress":"黄泰说出了送信人的名字，贾珩令蔡权核对名册。"},"reason":"当前节点交代了供述及随后的核对安排"}]}
```

```json
{"ok":true,"created":[],"updated":[{"event_id":"E1"}],"current_node_assigned":true}
```

### 候选事件如何装入当前节点

节点 `clues / actors / locationNames` 按 0.5 / 0.3 / 0.2 加权，匹配事件名称、概况、最新进展、待解决问题和线索，五个事件字段各占 0.2。关键词取前 20；节点 `process` 和事件 `unresolved` 各自建立向量，按余弦相似度再取前 20。按名次融合，单路贡献为 `1 / (60 + 名次)`，取前 30。重排用节点概述作查询、五个事件字段拼接作候选，最终最多 10 个，按实际数量加载事件及成员编号和名称。

启动或继续时先准备向量，空问题跳过。节点 N 进入 Agent 处理时预取 N+1，交接时按当下事件集重新核对，变化内容重新计算。向量或重排服务失败时记录降级并采用本地排序。候选已覆盖全库时，装载器把实际事件总数写入输入。模型依据剧情判断归属；检索分数留在诊断数据中。[排序与预取](../../src/features/story/eventCandidates.ts) / [装载输入](../../src/features/story/narrativeInput.ts)

## 本机存储协议

桌面本地服务设置 `WESTWORLD_STORAGE_DIR` 时，Vite 挂载 `POST /api/storage`。前端发同源 JSON，正文用 `action` 区分操作。成功统一返回 `{ok:true,result}`，失败返回 `{ok:false,error}`。来源检查限定回环主机和同源调用。`scope` 取 `settings` 或 `book:<bookId>`。`table` 必须是该范围的已登记表名。存储记录为 `{key,value,version}`，业务对象的 `revision` 在 `value` 内。[HTTP 入口](../../src/features/local-storage/vitePlugin.ts) / [类型](../../src/features/local-storage/contracts.ts) / [服务端分派](../../src/features/local-storage/server.ts)

| `action` | 请求字段（除 `action`） | `result` 语义 |
|---|---|---|
| `status / backup / exists` | 状态可传 `since,epoch`；备份无额外业务参数；存在性查询传 `scope` | 服务状态或自指定修订后的通知、本机备份时间、范围是否存在。 |
| `begin / commit / abort` | 开始传 `scope,tables,write`；结束传 `scope,transaction` | `begin` 成功返回事务 ID，占用时可返回 `null`；`commit` 持久化暂存变更；`abort` 释放事务并丢弃暂存写入。 |
| `get / bulkGet / credentialPresent` | `scope,table,key` 或 `scope,table,keys[]`；可传 `transaction` | 单记录或 `null`；批读按输入顺序逐项返回；凭据存在性只返回布尔值。 |
| `query / count` | `scope,table,query?,transaction?` | 记录数组或数量。`query` 可含 `index,operator,values,reverse,offset,limit,keysOnly`。`operator` 可取 `equals, anyOf, noneOf, startsWith`。[查询参数](../../src/features/local-storage/schema.ts) |
| `add / put / remove` | `scope,table,transaction,key`；新增、覆盖传 `value` | 须在写事务内。返回主键；`add` 拒绝已有主键；写入的主键须与正文一致。 |
| `bulk / bulkRemove / bulkUpdate` | 写事务；分别传 `rows[],add?`、`keys[]`、`updates:[{key,changes}]` | 批写与批删返回 `null`，批更新返回实际更新数。 |
| `assetPage / tracePage / executionPage / executionBody` | `scope,options`；资产分页还传 `kind` | 分别返回资产列表页、追踪分页、请求分组页及指定请求内容。[资产分页](../../src/features/assets/assetPage.ts) / [执行链类型](../../src/features/agents/executionPagingTypes.ts) / [查询实现](../../src/features/local-storage/executionQueries.ts) |
| `publishMigration / migrateSettings` | 前者传 `book,digest,counts,source`，后者传 `appSettings?,credentials?` | 前者核对暂存书库各表数量后发布，返回 `alreadyApplied`；后者迁移尚未存在的设置与凭据。 |

请求示例，查询当前书的一条事件：

```json
{"action":"get","scope":"book:demo","table":"storyEvents","key":"E1"}
```

| 原文、资产、归属 | `chapters` 与 `chapterTexts` 用 `chapterIndex`；`characters, locations, nodes, storyEvents, eventLines, characterRelations, legacyRelationRecords` 用 `id`；`characterRelationEdits` 用 `pairKey`；`assetLifecycle` 用 `key`。 |
| 提取和进度 | `compileProgress.stage`、`extractionReceipts.key`、`extractionTasks.id`、`extractionInputs.id`。 |
| 运行、历史、检索缓存 | `pipelineRuns, storySessions, storySessionEntries, storyEditorMemory, storyEditorNotes, storyEditorCheckpoints, eventRetrievalVectors` 均用 `id`。`pipelineRuns.recordType` 区分运行、任务快照与工具回执等记录。 |

字段类型、可空、必填、条件分支见[存储 Schema 的 $defs](resources/v2.2/storage.schema.json)和[字段说明](03-Spec-数据与存储.md)。`eventRetrievalVectors` 的读写与数据依赖见[向量缓存](../../src/features/story/eventVectorCache.ts)；备份路径的引用完整性由[整书数据校验](../../src/features/backup/data.ts)落实。业务文本的推荐字数写在提示词里，写入与恢复遵循[仓库字段规则](../../AGENTS.md#字段数据流与触发逻辑)。

## 技术变更交接

交接时把“当前”和“拟变更”标清。已确认但尚未实现的改动标注关联需求和生效条件；开发验收后再把条目标为当前。修改顺序以[仓库开发指令](../../AGENTS.md#技术文档先行)为准。

| 要改什么 | 在本册及对应材料中先确定什么 | 实施后对照什么 |
|---|---|---|
| 新增、删除、改名或调整工具 | 任务、可见性、完整参数、必填和可空、默认值、返回、错误、读写范围；影响旧任务时写明恢复口径 | 模型声明、参数准备、执行分派、短回包、实际持久化、回放与详情。 |
| 修改接口、字段或技术参数 | 调用方、请求与响应、单位、默认值、超时与失败处理；列出受影响的存储、备份、设置和使用页面 | 客户端与服务端、成功与失败示例、旧数据的读取或恢复。 |
| 修改提示词或输入材料 | 任务对应的唯一正文文件、装入字段及来源、原生工具、允许写入的截止位置、确认条件 | 实际系统消息、原生 `tools`、动态资料和回包样例。修改活动提示词后按仓库规则执行 `npm run prompts:sync`。 |

例如调整 `search_prior_nodes` 的返回字段，先在本册的 P3 工具行写明新默认值和一个输出样例，标记为拟变更；再核对串联规则、公开参数及回包投影。验收应从串联任务调用一次，检查实际发给模型的字段，同时确认后台历史记录仍按已约定的方式读取。

### 两步事件复核
REQ-032。「取消 P3」按书结束主流程及独立复核的运行中或暂停进度，保留已写回的事件与历史。再次点击「重新开始事件复核」按现有事件生成新队列、新运行和新会话；「暂停」后点击继续则使用原进度。首页「事件复核」使用当前书数据原地写回，跳过节点串联和初始向量计算。旧任务详情可查，旧版复核确认不抵扣新任务。宏观 review_boundaries 的首包只含疑似组、组内成员并集时间表（ID、名称、概述、当前所属事件）。微观 review_sequence 的首包只含当前事件与其顺序成员，以及待核实或转回意见。按具体任务装入独立 Markdown 规则及原生工具。
两轮均可按需 get_nodes、get_event、search_nodes、search_events。两步复核的首条任务材料先列资料说明。组内事件卡七项字段和时间表中按 event_ids 汇出的完整成员已计为读取；get_event 用于组外卡或已变更的版本，节点事实不足用 get_nodes 查对应节点。宏观 edit_events 可新建、修改、撤销。合并时在同批更新保留卡的完整成员及受影响字段、删除重复卡；replacement_event_ids 仅记录去向。共享节点先核查每条归属，再判事件去留。宏观组内，含成功 get_nodes 或 get_event 的工具轮次保留原生调用及模型可见回包到本组结束，即使超出普通保留轮数；恢复时从同一任务的原始工具记录重建。其他轮次沿用原压缩策略；微观仅允许 update 当前事件。宏观 confirm(completed) 只完成组比较，微观 confirm(completed) 只完成当前事件版本。微观 confirm(return_to_macro) 提交 event_ids、evidence_node_ids 和 reason。依据不足可 confirm(pending_review) 并填写 pending_issues。不同阶段的任务状态、版本、转回证据保存在运行记录；恢复后复用同一任务回执。

事件已经归线时，撤销事件沿用现有大纲删除规则，移除故事线中的该编号。替代编号记录在复核回执。成员增减及删除涉及的故事线节点统计和节点反向关联在同一事务同步。

宏观规则沿用[复核 PRD](<../P3 事件复核 PRD.md>)对事件过大、核心偏移与事件过碎的判断，按本组各件的独有事实、共享节点的具体作用及各自结果划界。微观规则沿用其中的断点核查方法：从两端事实提出疑问，查明后区分漏挂、概述遗漏、跨事件、原文省略与证据不足。提示词分别说明对应的编辑或确认方式。

**组队与输入顺序**

1. 程序按节点在原文的位置给事件成员排序，建立“节点 → 所属事件”的倒排表。两个事件共享至少两个节点即可候选。较小事件只有一个成员时，共享它也可候选。多节点共享对优先，再依次比较双方都连续的最长共享段、共享总数、较小事件的覆盖比例、最早共享位置和事件 ID。
2. 以排名最前且当前版本尚未比较的事件对为起点。第三件须与起点共享至少两个相同节点才可加入，扩组沿用起点的节点集合，组大小使用 eventGroupSize。未进入上述成员重叠队列的两件，若有相同的具体核心线索且共享零个或一个节点，进入同一条线索重排队列，排除单独的人名、地点名及已知别名。共享成员队列用尽后，才以一件的进展和遗留问题对另一件的名称和概况做双向 Rerank，取较高分排序。模型不可用时沿用本地候选顺序，在运行中标注。
3. 一次宏观确认记录所比较事件对及其当时版本。下一任务按最新书库重新挑选。删除事件即退出，新建、变更的事件按其当前版本参加。疑似组用尽即进入逐件主审。主审发现因果断点时，可用 search_nodes 搜索包括未归属节点在内的历史经过，核实后由 edit_events 补入本件。微观发现跨事件问题可带着编号和证据优先返回宏观。
4. 微观按首个成员的原文位置、事件 ID 排序；同一存续版本只有一次有效主审确认。待核实可先审其他事件，最终有遗留则暂停；点击继续重试待核实项。每个任务单独保存系统规则、原生工具、动态资料、历轮请求和工具回执。
