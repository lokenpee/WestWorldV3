# 接入设计

锁定仓库级 OpenSpec，配置中型、完整两种工作流；小修改按仓库指令执行。现有条款映射至能力或技术契约，重复行为转引用，历史证据保留独立用途。

应用直接导入的提示词和结构文件登记实际消费者并核对内容哈希。现有要求进入主规格，待开发与待人工验收事项分别进入活动变更。治理正文由 AGENTS.md 维护，配置、模板及工具技能引用。

接入使用 OpenSpec 严格校验、工作流依赖检查、来源及链接检查，配合类型与构建检查。用户审阅交付后归档，真实业务试运行沿用下一项已确认需求。

## 字段变化

应用数据库、接口和工具字段无变化：本需求只整理治理材料。需求池新增的索引列如下，写入位置是需求池 Markdown 表格。

| 字段及含义 | 类型与约束 | 赋值和读取 | 兼容处理 |
|---|---|---|---|
| 编号 | 唯一的 REQ-数字，必填 | 讨论需求时分配，补充沿用；供提案、任务和其他 AI 定位 | 现有需求补上编号，保留原变更目录 |
| 需求、级别 | 中文名称；小修改、中型或大型，必填 | Agent 按实际影响填写；用户可纠正 | 已有功能保持原称呼 |
| 状态 | 仓库指令定义的状态，必填 | 随澄清、确认、实施、验收及归档更新；接手前读取 | 不从 OpenSpec 文件齐全状态推断已确认 |
| 资料入口 | 相对链接，必填 | 指向提案、细分需求章节或小修改记录 | 归档或拆分时更新链接，原编号保持 |
| 缺口或下一步 | 具体文字，必填 | 未明确的选择写成可回答的问题；可实施事项写下一任务 | 任务细节继续在任务文件维护 |

## 数据流转

用户描述 → Agent 读取现有规格和代码 → 在需求池登记编号 → 将已选规则、理由与缺口写入提案 → 编写规格、字段与流程说明、任务和验收 → 用户确认 → 更新需求池状态 → 接手 Agent 从编号读取材料并实施 → 保存检查与验收结果 → 同步规格、归档并更新链接。

具体示例：REQ-004 的资料入口指向单章试跑章节，状态为“待设计”；用户已确认保留目标，但关闭窗口时是否取消仍需设计和确认。因此接手 Agent 先补方案。只有具体选择、相关数据流、触发逻辑、任务及验收齐备并获确认，才将状态改为“可实施”。本次保留其待设计状态。

需求池负责总状态和入口，提案负责决定，设计负责数据与流程，任务负责执行，验收记录负责结果。链接更新后由治理检查验证；失败时修复资料并重跑检查，应用数据保持原值。

## 触发逻辑

| 触发 | 前置与处理 | 结果或失败处理 |
|---|---|---|
| 收到新需求或补充 | 查需求池；独立目标分配编号，补充沿用编号；记录结论和问题 | 未解决问题进入待澄清或待设计；不自动编写未确认业务规则 |
| 方案完成及用户确认 | 检查字段变化、数据流、触发分支、依赖、任务及验收；记录具体确认 | 满足接手条件转可实施，缺材料则保持待设计或待确认 |
| 开始实施或恢复工作 | 读取需求编号、授权和任务证据，核对仓库实际进度 | 转实施中；避免重复执行已完成任务；新增取舍回写方案 |
| 开发检查通过 | 提供入口、样本、步骤、预期结果 | 转待验收；失败回到相关任务，保留已记录证据 |
| 用户验收通过与归档 | 核对全部任务、规格和技术契约，执行既定归档流程 | 转已完成并更新归档链接；提交推送仍按原授权规则 |

讨论和文档检查不触发模型调用、业务工具或产品后台任务。小修改按仓库指令简化材料，仍保留编号或关联原需求。

## 验收与接手

从需求池随机选择已知需求，验证能定位具体已确认结论、缺口、实施入口和验收。将一个资料不全的需求误标为可实施，治理检查应指出缺少的结构；移除链接目标应报错。恢复原资料后检查通过。语义是否完整仍按仓库指令人工审阅。
