## 已定位的实现问题

1. **上下文沿用过重。** 新一轮检查仍把旧会话大量消息交给模型；普通请求从35.9万增长到43.9万token。归档完整历史不要求每次重送完整历史。
2. **第二步详情混入关系。** get_character_detail同时返回relations、relationEdges、unresolvedRelations和完整底稿等。完整读取校验又把整个序列化对象当作必须读完的单位，导致改身份字段也被大量关系和长文本拖累。
3. **自由调用与证明流程摩擦。** Agent只读取片段便尝试编辑/批量完成，被反复拒绝；工具错误没有及时切换为有明确剩余范围的经济恢复，继续在大上下文上消耗。
4. **分批规则矛盾。** runtime/提示词给新流程200次预算，gateway仍把cooperative Agent请求硬限制为20次，导致技术分批继续发生。system prompt包含变化的taskId；两个技术批次首请求分别有351,698和394,410个未缓存输入token，其余普通请求多数命中缓存。
5. **压缩失败额外消耗且证据不足。** 只有全部压缩成功才保存compaction条目；本次摘要校验失败后，没有保留压缩逐次原始请求/返回，不能准确解释每一次压缩修正。
6. **用量汇总不能作为逐次账单。** 普通消息中的原始usage包含input/output/cacheRead，报告仅展示累计总量和估算费用；历史汇总与原始消息累计存在差异，且当前summarizeUsage未把cacheRead费用合入cost。供应商账单需单独核对。

## “修改前后”是什么格式

模型调用edit_character，提交id、expectedRevision、patch（只含要改的字段）、reason和basis。修改前的值由代码从数据库取得；修改后来自实际生效的patch，界面按fieldChanges展示对比。它不是要求模型先输出一整份“修改前”，再输出一整份“修改后”。

- 修改后：贾府文字辈，荣国府二老爷（政老爷），工部官员；贾母之子、贾赦之弟、宝玉与元春之父；曾于朝堂举荐贾珩为贾族族长，率阖族迎贾珩归族

## 合理的调整方向（尚未实施）

- 第二步只提供当前人物的非关系字段、必要事实及来源定位；可确定的重复直接提交字段patch，矛盾或缺漏再按需查原文/其他资产。
- 当前工作上下文与历史存档分开：同一逻辑Agent会话保留，但不要每次带几十万token旧历史；摘要按经济工作窗口触发，不等到模型容量接近上限。
- 读取证明与当前实际字段/读取范围对应，不强制为改一个字段读完无关的整个关系对象；错误恢复直接返回未读范围，不反复自由猜测。
- 对齐运行器与网关预算，保留实际请求及压缩失败用量记录；增加整轮费用/总token停止条件。
- 用真实小说单人物和小批样本实测请求数、有效修改和消耗后再扩到整书；固定响应测试只能验证机制，不能验证真实模型经济性。
