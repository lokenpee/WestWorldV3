# P2三个步骤启动后卡顿：排查与可选方案

## 用户反馈及授权

2026-11-12，用户反馈点击第一步识别重复人物、第二步优化人物资料、第三步整理人物关系后整个网页非常卡，不调用API时正常。关联REQ-019、REQ-020，登记BUG-39。用户随后以“开始吧”确认实施A+B：优化后台读取/计算和详情加载渲染。按中型缺陷实施，保留现有Agent与提交语义。

## 已检查的执行路径

以下为优化前当前工作区实现的排查记录，不与某个提交比较；未对正式书库运行模型或采样。这些开销在用户实际卡顿中的占比仍需实际书库验收。

1. 三个步骤均经world/service.ts的startOrganizationStep进入。第二、三步调用buildProfileReview/buildRelationReview；organizationReview.ts的reviewContext读取全体人物、原始关系、生命周期和关系编辑记录并重建有效关系。资料步骤也构建了关系上下文；关系步骤逐人物过滤全体关系，缓存仅在单次上下文内复用。
2. agents/repository.ts中rows先读取整表并structuredClone，返回时再次复制；只读快照随后再次读取整表并canonical比较，写快照也比较实际读取集合。已有按ID读取路径，不是所有事务都会读全库；全表调用路径仍承担随数据量增长的扫描、复制和序列化成本。并发一致性校验必须保留，不能简单删除。
3. runtime.ts恢复会话先store.rows('storySessionEntries')再按sessionId过滤；底层先读取/复制整表再排除观测日志。历史日志会增加非当前工作项的读取成本。
4. P2OrganizationPanel订阅traceHub，更新后分别读取三个步骤索引；trace.ts的readOrganizationStepIndex每次读取整表storySessionEntries再过滤。选中对象的readExecutionChain也读取整表。80ms通知有合并机制、索引/详情有350/300ms延迟，因此并非每个token都查库；有间隔的连续更新仍会反复扫描历史表。关闭详情可避开这部分展示读取，不能消除后台开销。
5. AgentRunPanel的details内直接调用displayContent/full并构建pre，折叠不阻止React执行这些计算和创建子节点。长Prompt、工具Schema和结果仍在每次渲染时处理。上轮视觉简化并不等于按需渲染。

## 可选实施范围

| 方案 | 内容 | 预期适用场景 | 规模与注意点 |
|---|---|---|---|
| A 展示优化 | 展开后才生成长内容；索引一次查询供三个步骤复用；按当前人物/请求读取日志；只刷新变化请求 | 打开详情后明显加重 | 中型；保留完整日志与现有界面内容 |
| B 数据读写优化 | 资料步骤仅构建资料依赖；按session/unit查询历史；复用本批计算和关系索引；减少重复复制/序列化，保留事务冲突检查 | 不开详情也卡，开始/保存/切人物卡 | 中型起，若涉及共享存储接口或迁移需完整设计 |
| C 后台线程 | 将已定位的重计算移入Web Worker，页面线程处理交互 | A/B后仍有明显主线程长任务 | 大型；须设计取消、恢复、消息传递与数据一致性 |

建议先用固定响应与隔离的大样本录制启动、等待回复、工具保存、详情打开四个阶段的长任务、帧响应、内存和读表次数，再实施A+B中实际热点。C按测量结果决定，不先搬整套Agent。

## 验收与下一步

使用隔离样本，分别覆盖不开详情/打开详情、三个步骤、长历史日志；比较同一数据规模与操作下的主线程长任务、交互延迟、读表量和内存。验证暂停、取消、恢复、冲突检测和提交结果保持原语义。没有测量前不承诺提速比例。

已完成A+B实施与隔离样本检查，用户实际书库观感待验收。没有调用真实模型、修改正式书库或提交Git。

## 实施内容

- repository/runtime：恢复会话沿既有sessionId索引读取；业务整表快照先按type索引排除观测正文，减少重复复制；修复只读复核时拿过滤后的业务快照与未过滤日志比较而额外重读的问题。会话范围写快照提交前重新比较，仍检测并发插入、修改和删除。
- organizationReview：资料准备仅读人物；关系计算建立人物/人物对映射，保持原指纹内容和顺序，减少逐人物扫描整组关系。
- trace：三个并发步骤索引请求共享一次正在进行的查询，完成后释放；详情按会话读取。缺少sessionId的旧运行仍通过请求类型索引回退。
- LazyDetails、AgentRunPanel、ExecutionChainView：折叠内容不创建和格式化，展开后生成，关闭后卸载。保留当前会话时间线和API分隔行的展示设计。

## 固定样本与实测

入口：`node node_modules/@playwright/test/cli.js test --config playwright.workspace.config.ts tests/browser/world.spec.ts --grep "P2性能隔离" --project=production --workers=1`。

生产构建、Edge无头浏览器、1440×1000；Playwright独立上下文导入7个人物的小样本，第一步合并后剩5人。额外写入400条无关会话历史请求，每条正文3万个字符（总正文约24MB UTF-16）。所有模型API由本地固定响应拦截。三个步骤依次点击，轮询持久化运行状态确认为completed后记时；最后打开沈青详情和首个API分隔行。相同数据与操作分别测量优化前后一次。

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 第一步点击至完成 | 2565 ms | 2004 ms |
| 第二步点击至完成 | 4533 ms | 1987 ms |
| 第三步点击至完成 | 4453 ms | 1946 ms |
| storySessionEntries整表getAll调用 | 32 | 0 |
| 主线程长任务次数 | 23 | 1 |
| 最长长任务 | 128 ms | 59 ms |
| 长任务累计 | 1997 ms | 59 ms |

整表指标仅计IDBObjectStore.getAll，不等于总查询次数或总读取字节；索引读取仍存在。长任务由PerformanceObserver测量。耗时包含状态轮询间隔，不代表真实模型延迟改善比例。当前会话内和历史P2运行内的数据仍需按范围读取；本样本没有覆盖数百人物的大关系图、长时间流式输出或真实书库内存峰值，不能把一次样本当作所有规模的性能保证。
