# 后台人物整理流程

> 2026-11-08 后续变更：P2 提示词与默认工具按工作项拆分见 [BUG-34](../step-specific-organization-prompts/proposal.md)。本文件中“提示词/工具集不随步骤变化”的旧条款由该变更替代；跨步骤查询、候选、合并、资料/关系纠错仍保留。


## Why

REQ-019，大型需求，project-full。2026-11-05业务取舍已确认，规划材料供其他Agent实施。目标是一个后台整理入口连续完成人物识别合并、人物资料优化、人物关系整理。按2026-11-06 BUG-32方案v3确认，三个步骤使用独立工作上下文，第二步按人物、第三步也按人物切换；历史统一保存，不整包重送。

初版三步流程及BUG-30/31已实施，真实运行暴露整轮历史反复发送、非关系资料读取混入关系、无效登记和摘要失败导致高用量。当前修复保留全工具能力与原始成果，调整工作上下文、默认资料、提交方式、错误恢复和日志，取消任意固定额度；复现与修复入口见BUG-32节。

## What Changes

1. **识别人并合并。** 先按每页约100人通读全量人物简略目录，业务字段只有姓名、别名、身份，附稳定编号定位。用工具保存疑似同人组，允许跨批发现、补充和查回；目录读完后逐组读取完整人物资料，充分时直接据此合并，不确定时查原文。仍不能判断的暂不合并，报告保存编号和原因。全部组处理后调用工具清空本轮疑似工作集，保留报告。
2. **优化人物资料。** 按合并后有效人物逐个整理非关系字段，压缩重复表述、修正矛盾、保留独有事实；可修改姓名、别名、身份、外貌、性格、背景、说话样本、层级等业务内容，不再强制另起一次模型复核才写入。
3. **整理人物关系。** 逐个人物整体整理当前关系，已处理关系显示标记避免无意义重复，有新依据仍可重查；整理重复杂乱内容，查资料纠正矛盾、补缺。可新增、修改、删除关系；未知反向保持空，不猜测同名对象。
4. **一套工具贯穿全程。** 本书四类资产均可查询和编辑，合并能力和关系增删全程可用；读取原文、完整事实、历史关系依据不按三步禁用。三步是工作顺序，工具不是每步换一套。不给Agent删除资产的能力；合并沿用保留编号和来源映射，不等同直接删除资产；人物可降级为NPC。具体合并与字段语义见设计。
5. **依据允许概述。** 三步均可使用实际读取的资产资料或原文作依据，文字不要求逐字一致。保存来源引用、读版本和AI概述/理由，不以字符串包含或相似度阈值判断概述是否合格。
6. **后台持续任务。** 同一轮统一保存历史、候选、进度和确认；三步独立上下文，第二和第三步按当前人物切换并由代码装入必要资料。只显示进度、运行控制、报告和可核对的请求用量，不增加聊天输入。正常人物完成后自动接下一人；不设置固定token、每人请求次数或整轮额度门槛；记录实际用量并正确恢复错误，见BUG-32设计。
7. **入口与继续。** P1全书提取完成才能启动。移除“整理范围/仅人物关系/先10项/继续全书核对”专用入口，AI整理默认完整三步，中间自动衔接。暂停、取消或失败后继续原轮余项；一整轮结束后再次启动，新一轮重新检查全量当前人物，无变化不写回。代码整理和机械队列入口保留。
8. **同书单任务与断点恢复。** 2026-11-10补充：同一本书同一时间只允许一个P1/P2/P3后台任务，P1内部两类lane仍并行，不同书籍独立。P2每次运行只保留一套周期心跳；续租只更新时间，业务提交仍核执行者身份和有效期。快照冲突等内部可恢复错误保留当前人物和已提交确认，转为可继续的暂停；owner/runId或会话租约真实变化时旧执行者停止写入。用户主动取消与异常暂停分别记录。

术语：“疑似组”是本轮工作存储中的可能同人集合，不是已确认合并；“本轮”是一次完整三步执行及其中断续做；“概述性依据”是带可追溯来源的AI解释，不冒充逐字引文。

## Capabilities

### New Capabilities

无独立产品能力目录；疑似组、持续会话和进度作为世界整理能力的一部分。

### Modified Capabilities

- world-organization：三步工作流、候选组、全量扫描、自动衔接、完成与继续。
- agent-session：P2持久会话、工具全程可用、压缩、概述性依据、命令确认。
- asset-management：本书全资产编辑/合并、禁止直接删除资产、层级调整。
- character-relations：统一流程内的关系核对与新依据格式，替换专项限制。
- book-backup：新会话、候选、进度、来源引用和旧运行兼容。

## BUG-32 高用量与摘要校验失败修复

**当前方案v3，确认日期2026-11-06。** 用户指出第二步应由代码预装当前人物资料、第三步应逐个人物整体整理关系、不应强制阅读证明和固定请求/token额度，并明确要求“改正过来，先改文档，把改的点说明白给干活的Agent”。本次授权文档修订，代码由接手Agent实现；不运行用户模型、不直接修改书库。

BUG-32沿用原编号，大型 / P1。原备份中40条成功普通回复合计16,050,662 token，输出11,806，8人实际完成，第三步未开始；其他压缩/修正日志不全，不能与用户约1780万token、1.9元账单精确对齐。原始证据保持：[诊断](evidence/bug-32-cost-analysis.md)、[请求清单](evidence/bug-32-request-trace.csv)。

### 交给开发Agent的明确要求

1. **第二步首次资料由代码提供。** 程序读当前人物非关系字段、相应事实与来源，直接加入第一次模型请求。不要先让模型调用get_character_detail才拿到当前人物，也不要混入无关的大关系对象。遇到矛盾或需要其他人物/原文时，Agent再自主查工具。
2. **第三步也按人物处理。** 默认提供当前人物必要介绍、完整当前关系和必要对象介绍/编号/依据，让Agent整体归纳和纠错。只有有疑问的对象才补查详情或原文。人物对只是关系数据的编号定位方式，不是独立任务，不强制为每两个角色开新上下文。
3. **保存可以同时声明完成。** 当前人物提交工具带done；done=true将修改和此人物完成同事务保存，代码直接进入下一人。done=false保存部分修改但不结束。不要强制edit_character之后再调record_organization_progress。允许已有编辑工具继续用，但不能重复写同一修改。
4. **不额外调用模型做结束总结。** 修改前后、计数和用户报告由代码读取真实保存记录生成。普通人物可能一次模型响应就完成阅读、判断及工具提交；有查证需求就允许多轮，不能为了达到“一次”省略必要调查。
5. **第二、三步去掉读取证明通关。** 程序负责把该给的资料提供好，模型不必提交完整详情阅读、字段/事实覆盖或逐段证明。保留必要格式、编号、版本、执行权、引用与防重复写入校验；概述依据不要求逐字一致。第一步合并依据的既有要求保持。
6. **出错马上给具体恢复办法。** 参数错交回Agent修正，版本变提供新版本/资料；原样重复同一失败且无新进展时，拦截空转，当前人物留待处理，继续其他人物。密钥、存储、执行权或持续网络故障暂停整轮。失败不能卡死界面，也不能伪报已完成。
7. **取消固定额度，保留用量记录。** 不设置32K输入、每人8次、整轮200万token的默认停止门槛，不开发扩额操作。移除新P2互相矛盾的20/200次限制；模型真实容量、网络超时和取消机制仍保留。每次普通/失败/重试/摘要请求的token、缓存、费用和错误全部可查。

### summary故障

原错误“压缩摘要须包含非空summary，长度至多8192字符”同时涵盖缺字段、类型、超长等问题；不能据此断定一定是空值。固定提示64000字与动态Schema上限冲突，失败原始返回不完整，均需修复。

正常换人物、正常保存完成不调用摘要模型，不要求summary字段。当前人物多轮工作确实需要压缩时，提示与校验共用同一约束，具体区分错误，先保存原响应和费用，再修正或从持久状态重建。不能将结束总结和上下文压缩混为一个必须步骤。

### BUG-31 资料与关系整理未落实及进度误报

字段变化：organization新增可选reviewVersion（检查规则版本，整数2）、reviewStartedAt（第二步开始时间，ISO字符串）和repairNotice（旧进度重查说明）；旧数据缺省表示旧规则。人物工作项新增可选name及uncertainFields；readRefs继续为字符串数组，由代码记录完整读取或分段覆盖的指纹证明。pairChecks允许outcome=null表示待核，新增可选readFingerprint记录实际查询。存储仍在pipelineRuns，格式9和既有表不变；恢复时保留不含bookId的业务指纹，校验人物对端点。详情工具新增可选char_offset/maxChars以续读长人物资料。其他资产写权限和字段含义无变化。

数据流转：完整人物详情/续读 → 代码核对返回的完整字段、底稿和当前业务指纹 → 保存工作项readRefs → Agent归纳可确定内容、查证疑点、通过原编辑工具写入 → 真实assetEdits确认与工作项关联 → 核对结论后推进。关系详情 → 当前人物对及实际查询指纹 → 保存共享核对结果 → 人物两端复用。业务资料变化只重查受影响项，频次、更新时间及单纯revision不使有效结果失效。例：崇平帝身份重复“皇帝/当朝皇帝”可归纳，五子三女、登位经历等独有事实保留；“大明/陈汉/大汉”未证实时保留分歧并列疑点，不能因此整段不整理。

触发逻辑：点击AI整理或继续 → 识别旧检查版本，已过第一步的旧轮保留组结论/合并确认/会话并重建资料余项；新版轮沿有效进度继续。目录全部处理、疑似组清空后自动进入第二步，资料实际核对完进入第三步，人物及人物对核对完才统计完成。取消/刷新保留已提交结果及有效读取证明，恢复不自动调用模型，不重放合并；无变化不制造业务修改。提示词要求逐字段处理可确定整理和待查证内容，不能将未查证作为跳过其他字段的理由。

- 一套后台持续Agent工作流，阶段只决定工作重点；阶段/工作项不能成为读取其他资料或使用已开放工具的权限门槛。
- 不新增资产删除工具；共享入口若能间接删除资产也必须拒绝。关系删除仍允许。降低层级写agent来源，频次统计不自动改回。
- 资料充分时直接使用现有资料，程序记录读过的来源、校验引用和版本，不用逐字匹配代替语义判断。
- 疑似组清空只清本轮活动工作集，合并结果和不确定结论进报告；后续发现新疑似可用同一工具再核对，不强制新开Agent。
