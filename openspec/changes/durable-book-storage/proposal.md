# 书库持久保存与浏览器数据丢失恢复（讨论稿）

## 原意与状态

REQ-023，2026-11-12用户询问：目前数据均在浏览器IndexedDB，清理缓存/网站数据或其他情况下可能消失，有什么应对方法。目标是长期保留小说原文、整理结果和会话，降低已付出模型费用的成果丢失风险。当前只讨论选项，尚未选择实施路线，不授权迁移或改写正式书库。

整体暂按大型需求登记；若最终只选择已有备份能力的局部增强，再按最终数据和接口影响分级。关联REQ-010的备份兼容、REQ-019/020的整理结果和会话保存。

## 现状

- 单书IndexedDB保存原文、资产、运行记录和会话；全局库另存书架、模型配置和凭据。
- 已有`.wwv2`整书快照导出、校验、导入为独立副本，支持下载和授权磁盘目录写入。
- 目录句柄保存在浏览器设置库，清除站点数据后需要重新选择目录；已写出的普通磁盘备份文件仍可手工导入。
- 目前没有自动磁盘备份，也未发现navigator.storage.persist接入。现有单书备份不包含模型密钥/全局设置。

## 待选方向

1. 浏览器持久存储申请：减少存储压力下的自动驱逐，不能防用户清除站点数据，只作为补充。
2. 保留IndexedDB，增加授权目录自动备份：有修改时合并调度，关键任务完成后保存，保留多个版本，显示最近成功时间；失败/权限失效可见。页面关闭时不依赖卸载事件完成保存，恢复最多到最近成功备份。复用现有格式，另评估全局非敏感设置备份。
3. 本地服务或桌面应用，以用户数据目录中的SQLite等本地数据库为主存储：界面继续复用，业务提交通过本地服务事务保存，浏览器清理不删除主库。此路线需要数据库适配、全量迁移校验、任务并发与恢复改造及独立备份；不是把SQLite放进浏览器OPFS。

初步建议：近期优先补外部自动备份及恢复，长期若要求保存不依赖浏览器，选择第三种。云端备份/多设备同步属于可选后续选择，用户尚未要求上传数据。

## 待确定及接手

先由用户选择保留纯网页还是接受本地服务/桌面应用，再确定频率、保留版本、保存成功含义、恢复方式和允许丢失的最近工作量。字段、数据流、触发和迁移验收将在路线确认后具体设计。当前没有实施任务或产品代码变更。
