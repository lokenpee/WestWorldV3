## 界面与实施方法

每个API请求只保留一张卡片：编号、时间和状态 → 发送内容（按SYSTEM、USER、ASSISTANT、TOOL区分）→ 模型回复（正文、可展开推理、工具调用参数）→ 对应工具执行结果。工具结果明确是本地执行结果，不混为API回复正文。工具定义只显示一份，默认折叠；长消息可展开全文。删除第二套对话事件、拼接原始JSON、重复请求标题、执行/会话UUID及空的解释块。全部请求和嵌套折叠内容默认收起，可逐次展开；用户展开状态不随流式更新重置。

人物索引首次读取立即执行；后续日志更新仍合并刷新，避免刚打开时连续日志将首次读取反复推迟。顶部统计及底部assetEdits保持。P2人物/步骤选择、P3持续会话入口保持。无API记录的旧运行显示简短缺失提示，不根据事件伪造实际请求。

## 字段变化

- 在模型网关的实际fetch发送位置增加只读观测回调，获取即将发送的JSON消息和工具定义，不采集HTTP鉴权头，不改变请求。
- trace的input.messages保存发送体里的消息投影；messageFormat标识provider-request/v1。系统提示在不同协议的system/instructions/messages中统一映射为SYSTEM展示。工具声明保存在既有tool_snapshot，由input.toolSchemaSnapshotId引用，消息不再另存SDK toolsAdded工具定义。旧pi-agent-message/v1记录继续可读，界面标为历史上下文记录。
- 可选input.requestParameters保留请求中模型/采样等非消息字段，input.transportAttemptIds记录此次逻辑请求对应的HTTP尝试；失败/缺失仍明确显示。沿用现有开放input结构，无数据库升级及备份格式变化。
- 模型可见的submit_profile_review与submit_relation_review参数隐藏自动生成的operationKey；关系提交隐藏顶层默认basis，只保留changes[].basis。内部契约和执行兼容已有operationKey及顶层basis，不削弱证据或提交校验。

## 数据流转

SDK生成请求 → 网关读取即将发送的body → trace提取messages/input、system/instructions及tools → 保存同一requestId下的输入和单份工具快照 → ApiRequest按消息角色展示；模型流式返回继续写text/thinking/toolCalls；工具执行结果按toolCallId对应到调用下方。

例如API #1返回query_relation_work参数，程序执行得到结果R；API #2输入含R。页面把#1下的R标为工具执行结果，把#2输入中的R标为TOOL消息；这表示实际反馈链路，不另生成一套对话事件重复回放。输入历史原样保留，折叠只影响阅读。

## 触发、恢复与检查

打开整理详情按requestId渲染；实时更新只更新同一请求，手动折叠保持。重试属于原逻辑请求，记录实际尝试次数；观测失败不阻断调用。存储不足沿用摘要降级，不能把缺失内容显示成完整。

固定测试核对真实fetch请求与trace发送消息/工具一致、工具定义无outputSchema/重复toolsAdded、两种提交模型Schema精简且空提交/证据删除/旧调用兼容。组件检查只有一条API流、无重复原始JSON、正文与工具结果无重复包装；开发和生产浏览器检查人物切换、长内容、折叠稳定及窄屏，保存截图检查观感。

## 单行执行状态
字段：新增展示用瞬时状态（文案、是否运行、错误、起始时间），不新增数据库字段；读取现有request_trace的请求、返回和工具状态，以及任务stepsUsed/lastError。P3服务投影必要任务摘要，旧任务缺省为空；备份结构不变。
数据流：现有Trace事件→按bookId/runId/taskId及当前人物筛选→共用单行组件→原位更新。刷新后任务错误恢复停止原因；最新运行事件覆盖旧错误。P2资料/关系计数仍为当前人物，查重和P3为当前阶段累计。例：第3次API等待18秒→第3次API已返回、查询人物资料→已暂停、进度已保存。
触发：启动时准备，实际请求时等待并每秒计时，流式返回时接收，工具事件时执行/保存，终态停止动画。主动暂停优先显示已保存；异常停止显示真实原因（402余额不足），不再显示scan:0。新运行可清除旧异常，切书或人物不接收其他对象的晚到状态。流式刷新合并至约250ms，计时仅更新状态组件，减少动画偏好关闭光晕动画。
范围：保留页码、人物进度及Token，状态文案合并为同一行；全链路仍在详情。复用已有错误和恢复逻辑，不新增输出校验。
检查：固定响应与组件验证等待计时、工具执行、主动暂停、402错误、恢复、完成、作用域隔离；P2三步/P3浏览器回归、类型、治理及本变更严格校验。

恢复修复：独立continueOrganization需在取得执行权事务内清除未完成项lastError，防止nextUnit将其再次跳过；历史任务错误不删除。finalizeStepRun记录已有pauseRequested区分人工暂停。生产浏览器固定402→刷新→继续→成功用于复现与验收。

## 普通回复与任务结束（BUG-42再次反馈）

运行层在每轮返回后先处理用户暂停/取消、真实工具完成、已记录的工具失败及现有预算退出；其他正常纯文字回复保存在会话，并提示继续当前任务，再请求模型。带工具的正常回复沿用Pi工具循环。API异常直接退出，不能通过继续分支重试；不新增请求次数或文本格式校验。未完成任务的异常退出使用“尚未收到任务完成确认”，不要求未开放的总结工具。

字段无变化：完成由tools.completed/summary判定，退出原因复用itemFailure和调用方暂停标记，提示是已有message记录，非新业务字段。数据流例：助手“我先核对别名”→保存原回复→同会话继续→查详情/保存候选→最后一页翻页回执complete=true→完成；回复文字不会把当前页标成已检查。真实错误与已提交成果分别保留。

检查所有runtime.run调用入口及其错误消费；P1直接提取、压缩和连接探测按各自工具结果协议核对，不强套分页完成。固定响应测试覆盖P2三步、P3两个阶段的文字后继续和完成，零候选末页完成，暂停、取消、API失败及重复工具失败；不运行真实模型或修改用户书库。用户副本验收后再同步规格。

重复失败处理移至每轮完整toolResults，覆盖Pi未经过afterToolCall的工具名/参数错误，复用原有重复失败和连续冲突规则。当前P3主动阅读显式消费itemFailure。旧窗口流程按既有批次契约保存成功覆盖、记录失败项并继续其他批次，此调用方保持不变；共用层的普通文字继续同样适用。
