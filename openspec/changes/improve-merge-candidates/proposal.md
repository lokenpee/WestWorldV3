# 机械合并候选识别增强

## 结论

代码可以直接识别“北静王 / 水溶”和“甄妃 / 甄雪”这两类记录，不需要上 AI。当前漏组不是语义问题，而是别名相似度被一方的独有别名稀释：实测得分分别为 `0.7` 和 `0.5714`，低于现有 `0.9` 阈值。

本变更只扩大“疑似候选”的识别范围，不改变自动合并边界：仍然只有完整主名相同才自动合并，新增识别结果全部进入人工候选。

关联需求：REQ-016。级别：中型，采用 project-local。当前状态：待确认。

## Why

人物和地点的现有关键词已能识别大量同人记录，但以下两类精确证据没有被单独使用：

| 记录 | 主名 | 别名 |
|---|---|---|
| A | 北静王 | 北静王爷、北静郡王 |
| B | 水溶 | 北静王、北静郡王 |
| C | 甄妃 | 北静王妃 |
| D | 甄雪 | 北静王妃、甄家二小姐、甄妃、甄氏 |

A 的主名等于 B 的别名；C 的主名等于 D 的别名。C/D 的有效称呼还构成包含关系。当前算法只比较“主名与主名”和“整组别名相似度”，因此漏掉这两组。

## What Changes

1. 新增“主名与别名精确相同”规则。任意一方的主名等于另一方主名或别名时，两条记录进入同一候选组。
2. 新增“别名重叠系数”规则。用交集除以较小一方的称呼数，避免额外别名稀释；阈值为 `0.8`，并要求至少共享两个称呼，或共享一个长度不少于 3 的称呼。
3. 新增“稀有共享别名”规则。共享称呼长度不少于 3，且该称呼在本书人物/地点中最多出现在两条记录时，进入候选。
4. 保留现有完整主名自动合并、人物主名包含、别名相似度 `>0.9` 规则。新规则只增加候选，不增加自动合并。
5. 候选分组继续使用并查集，A–B、B–C 相连时进入同一组，最终由用户核对成员和主名。
6. 候选原因改为写明命中的证据，例如“主名与别名相同”“称呼重叠 2/2”“共享稀有称呼：北静郡王”。

## 实施方法

### 候选计算顺序

1. 读取当前人物或地点，按编号稳定排序。
2. 人物排除上下文称谓（父亲、老爷、老太太等）；地点不排除。
3. 规范化主名和别名，沿用现有去空白、去章节/版本后缀、去标点规则。
4. 先执行原有规则，不经过任何共享称呼索引过滤：
   - O1 主名相同或人物主名包含：仍按当前两两比较执行；
   - O2 首轮分组后的整组别名相似度 `>0.9`：仍对全部首轮分组两两执行。
5. 再建立“规范称呼 → 记录编号”索引，只为新增规则生成记录对，不改变 O1/O2 的输入范围：
   - R1 主名交叉：A 主名等于 B 主名或别名，或 B 主名等于 A 的称呼；
   - R2 重叠系数：按全部非上下文共享称呼计算 `交集数 / min(A称呼数, B称呼数)`，严格 `> 0.8`；同时要求至少共享 `candidateMinimumSharedNames` 个称呼，且其中至少一个长度 ≥ `candidateDistinctiveNameMinLength`；
   - R3 稀有共享称呼：至少共享一个长度 ≥ `candidateDistinctiveNameMinLength`、全书同类资产出现次数 ≤ `candidateRareNameMaxRecords` 的称呼。
6. R2 的“有区分度称呼”只要求规范化后长度 ≥3；R3 的“稀有称呼”还要求出现次数 ≤2。上下文称谓和短泛称不计入 R2/R3。O2 整组相似度也要求至少一组含长度 ≥3 的称呼或主名，避免只有短泛称的整组相似。
7. 用并查集合并 O1、O2、R1、R2、R3 命中的记录，输出成员数大于 1 的候选组。
8. 每个候选组记录命中原因；同一组命中多条原因时合并去重。

为什么不能只用共享称呼索引：旧候选“贾宝玉/宝玉”只有主名包含关系，没有任何相同称呼，提前按索引过滤会丢失原候选。新索引只服务 R1–R3，O1 包含和 O2 整组相似度仍按原范围执行。

### 误报边界

R2 要求至少一个长度 ≥3 的共享称呼；O2 还要求整组至少一个长度 ≥3 的称呼或主名。例如三个人都带“贾家、宁府、东府、西府”四个两字别名，各自再加一个不同主名：

- 四个共享称呼长度都小于 3，不计入“有区分度稀有称呼”；
- R2 没有长度 ≥3 的共享称呼，不连接；
- R3 没有长度 ≥3 的共享称呼，不连接；
- O2 因整组只有短泛称，不连接；
- R1 没有主名与别名交叉，不连接。

因此不会因为 `4/5=0.8` 把三人连成一组。传递连接也遵循同一规则：只有命中规则的边才进入并查集。

### 参数

在 [算法参数](../../../docs/v2/resources/algorithm-parameters.json) 增加：

| 参数 | 含义 | 建议值 |
|---|---|---|
| `candidateOverlapThreshold` | 别名重叠系数阈值，严格大于该值才命中 | `0.8` |
| `candidateMinimumSharedNames` | R2 要求的最少共享称呼数 | `2` |
| `candidateDistinctiveNameMinLength` | 有区分度称呼最小长度 | `3` |
| `candidateRareNameMaxRecords` | 稀有称呼最多出现的记录数 | `2` |

这些参数只影响 R2/R3，不影响 O1/O2 和自动合并。

### 性能

O1 和 O2 保持当前实现与比较范围。R1–R3 使用称呼索引，只检查共享称呼的记录对；R2 的重叠计算也只在这些记录对上进行。对 2000 人物规模的验收样本，候选生成不得比当前版本明显变慢。具体上限在任务检查中记录实测值。

## 字段变化

无存储字段变化。`Candidate.reason` 的文案增加命中证据；`Candidate` 结构不变。算法参数文件新增四个数值字段，均必填、从文件读取，无默认值。旧数据无需迁移。

## 数据流转

读取当前人物/地点 → 规范化称呼 → O1 主名/包含与 O2 整组相似度 → 称呼索引生成 R1–R3 记录对 → 并查集分组 → 候选列表 → 界面展示 → 用户选择成员、主名、保留编号 → 现有预览/入队/合并流程。

示例：

| 输入 | 命中规则 | 目标结果 |
|---|---|---|
| 北静王（别名：北静王爷、北静郡王）与水溶（别名：北静王、北静郡王） | R1 主名交叉；R2/R3 共享“北静王、北静郡王” | 候选一组，原因“主名与别名相同；共享稀有称呼：北静王、北静郡王” |
| 甄妃（别名：北静王妃）与甄雪（别名：北静王妃、甄家二小姐、甄妃、甄氏） | R1 主名交叉；R2 共享“北静王妃”和“甄妃”，重叠 2/2 | 候选一组，原因“主名与别名相同；称呼重叠 2/2” |
| 贾宝玉（别名：宝二爷）与宝玉（无别名） | O1 主名包含“贾宝玉”包含“宝玉” | 候选一组，原因“主名包含”；不依赖共享称呼索引 |
| 三个人物都带“贾家、宁府、东府、西府”四个两字别名 | 没有长度 ≥3 的共享称呼 | 不显示；R1/R2/R3 和 O2 均不命中 |
| A 有 5 个有区分度称呼，B 共享 4 个且另有 1 个不同称呼 | R2 重叠 `4/5=0.8`，不严格大于阈值 | 不连接 |
| A 有 6 个有区分度称呼，B 共享 5 个且另有 1 个不同称呼 | R2 重叠 `5/6≈0.833` | 连接候选 |
| 两条记录共享“长安侯”，全书只出现在这两条记录 | R3 稀有共享称呼 | 连接候选 |
| 三条记录共享“宁国府”，全书出现三次 | 高频称呼不计入 R2/R3 | 不因该称呼连接 |

## 触发逻辑

用户点击“代码整理”触发候选扫描。扫描前仍要求全书 P1 完成、无世界整理或提取任务。扫描只读当前资产，不调用模型、不修改资产。用户确认候选后仍走现有预览、加入待合并、机械合并流程。自动合并仍只由“完整主名相同”触发。

## 确认依据

2026-11-04，用户给出北静王/水溶、甄妃/甄雪两组实际资产，询问能否通过代码识别，并要求按 AGENTS.md 登记需求、编写文档后审核。用户未要求修改自动合并规则，也未要求立即实施。

2026-11-04 审核意见：共享称呼索引会过滤原有包含候选；多泛称仍可能通过重叠规则误连；C04 与阈值边界冲突。本稿已改为 O1/O2 保留原范围执行、R2/R3 只计有区分度稀有称呼，并补充 0.8、0.833、出现两次/三次及多泛称反例。

## 不做什么

- 不把新识别的候选自动合并。
- 不按标题、亲属称谓或章节上下文推断身份。
- 不处理完全没有字符串重叠的别称。
- 不改变人物关系、备份或 P2 AI 整理流程。
