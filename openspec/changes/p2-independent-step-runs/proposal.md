# P2 三步独立运行、暂停继续与彻底取消

关联 [REQ-022](../../需求池.md)、[设计](design.md)、[任务](tasks.md)、[验收](acceptance.md)。本变更只改 P2 整本书整理的启动和调度方式，保留现有提示词、工具、业务提交、P2 整理详情和单人物整理。

## 结论

1. “AI整理”拆成三步独立入口：第一步只做目录扫描和疑似组合并，第二步只检查全部人物资料，第三步只检查全部人物关系；任一步完成后不自动进入下一步。
2. 开始、暂停、继续、取消是四种不同行为：开始新建 runId 并重建完整队列；暂停保留同一运行和上下文；继续恢复同一运行；取消废弃未执行队列，下一次开始必须新建运行。
3. 暂停不必等整人物完成。当前 API/工具安全结束后，停止发起下一次模型请求或新工具操作；当前人物未完成的进度、上下文和剩余队列保留。
4. 取消先落库标记 `cancelled`，再终止执行器；旧请求返回后不得再执行新工具或写库。已提交修改保留，未提交事务回滚，旧队列永久失效。
5. 第三步不再自动出场统计；原 `finalizeStatistics` 保留为独立统计能力，避免影响其他依赖。
6. 任一步骤正常完成或取消后，三个步骤按钮都恢复为“开始整理”。只有运行中或暂停中占用整本书 P2 时才禁用其他步骤。

## 现状

### 启动与自动串行

当前 [WorldPanel.tsx](../../../src/features/world/WorldPanel.tsx) 只有一个“AI整理 / 继续AI整理”按钮，调用 [service.ts](../../../src/features/world/service.ts) 的 `startOrganization`。

`startOrganization` 读取 `compileProgress` 的 P2 运行：

- 上一次未完成或需要重查时，沿用原 runId 和原队列；
- 否则创建完整三步运行；
- `runCharacterOrganization` 依次执行 `scan → resolve → profiles → relations → finalize`。

所以目前不能只启动某一步，也没有“完成一步就停”的入口。

### 当前“取消”实际是暂停

`WorldPanel` 的“取消AI整理”调用 `service.cancel`，最终是 `AbortController.abort()`。运行状态写成 `cancelled`，但 `startOrganization` 把 `cancelled` 也视为可恢复，因此再次点击会接着旧任务执行。

这与本次要求的“取消后废弃旧队列”相反。

### 统计位置

`finalizeStatistics` 现在由 `runCharacterOrganization` 在 `finalize` 阶段自动调用。拆开三步后，第三步不能继续偷偷调用它。

## 已确认行为

| 操作 | 运行 | 完成后 |
|---|---|---|
| 开始第一步 | 新建 runId，扫描当前全部人物，核实疑似组并合并 | 结束，不进入第二步 |
| 开始第二步 | 新建 runId，按当前人物列表建立资料队列 | 结束，不进入第三步 |
| 开始第三步 | 新建 runId，按当前人物关系建立关系队列 | 结束，不进入统计或其他步骤 |
| 暂停 | 保留 runId、当前工作项、剩余队列、Agent 上下文 | 状态 paused |
| 继续 | 恢复同一 runId、同一队列和上下文 | 不重复已确认提交 |
| 取消 | 标记 cancelled，终止执行器，废弃剩余队列 | 历史保留，旧任务不可恢复 |
| 再次开始 | 新建 runId，重新读取当前数据库 | 重新生成该步骤完整队列 |

## 暂停边界

暂停不能等工作项整体结束。一个关系工作项可能连续调用几十次 API。

实现使用 Pi Agent 现有的安全边界：

- `finishTurn`：当前 ASSISTANT 回复、工具批次和工具结果完成之后，如果已请求暂停，返回结束，不再发起下一次 API；
- `beforeToolCall`：暂停后尚未开始的工具调用被拦截，不执行新的写库；当前已经开始的工具允许安全结束；
- `prepareRequest`：暂停/取消检查后不进入下一次模型请求；
- 当前数据库事务允许完成或回滚，不在事务中途强杀。

暂停状态保存后，继续仍从当前人物的未完成上下文处理，不回到该人物的第一步，也不等待整个人物资料或关系全部完成。

## 取消边界

取消顺序：

1. 在数据库标记运行 `cancelled`，写入取消时间和可审计原因；
2. 设置取消标志并 abort 执行器；
3. `beforeToolCall`、`commitCommand` 和写事务前再次检查运行状态和取消信号；
4. 已提交事务保留；
5. 未开始队列、旧 remainingWorkIds、旧游标不再使用；
6. 下一次开始创建新 runId，重新读取当前数据库并构建完整队列。

取消后，旧模型响应即使晚到，也不能执行新的工具调用或写库。

## 字段变化

### `OrganizationState`

| 字段 | 中文含义 | 类型 | 必填 | 赋值 |
|---|---|---|---|---|
| `runStep` | 本次整本书运行只执行的步骤 | `'scan' \| 'profiles' \| 'relations'` | 新运行为是；旧运行缺省 | 创建单步运行时 |
| `pauseRequested` | 是否已请求暂停 | boolean | 否 | 点击暂停时；继续时清除 |

不新增历史表。步骤运行仍使用现有 `pipelineRuns`，步骤历史仍通过 `runStep` 和现有工作项记录读取。

### 运行状态

使用现有 `pipelineRuns.status`：

- `running`：当前有执行器；
- `paused`：同一运行可继续；
- `cancelled`：终态，不可继续；
- `completed`：该步骤正常完成；
- `failed`：失败/中断，后续是否允许新开始由按钮状态处理。

“暂停”不释放执行权；“取消”释放执行权和 lease。

## 数据流转

```text
开始第一步/第二步/第三步
  → 新建 runId
  → 读取当前数据库
  → 构建该步骤完整队列
  → 只运行该步骤
  → 完成或暂停/取消

暂停
  → finishTurn / beforeToolCall 安全边界
  → 保存 activeWork、剩余队列、上下文
  → status=paused，保持 lease

继续
  → 同一 runId + 同一队列 + 同一 session/context
  → 不重建队列，不重放已确认提交

取消
  → status=cancelled
  → abort + 写前检查
  → 旧队列失效，lease 释放
  → 下一次开始创建新 runId
```

## 触发逻辑

### 按钮状态

- 无活动/暂停运行：三个步骤按钮显示“开始第X步”。
- 某一步 running：该按钮显示“暂停第X步”，其他两步禁用，取消可用。
- 某一步 paused：该按钮显示“继续第X步”，其他两步禁用，取消可用。
- 某一步 completed/cancelled/failed：该按钮恢复“开始第X步”，其他两步可用。
- 刷新后从 `pipelineRuns` 和 lease 恢复状态；数据库 `running` 但无活动执行器且 lease 已失效时，标记为已中断/可继续，不能假装仍在运行。

### 继续与取消

- 继续只接受 `paused` 且 runStep 匹配的运行。
- 取消只终止当前活动/暂停运行；不改变已保存资产和历史。
- 取消后再次开始不复用旧 `remainingWorkIds`、旧游标、旧消息或旧任务。

## 出场统计

- 第三步不自动调用全书出场统计。
- 保留独立 `updateStatistics` 能力，可由单独操作触发；检查报告、进度和备份依赖。
- 统计更新失败不回滚人物关系修改，也不改变三步历史。
- 不删除已有统计数据或统计相关表。

## 影响范围

- `WorldPanel`：入口按钮、状态显示、暂停/继续/取消。
- `service.ts`：步骤启动、暂停、继续、取消、状态恢复。
- `organization.ts`：目标步骤调度、暂停边界、取消检查、第三步不 finalize。
- `runtime.ts`：`finishTurn`、`beforeToolCall`、`prepareRequest` 的暂停/取消回调。
- `commands.ts`：写事务前取消检查。
- `pipelineRuns`：`runStep`、状态和历史。
- `P2OrganizationPanel`：历史仍按三步展示，不改 API 详情和连续消息链。
- 单人物运行：保持现状，继续归入历史对应步骤。

## 非目标

- 不改变原 Prompt、工具业务逻辑和资产合并规则。
- 不改变 P2 整理详情内部样式、消息链、API 请求回放。
- 不删除或回滚已提交业务修改。
- 不新增一条新的历史系统或复制原始请求。
