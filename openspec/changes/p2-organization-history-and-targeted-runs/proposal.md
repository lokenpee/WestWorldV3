# P2 整理详情三步骤历史、分页与单人物整理

关联 [REQ-021](../../需求池.md)、[设计](design.md)、[任务](tasks.md)、[验收](acceptance.md)及差异规格。本变更只改 P2 整理详情的查询、分页、步骤归属和单人物运行入口，不新增另一套历史系统。

## 结论

1. P2 每次运行的请求明细仍保存在现有 `storySessionEntries`，不新增原始请求表。当前看不见第一、二步，主要原因是详情只读取最近 50 条请求，且 P2 详情以运行而不是三步骤作为第一层导航。
2. P2 整理详情固定提供三步切换：识别与合并、整理人物资料、整理人物关系。每一步先显示该步骤所有已整理对象索引，不依赖最近 50 条请求；点击对象后再分页加载其完整 API 请求。
3. 人物编辑页底部增加“AI 整理人物资料”和“AI 整理人物关系”，复用现有 P2 profiles/relations 工作项、提示词、工具和执行详情，不新建 Agent。
4. 单人物整理每次生成独立的运行记录，只增加历史，不改变完整三步运行的进度、统计或覆盖旧记录。
5. 旧数据没有 `request_trace` 时只显示可恢复的步骤状态、人物项、疑似组和修改记录，并明确标注“无 API 明细”，不伪造请求。

## 现状与根因

### 已保存的数据

现有每本书的 P2 运行保存在 `pipelineRuns`，请求明细保存在 `storySessionEntries`：

| 数据 | 位置 | 用途 |
|---|---|---|
| 运行、步骤状态、报告、修改记录 | `pipelineRuns` | 本次运行的组织状态和结果 |
| `request_trace` | `storySessionEntries` | 每次 API 的输入、工具调用、用量 |
| `prompt_snapshot` / `tool_snapshot` | `storySessionEntries` | SYSTEM、业务提示词和工具 Schema |

请求行已经有 `runId`、`contextId`、`unitId`、`characterId`、`purpose`、`usage`，足以按运行、步骤和人物分组，不需要复制新表。

### 当前不可见的原因

- [trace.ts](../../../src/features/agents/trace.ts) 的 `readBookTrace` 默认只返回最近 50 条请求，界面没有加载更早请求的入口。
- [AgentRunPanel.tsx](../../../src/features/agents/AgentRunPanel.tsx) 先按当前 `runId` 读取，再从已加载请求生成人物窗口；前面的目录页、疑似组和人物请求被截断后，相关窗口自然消失。
- [WorldPanel.tsx](../../../src/features/world/WorldPanel.tsx) 的进度只绑定最新一次 `organizationRuns[0]`，不是三步骤历史视图。
- 当前没有“只整理一个人物”的服务入口；人物编辑页也没有对应按钮。

### 已核对的数据限制

仓库内最新可用备份是 `红楼之挽天-三河帮-2026-11-05T15-00-00-001Z-289280b5.wwv2`：

- `storySessionEntries` 854 条，只有 `message` 546 条和 `commit` 308 条，`request_trace` 为 0。
- 唯一一次人物整理运行停在 `profiles`，138 个人物中 8 人已检查，疑似组结论 4 条，关系项为空，`requestLedger` 为 0。

因此，这份旧备份的第一、二步 API 请求明细无法恢复。它的步骤状态、疑似组结论、已检查人物和修改记录仍可显示。当前浏览器中的书库是否已有请求明细，需要以最新导出的书备份核对；新版本运行会写入 `request_trace`。

## 已确认需求

### P2 整理详情

- 保留现有唯一的 P2“整理详情”入口。
- 进入后固定显示三个可切换步骤，不随当前执行步骤隐藏：
  1. 第一步：识别与合并
  2. 第二步：整理人物资料
  3. 第三步：整理人物关系
- 每一步进入时先展示该步骤所有已经整理过的对象索引：目录页、疑似组、历史人物及其运行入口，不受 API 请求分页影响。
- 点击某个对象后再加载它的 API 请求；请求超过 50 条时可以加载更早记录，不能牵动其他对象或把早期人物藏起来。
- API 详情内部保持现状：SYSTEM、USER、ASSISTANT、TOOL CALL、TOOL RESULT 的显示顺序、参数展开、Token、耗时、费用、修改前后对比均不改。

### 单人物整理

- 在打开某个人物后的编辑页底部操作栏增加两个按钮，与“保存 / 取消编辑 / 删除条目”并列：
  - `AI 整理人物资料`
  - `AI 整理人物关系`
- 两个按钮分别复用现有 P2 的 `profiles` 和 `relations` 工作逻辑，不新建 Agent。
- 单人物资料记录归入 P2 第二步，单人物关系记录归入第三步。
- 运行中即可查看；完成后永久保留；同一人物多次整理保留多条运行记录，不覆盖旧记录。

## 字段变化

### `OrganizationState`

新增字段：

| 字段 | 中文含义 | 类型 | 必填 | 默认 | 赋值时机 | 读取者 |
|---|---|---|---|---|---|---|
| `mode` | 整理范围 | `'full' \| 'profile' \| 'relations'` | 否 | 旧数据按 `full` 处理 | 创建完整运行或单人物运行时 | 调度器、运行详情、主进度过滤 |
| `targetCharacterId` | 单人物整理目标人物编号 | `string` | 单人物运行时必填 | 无 | 创建单人物运行时 | 调度器、关系项构建、详情筛选 |
| `CandidateGroup.originStep` | 候选组来源步骤 | `'scan' \| 'resolve' \| 'profiles' \| 'relations'` | 否 | 旧数据按运行范围回退 | 保存疑似组时写入当前工作项来源步骤 | 详情归属、历史兼容 |
| `CandidateDecision.originStep` | 候选结论来源步骤 | 同上 | 否 | 旧数据按运行范围回退 | 候选结论保存时从候选组复制 | 详情归属、历史兼容 |

完整三步运行使用 `mode: 'full'`。单人物运行使用 `mode: 'profile'` 或 `mode: 'relations'`，并带目标人物编号。

### `WorldRun`

新增或明确顶层运行范围：

| 字段 | 中文含义 | 类型 | 必填 | 默认 | 赋值时机 |
|---|---|---|---|---|---|
| `scope` | 运行范围 | `'fullBook' \| 'character'` | 是 | `fullBook` | 创建运行记录时 |

单人物运行 `scope: 'character'`；完整三步运行保持 `fullBook`。`scope` 只用于区分完整进度和单人物记录，不参与资产权限判断。

### 不新增的数据表

请求明细继续使用 `storySessionEntries`。不新增 `organizationHistory`、`stepTrace` 或其他历史表。步骤索引由现有 `pipelineRuns.organization` 里的目录页、疑似组、人物资料项和关系项生成；请求仍按 `runId` 和对象工作项读取，不重复保存整份 Prompt、工具 Schema 或消息。

## 数据流转

### 完整三步运行

```text
用户点击 AI整理
  → 创建 mode=full 的 pipelineRun
  → 每一步 runtime.run
      → TraceSession 写 request_trace、prompt_snapshot、tool_snapshot
      → request_trace 带 runId/contextId/unitId/characterId
  → 报告保存到同一个 pipelineRun
```

### 单人物运行

```text
人物编辑页点击 AI整理人物资料/关系
  → 校验人物、编辑锁、未保存修改和世界执行权
  → 创建 scope=character 的新 pipelineRun
      organization.mode=profile|relations
      organization.targetCharacterId=当前人物
  → 只构建目标人物的一个 profile 或 relations 工作项
  → 复用现有 P2 runtime、提示词、工具和 TraceSession
  → 完成后结束本次运行，不写全书 compileProgress
  → 运行详情按步骤归入第二步或第三步
```

单人物资料运行只增加第二步记录；单人物关系运行只增加第三步记录。跨步骤查询、合并、资料或关系编辑仍按现有权限执行，但不把其他步骤标记为已完成。

### 步骤索引与请求详情

步骤索引和 API 请求分开读取：

```text
进入某一步
  → 读取本书所有 P2 运行的 organization 工作项
  → 生成该步骤全部对象索引
      第一步：目录页、来源为第一步的疑似组/合并结论
      第二步：人物资料项、单人物资料运行
      第三步：人物关系项、单人物关系运行
  → 立即展示所有对象，不读取 API 请求正文
  → 用户点击某个对象
      → 按 runId + 对象工作项读取该对象的请求页
      → 首次 50 条，之后按稳定游标加载更早请求
  → API 详情继续使用原有 ApiRequest 渲染
```

归属规则：

- 单人物运行的全部请求按运行范围归属：`mode=profile` → 第二步，`mode=relations` → 第三步。运行内部临时出现的 `candidate` 工作项不改变归属。
- 完整运行的 `directory` 和来源为 `scan`/`resolve` 的 `candidate` 工作项归入第一步。
- 完整运行第二、三步发现的候选组按 `originStep=profiles`/`relations` 归入对应步骤；`unitId` 的 `candidate:` 前缀不能单独决定步骤。
- 旧候选组没有 `originStep` 时：单人物运行按运行范围回退；完整运行若候选位于第一步工作集则归入第一步，否则按该运行当前已知的工作项或请求上下文回退。

分页规则：

- 对象索引一次展示完整对象集合，不因请求分页减少。
- 请求页使用 `(startedAt, requestId)` 稳定游标：加载更早请求时取当前最早一条之前的记录，不使用会随新请求变化的 offset。
- 运行中的新请求追加到当前对象列表，按请求 ID 去重；旧请求游标不因新增请求漂移。

旧运行没有 `request_trace` 时：

```text
organization.scanPages + candidateDecisions → 第一步摘要
organization.profileItems → 第二步摘要
organization.relationItems + pairChecks → 第三步摘要
report.assetEdits → 修改前后
显示“旧版本未保存 API 明细”
```

## 触发逻辑

### 步骤切换

- 点击任一步骤：加载并显示该步骤全部对象索引；不读取请求正文，不改变运行状态。
- 点击对象：加载该对象的请求页；该对象没有请求明细时显示摘要或“暂无记录”，不影响其他对象。
- 某对象请求超过当前页：显示“加载更早请求”；只追加该对象记录，不刷新、覆盖或重新排序其他对象。
- 运行中新增请求：追加到当前对象；加载更早记录使用稳定游标和请求 ID 去重。

### 单人物按钮

- 前置条件：已打开一个人物、不是新增、没有未保存修改、没有版本冲突、世界资产未锁定、没有正在运行的世界资产任务。
- 点击资料按钮：创建 `profile` 单人物运行，打开同一次运行的 P2 详情。
- 点击关系按钮：创建 `relations` 单人物运行，打开同一次运行的 P2 详情。
- 运行中：按钮禁用，详情可打开并显示进行中的请求；完成后按钮恢复。
- 失败或取消：保留已提交修改和请求记录，详情显示失败/取消状态；用户可再次点击生成新运行记录。
- 同一人物连续整理：每次新建运行，不覆盖旧运行；详情按时间倒序显示，可逐条打开。

### 完整运行与单人物运行

- 完整运行的 `organizationSummary`、`compileProgress` 和主进度只读取 `scope=fullBook` 的运行。
- 单人物运行不更新 `compileProgress`，不修改完整运行报告中的 checked/modified 统计。
- 单人物运行仍使用世界执行权、版本校验、关系重检和现有并发保护。
- 已提交资产修改不会因新的单人物运行回滚；旧运行的历史记录不会被删除。
