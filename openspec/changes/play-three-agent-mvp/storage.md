# 游玩存档、回合提交与整书恢复

[PRD 总导航](proposal.md)　｜　[界面与流程](ui.md)　｜　[工具目录](proposal.md#tools)　｜　[提示词目录](proposal.md#prompts)　｜　[存档与表](storage.md)　｜　[代码运行](design.md)　｜　[验收](tasks.md)

本文的产品用语见[提案中的术语说明](proposal.md#terms)。本附件说明方案拟怎样存储游戏进度。以下表名、版本号和时序用于实施评估，当前代码里的书库尚未建立这些表。

## 1. 放到哪一层

游玩服务拿到 `workspace.openBook(bookId)` 后，在该书库新增四张逻辑表。同一本书可以有多个独立存档。按书打开数据库后，任何跨表引用还要核对同一个存档。上游人物、地点、关系、节点、事件与故事线沿用资产库；游玩建档服务只复制本局获准使用的人物、节点等资料，作为建档时保存的书中资料（`assetBaseline`）。查看小说原文属于人在节点详情中的操作，游玩表和游戏服务不读取该操作的内容。每次操作的书和存档在启动时绑定，工具参数、当前界面后来选中的书都不能改变该次执行的归属。[应用装配](../../../src/main.tsx) · [书库入口](../../../src/lib/storage/workspace.ts) · [游玩接入设计](../play-session-foundation/design.md)

正式入口通过本机服务读写 SQLite 数据库；浏览器测试环境通过 Dexie 读写浏览器数据库。实施时保留原有第 12 版迁移，另加第 13 版建四张空表，同时登记本机存储的逻辑表名及主键。SQLite 已有统一的记录表，按书、逻辑表和字符串主键寻址，组合字段查询由适配层翻译。两端都在写入时逐一核对主键和当前版本，保证同一请求只保存一次。只给 Dexie 加二级唯一索引无法覆盖正式运行路径。[Dexie 版本声明](../../../src/lib/storage/workspace.ts) · [本机表清单](../../../src/features/local-storage/schema.ts) · [SQLite 查询和提交](../../../src/features/local-storage/sqliteStore.ts)

## 2. 四张表和字段

以下 ID（记录编号）均为非空字符串，程序新建记录时使用 UUID（通用唯一标识符）。各表均有唯一标识本条记录的主键 `id`、所属书籍编号 `bookId` 和创建时间 `createdAt`（ISO 格式的 UTC 时间），由程序在创建时写入。游玩子表另有必填 `saveId`，指向同书 `playSaves.id`。这些字段不可由模型修改。下文“空”指 JSON 的 `null`。除标明可空或初始值外，字段一律必填。业务文本完整保留，列表初始为空数组。界面、执行器、备份预检均以这些定义解释记录。

<a id="table-saves"></a>

### playSaves · 存档和当前进度

| 字段 | 类型、初值与校验 | 写入时机与读取方 |
|---|---|---|
| packageTitle | 必填字符串，取创建时资产包对应书籍的名称。`bookId` 是本机该已导入包的身份，`assetBaseline.digest` 区分固定的资料版本。 | 建档时写入，列表及聊天页读取。备份恢复为新书时重写 `bookId`；存档名称和建档时保存的书中资料随存档恢复 |
| displayName | 非空字符串。程序在建档事务内按该包已有存档分配默认名“存档 N”，与稳定 ID 分开保存 | 准备页列表及聊天顶部读同一名称。导出恢复保留该名 |
| assetBaseline | 必填对象，含 `formatVersion`（资料格式版本，正整数）、`digest`（内容的 SHA-256 校验值）、`entries`（按资产类别和编号查找条目的对象）。每条含资产类别 kind、原书编号 id、修订号 revision 和实际保存的字段 fields；无独立修订号的资产可取 `revision:null` 并使用内容校验值核对条目有无变动。`fields` 仅存[装载器](context-loader.md)允许的游戏结构化字段，包括节点排序、参与人、地点名和已提取的经过。 | 建档时读取同一时点的书中资料，并随尚未生成开场的存档草稿一同保存。目录、详情及备份都从这一份资料读取。以后编辑原书时，新建存档采用修改后的资料。 |
| protagonistId | 可空字符串，存档草稿初始为空，确认开局后指向建档资料中的原著主角 | 与 `openingAnchor` 同时确定。局内沿用其身份并独立保存该主角的位置、所知和关系 |
| openingAnchor | 可空对象，存档草稿初始为空；确认后含 `nodeId`（建档资料中的节点编号）、`nodeRevision`（该节点修订号）、`phase`（首版为 `after`，从节点结束后接手）及 `assetRefs`（指向建档时保存的条目及其字段的稳定引用数组）。核验建档资料的内容校验值、节点排序位置及人物和场景是否有结构化依据 | 玩家点开始时与已选开局候选同时保存，第 0 版与恢复预检读该起点 |
| headVersionId | 可空版本 ID，初始空；非空须指向同局已提交版本 | 每次成功结算后写入当前生效版本的编号。回看历史、续玩、改写及恢复备份均从该编号查找 |
| activeAttemptId | 可空尝试 ID，初始空；非空时标明该局唯一正在执行的请求 | 启动、申诉或重试时登记正在执行的请求编号，完成、撤回、失败或取消时清空；界面据此锁定输入 |
| updatedAt | UTC ISO 时间，初值等于 createdAt | 存档进度变化时由服务更新，存档列表用于排序 |

主键 `id`，Dexie 二级索引 `updatedAt`。开局尚未成功时可以恢复或重试创建流程，`headVersionId=null` 的存档没有可供行动的世界。

<a id="table-attempts"></a>

### playAttempts · 玩家请求、审核与候选结果

每次发送或改写生成一个 `attemptId`，存为本表 `id`。界面在首次发送前生成并沿用它查询这次请求已提交的版本号，双击、超时重送不会创建两个回合。申诉和失败重试沿用此 ID。

| 字段 | 类型、初值与校验 | 写入时机与读取方 |
|---|---|---|
| kind | opening（开局） / action（发送行动） / rewrite（改写末轮） | 服务依开局、发送或改写入口设定，权限检查读取 |
| baseVersionId、expectedHeadId | 前者为计算本轮所用的版本，后者为提交前应核对的当前版本，均可空。开局两者均空；普通行动都指向当前生效版本。改写 V1 时，从它的父版本 V0 重新计算（baseVersionId=V0），提交前检查当前生效版本仍是 V1（expectedHeadId=V1） | 创建尝试时固定；装载器以 baseVersionId 读本局状态和该版之前的有效历史，提交器以 expectedHeadId 验证当前进度 |
| playerInput、rewriteDirection | 可空文本。开局均空；普通行动保存玩家最初输入的全文；改写复制原轮的玩家输入，另附必填改写方向。原轮存在已通过的申诉时，从 expectedHeadId 对应的已提交尝试取原申诉与采用的行动作为解释材料 | 服务创建时保存，导演和回看界面读取 |
| appealUsed、appealText、effectiveInput | 布尔值初始 false，后两项为可空文本。申诉说明与玩家最初输入的全文分别保存，审核采纳的可执行行动单独保存 | 程序首次接受申诉时在同一事务将标记置 true 并保存理由；导演审核通过后由程序保存 effectiveInput。重试不清空已用次数 |
| rejectionReason | 可空文本，初始空 | 导演首次拒绝时保存可向玩家解释的依据；申诉结果保存于对应执行记录，可查看初次与复核意见 |
| status | running（执行中） / awaiting_selection（等待选择开局） / withdrawn（行动已撤回） / committed（已结算） / failed（执行失败） / cancelled（已取消），创建为 running；awaiting_selection 只允许用于已准备开局卡的 opening | 执行器按候选准备、审核、提交或终止结果写入，界面恢复开局卡、输入和申诉入口 |
| runId、ownerId、leaseUntil | runId 为本次执行编号；ownerId 为执行页面的随机编号；leaseUntil 为该页执行权限的到期时间（UTC 毫秒时间戳）。后两者仅在执行期间有值，结束清空 | 启动、申诉或重试时换发 runId 并登记执行页面。该页工作期间延长执行期限，其他页面显示当前进度。丢弃旧 runId 返回的结果 |
| candidates | 对象含 `openingOptions[]`，每项保存 `id,protagonistId,locationId,label,nodeId,nodeRevision,phase,initialStateChanges,beats,stopAt,evidenceRefs`。执行器核对候选依据同属 `assetBaseline`，补上稳定 `openingAnchor` 与所用 `assetPins`。`selectedOptionId` 可空；`director`、`writer` 分别暂存行动导演的裁定和写手的段落，均可空。开局裁定已保存在所选开局卡中。 | 仅当前 `runId` 可补充输出。准备页据此显示推荐起点或多个有依据的起点，聊天窗口据此显示待结算正文。选中后持久保留该卡的完整结构、稳定证据和 selectedOptionId，直至可以从正式版本回读；重试、导出和副本恢复均按同一选择装载 |
| committedVersionId、error、updatedAt | 可空版本 ID、可空对象（code 和 message 均为字符串）、UTC ISO 时间，初值依次为空、空、createdAt | 成功提交时写入已提交的版本号；终止时提供明确原因。状态变化时更新时间，刷新时读回 |

主键 `id`，二级索引 `saveId`、`[saveId+createdAt]`。撤回、失败的输入按尝试显示在交流记录；只有已结算的剧情进入当前版本的游戏历史。首次撤回后，玩家申诉需同时满足本条行动尚未申诉、同局空闲、当前生效版本仍为 expectedHeadId。已推进的存档可以重新发出行动。

<a id="table-versions"></a>

### playVersions · 不可变的已成立事实

| 字段 | 类型、初值与校验 | 写入时机与读取方 |
|---|---|---|
| attemptId、runId | 非空字符串，分别指向产生该版本的请求和成功提交的那次执行 | 统一提交时固化，供丢失反馈时查证及回看 |
| parentVersionId、turnNo | 可空同局父版本、非负整数。开场固定空、0；其他均为父版本轮序加一。改写复用原轮序，可产生两个同轮序的历史版本 | 提交器写；装载器从当前版本逐次查找父版本，取得这次续玩可采用的游戏历史 |
| prose、snapshot、stateChanges | `prose` 为本轮已校验小说正文。`snapshot` 是到该版本为止本局已触及对象的可还原完整状态，字段见第 3 节。`stateChanges` 是本轮已写入存档的变更列表，保存稳定对象 ID、前后值与固定依据；开局记录各初始字段从空到有的变化。 | 一次事务提交。读取或改写直接取得计算本轮所用版本的完整游戏状态；需要核实具体何时发生变化，再查该版本的变更及剧情步骤 |
| beats | 本轮依次发生的剧情步骤，每步保存步骤编号 id、相关人物编号 actorIds、发生的经过 text、允许向玩家公开的依据 revealRefs。提交时将本次请求中的资料引用换成可在存档中长期查找的编号 | 提交程序从导演已核准的裁定复制，用于下轮回读具体经过和玩家可见信息 |
| assetPins | 本轮从建档资料实际采用的条目编号、字段名及其内容校验值列表；结构见第 3 节。无新增资产使用时可为空 | 提交器根据本轮各角色实际采用的字段生成，备份与回放可独立复核所用依据 |
| memoryNotes | 本轮新增的笔记列表，每项含 id、text、entityIds 数组与 evidenceRefs 数组。依原始资料核对，指向本局已生效历史 | 程序保存有依据的旧约定、指代和待处理事项，导演可按实体检索和回读原轮 |

主键 `id`，二级索引 `saveId`、`attemptId`、`[saveId+turnNo]`。同一尝试仅可提交一版，由提交事务核验。存档显示从 headVersionId 沿 parentVersionId 逐步查到开场版本，按正序显示。仅按轮序或创建时间排序会把改写前的正文混进当前历史。

<a id="table-runs"></a>

### playRuns · 模型执行和受控工具记录

| 字段 | 类型、初值与校验 | 写入时机与读取方 |
|---|---|---|
| attemptId、runId | 字符串，回合尝试编号及本次执行编号。一轮的多个角色、分页或修复请求各用独立记录主键 id | 程序在调用前写，调试和恢复时按 runId 查同一次执行的各条记录 |
| role、stage | 两字段均在建立执行记录时明确赋值。stage 为 play-opening（开局导演）或 play-direct（行动导演）时，role=director；play-write（写手）时 role=writer；play-compact（已结算回合的独立历史摘要）时 role=null。仅摘要允许此空值 | 回放按 stage 显示任务名称；备份预检核对角色和任务的对应关系。摘要只写本条执行记录 |
| model、promptRef | model 为模型标识字符串。promptRef 保存任务标识 task、提示词正文的内容校验值 hash 和当时使用的全文 text | 调用前由运行时截取，便于回答该次执行使用了哪版提示词 |
| request、toolEvents | 已发出的业务消息和工具声明对象；工具记录数组，每项含 callId、name、args、result、status。调用未返回时 result 为空 | 运行时记录实际发给模型的资料、工具调用和结果。恢复依据取有效版本，诊断人员按角色查看 |
| output、status、error、finishedAt | 可空模型输出；running / succeeded / failed / cancelled；可空错误对象（code、message）；可空完成时间。初始依次为空、running、空、空 | 调用结束后填入，记录已失效执行编号的返回结果或取消原因，不触发新一轮写入 |

主键 `id`，二级索引 `[saveId+attemptId]`、`runId`。仅序列化实际发给模型的角色材料、工具参数及工具按权限返回的结果、模型和提示词；鉴权头、API 密钥、凭据对象和原始网络请求对象不进入任何游玩表或备份。

## 3. 快照、来源和长期记忆

`playSaves.assetBaseline` 保存本档建档时取得的书中资料，`playVersions.snapshot` 保存本档在该版本结算时已涉及的人物、位置、物品、人物所知等状态的完整记录，下文称为快照。第 0 版保存所选开局卡核准的人物、场景和眼前已经成立的事实。后续版本从 `parentVersionId` 的局内快照应用本轮各项变更，一起保存新快照、本轮 `stateChanges` 和已用的 `assetPins`。读取新版本或改写时直接取所需版本快照；读取故事历史才逐次查找父版本以还原先前回合。每档保留一份只读的建档资料，版本内不重存整包、全书或历轮正文。一个存档内可保留同一轮的不同版本，续玩从 headVersionId 读取当前生效版本的游戏状态。同书各存档分别维护人物、地点、知情、事件和持有物。

| 字段 | 值的结构与更新规则 |
|---|---|
| scene | timeText（场景时间描述，字符串）、locationId（地点编号，字符串）、presentIds（在场人物编号数组）、stopAt（留给玩家接话的位置，字符串）。开局给出有依据的在场情况及可行动位置，后续只更新实际发生的时空变化 |
| people、places | 按局内编号查找人物或地点。人物值为姓名 name、生死状态 life（健在 alive / 已故 dead / 未知 unknown）、位置 locationId（可空）、当前状况 condition（可空文本）、依据编号 evidenceRefs。地点保存名称 name 和依据编号 evidenceRefs。导演可在本轮补充确有需要的局内实体 |
| items | 本局物品编号、名称 name、持有人编号 holderId（可空）、放置地点编号 locationId（可空）、数量 quantity（非负整数）、依据编号 evidenceRefs。一次转移在同一快照变更归属，持有该物品的人或物品所在地点有明确依据 |
| relations | 关系编号 id、从谁 fromId、指向谁 toId、关系说明 description、依据编号 evidenceRefs。两端均引用本局人物；方向相反的态度可分别记载 |
| events、promises | 本轮事件含编号 id、经过 summary、参与者 actorIds、依据编号 evidenceRefs；旧事件按版本与编号回读。承诺含编号 id、谁向谁作出承诺 fromId/toId、承诺内容 terms、状态 status（待履行 open / 已兑现 fulfilled / 已违约 broken）、依据编号 evidenceRefs。后续履约更新承诺状态，先前版本保留原记录 |
| knowledge | 每项有 id，以 holderId 指定具体人物，保存此人对哪句话或哪件事的看法 proposition、态度 stance（知道 knows / 相信 believes / 怀疑 suspects），以及此人获知消息的来源 sourceRefs。若人物不在场、无人传话，事实成立也不会给此人新增认知 |

导演给出的 `stateChanges` 是数组，每项含 `kind,subjectId,field,before,after,evidenceRefs`。程序按变更类别 kind、对象编号 subjectId、字段名 field 核对数据类型与依据 evidenceRefs，将变更前的值 before 与父版本实际值核对后，依序将变更后的值 after 写入临时状态；任一项失败即放弃本次候选。例：基础状态中贾珩 `C1-P001` 在本局“长安节度使府官厅”，改写行动为告辞离厅。若导演已判定离开成立，要同时使人物所在位置、场景位置与在场人符合厅外场景；云光仍在厅内。两个版本看到不同局面，源节点的地点字段保持原值。

玩家最初输入的全文和申诉说明取自 playAttempts，小说正文取自 playVersions。准备下一轮资料时，从计算本轮所用的版本开始逐层回查父版本，取出相关笔记、承诺和近期正文，引用不足时按版本读取原始记录。整理历史摘要时，任务记录引用所覆盖的最后一个游戏版本的 attemptId 和 runId，用选定的历史版本编号序列、正文和笔记计算 inputDigest（本次输入的校验值）。整理成功时在 playRuns.output 保存 summary（事实 facts、人物信念 beliefs、未了事项 openThreads、证据引用 evidenceRefs）、coveredVersionIds、inputDigest；写回前再核对同局、覆盖版本和来源内容的校验值。它只写自身执行记录，不领取存档执行权，不改变世界或解锁输入。程序从计算本轮所用的版本回查父版本。coveredVersionIds 必须是这段历史里连续的一组版本，输入校验值也须相符、引用仍然有效，才能采用该摘要；任务失败或旧分支命中时继续按原始记录装载。刷新不自动续跑压缩。写手只收到本轮可揭示的资料。

**固定资产依据。** 建存档草稿时从同一时刻的书中资料生成一份 `assetBaseline`。将允许保存的字段和值按统一规则写成 JSON，再计算内容校验值。冻结的条目涵盖已存在的人物、关系、地点、节点、事件与故事线及所需的 ID 解析信息。各节点按章序、节点顺序、ID 排序。条目仅包含允许进入游戏的结构化字段，排除节点引文、关系引用中的摘录、逐字摘录的人物台词、章节正文及一切定位到小说正文的字段。相应的用户查看入口仍由资产页处理。游玩中的检索、确认、恢复与重试只取建档时保存的书中资料。建档后即使原书编辑、删除或合并了某节点，旧档首次发给模型的资料、可搜索的目录与详情仍取自建档时保存的书中资料；在同一本书重新建档才读到新版资料。

每条 `assetPins` 记录保存引用编号 id、资产类别 kind、资产编号 assetId、修订号 assetRevision、本轮采用的字段名 fieldNames 和这些字段的内容校验值 projectionDigest，均指本档 `assetBaseline.entries[kind][assetId]`。无独立修订号时 `assetRevision=null`，核对所用字段的内容校验值。请求发出时在 `playRuns` 记录每个角色实际看到的字段，以及这些字段对应的来源；候选暂存只固定本轮实际采用的一组字段与内容校验值，成功时转成版本内的稳定引用。每轮不重复复制建档时保存的书中资料。局内证据用“版本编号 + 剧情步骤或事件编号”并沿 parentVersionId 核对来源版本属于当前游戏历史。备份预检校验建档资料的内容校验值及允许保存的字段清单、assetPins 中所列字段是否存在且其内容校验值是否一致、每个局内证据的版本归属，完全依据备份内这本存档的固定材料。[现有资产字段](../../../src/features/assets/types.ts) · [模型交付](agent-contracts.md)

### 导演可提议的字段与新增对象

`stateChanges` 的外层 `kind` 与快照的集合名按下表映射。程序为 `subjectId` 解析本局对象。首版把每个字段的变更做成可枚举的类型，用项目的数据类型校验库 TypeBox 核对数值、对象、枚举和引用；提交器将同一候选按以下顺序应用到临时快照。

| kind / 快照集合 | 可写字段或操作 | 提交时检查 |
|---|---|---|
| scene / scene | timeText、locationId、presentIds | 地点和在场人存在；场景所在地及主角的位置一致。导演在顶层提交 stopAt；提交器使用父版值（开局为空）和本轮已核准的 stopAt，在值变化时生成一条 scene.stopAt 变更记录，以本轮最后一个公开剧情步骤为依据。快照和写手请求取同一值。导演在 stateChanges 重复提交该字段时返回 INVALID_RESULT |
| person / people，place / places | 新建用 field=create；人物可改 life、locationId、condition，地点可新建 | 新建给出第 3 节该类型的完整初值及依据。已有资产复用书内身份；原著外实体仅在本局生成。死亡角色若出现在回忆或传闻中，出场方式须与现场状态分开 |
| item / items | create、holderId、locationId、quantity | 同一物品在人物手中或落在地点，两者互斥；转移的旧值要与父版一致，数量为非负整数 |
| relation / relations，promise / promises | create、description（关系）或 status（承诺） | 关系两端或承诺涉及的两个人物都必须存在；有方向的态度按方向记录；受托和已经答应需分别取证 |
| knowledge / knowledge | create、stance | 新条目同时含 holderId、命题、态度和获知来源。亲历须能定位角色参与的事实或目击过程，转述须有角色实际听到的传递事件。秘密或信念不得由在场名单批量生成 |
| event / events | create | 现场剧情步骤随版本保留，按需另建有编号的业务事件以供人物获知或履约引用。事件附实际发生的剧情步骤与参与者 |

新建项用 `before=null` 和一个仅在本次候选中唯一的临时编号，如 `new:heard-question`。服务在同一次尝试中为这些临时编号分配稳定 ID，先建身份映射，再解析同批引用，包括人物、物品和地点之间的引用。模型只能使用程序给出的已有编号，或本候选声明过的新名字。拒绝重复新名、对同一字段提出互斥修改、来源成环或引用未定义对象。整组变更应用后再检查数值和对象引用是否仍满足所有约束。输入、状态、依据的业务文本保留全文。

导演可在自己的输出中以 `beat:b1` 指向刚裁定的本轮剧情步骤；它用于给局内新事实标来源。程序校验剧情步骤、行动、前值和在场者，根据下一个角色可看的资料，为它生成只在本次请求有效的资料编号，最后将本次执行中的剧情步骤编号转为持久的“版本 ID + 剧情步骤编号”。提交的版本通过 `beats` 保存导演裁定的剧情步骤及先后顺序，并以 `attemptId,runId` 对应成功的执行证据，供回读和预检。源材料工具无法通过此临时编号读取未提交版本。写手只交按顺序排列的段落和依据。程序核对各段承接了导演的哪些动作，把段落拼成本轮正文 `prose`。

## 4. 回合如何提交

所有写步骤复用 `transact(db,'rw',tables,callback)` 及回调提供的数据库连接对象。SQLite 服务按书为显式事务加锁；导演查资料、写手生成正文、等待玩家申诉都在事务外。事务负责领取、暂存、校验或提交，每次只占用读写所需的时间。[事务封装](../../../src/lib/storage/transaction.ts) · [本机事务协调](../../../src/features/local-storage/server.ts)

1. **新建或继续。** 新建时在同一书库事务中读取允许游玩使用的书中字段、生成条目并计算内容校验值，同时写入保存了这些书中资料的存档草稿与 `opening` 尝试。在同一事务内同步计算校验值，或使用现有的事务等待机制完成计算，网络和模型调用在事务提交之后开始。后续检索不再访问当前上游数据。导演依据有序节点和本角色可读的资料提出推荐，程序核验其归属、修订与字段，把候选暂存 `openingOptions`。准备完转 `awaiting_selection`，释放执行权。准备页默认显示有效推荐。玩家选择推荐或另一个成立的候选并点“开始”后，确认事务先读取同局的 opening 尝试。如果已有 selectedOptionId，重复选择同一张卡会返回已存进度或已提交的开场版本号。选择不同卡时返回已选卡并提示冲突。首次确认要求 awaiting_selection、headVersionId 为空、同局空闲且候选与建档时保存的书中资料一致；在同一事务保存完整已选卡及稳定证据、主角和起点，设为 running，登记 activeAttemptId、ownerId、执行期限 leaseUntil 及新执行编号 runId。登记成功后页面进入聊天，只有取得执行权的调用方在事务提交后按所选开局卡的动作链调用写手。依据不足时显示缺哪些资产。点击“继续”时，有已结算版本就恢复有效聊天与当前位置；等待选卡的草稿回到原来的准备页，已有选择但开场未提交时显示进度或手动重试入口。单纯打开存档不调用模型。

   发送行动或改写时，读取存档、当前生效版本及对应请求。已有相同 attemptId 的请求返回它的运行状态或已提交的版本号。局内有其他活动尝试则返回占用信息。核对当前生效版本、填写 baseVersionId 和 expectedHeadId，设 activeAttemptId，生成新的 runId，登记执行页面 ownerId 和执行期限 leaseUntil，返回后才装载资料和调用模型。
2. **裁定与申诉。** 导演认为不可尝试时，在同一事务记录公开理由、标记 withdrawn、释放当前执行，当前生效版本保持原值。申诉沿用原 attemptId，一次事务检查状态为 withdrawn、同局空闲、当前生效版本符合预期、appealUsed=false，再同时设置 appealUsed=true、理由和新 runId，重新执行审核。第二次拒绝后仍可另发新行动。技术重试只接受 failed 或 cancelled；若申诉执行因模型故障中止，重试已保存的同一份申诉，不能换理由获得第二次申诉。
3. **从导演手中接戏。** 选定开局卡或行动导演允许尝试后，程序从已校验的 `beats[]` 保留动作编号、人物、具体经过及可公开的资料编号，附上 `stopAt` 和允许写到的现场事实，调用写手。写手逐段交出正文，程序核对步骤、顺序和依据。暂存前检查 activeAttemptId、runId 和 expectedHeadId，核对通过才更新本次尝试的 writer。待保存的短时间内，聊天可显示这份正文，发送框保持锁定。
4. **统一生效。** 同一事务检查表行同书同局、activeAttemptId 等于尝试 ID、attempt.runId 等于返回结果携带的 runId、headVersionId 等于 expectedHeadId，核对所选开局卡或本次行动导演裁定与写手正文均已通过校验，再核对状态变更前值、引用及知情边界。读取 `baseVersionId` 的局内快照、试算变更；将本轮正文、动作链、新快照、已生效变更记录及所用资产字段引用写入同一条 playVersions，将 headVersionId 设为新版本的编号，写入 committedVersionId，将状态设为 committed，清空 activeAttemptId、执行页面和执行期限。页面未收到提交成功的通知时，按原 attemptId 查回同一版本。已提交的旧版本不能被模型工具改写。
5. **改写例子。** 局 A 的 V0 以 `C15-N001` 中翠华山匪情谈罢为起点。V1 中贾珩留厅，追问云光先前为何改称恩主。玩家把最后一轮改成“告辞离厅”，程序建新尝试，`baseVersionId=V0,expectedHeadId=V1`。新版本 V1b 与旧版本 V1 的父版同为 V0。改写成功时将当前生效版本改为 V1b；此时 V1 的追问和云光自称方才失礼的答复只属于旧版，V0 已成立的称谓变化与匪情仍然保留。若改写失败则从 V1 继续。开场和未结算的候选没有改写入口。
6. **取消、故障与刷新。** 保存报错或玩家取消时，先按 attemptId 查询是否已有提交。已成功的直接返回该版本；尚未提交时按尝试与执行编号标记失败或取消，撤下暂存正文，清除 activeAttemptId、执行页面和执行期限，再恢复输入框。若存储暂不可写，在可读取后查询已提交版本；仍在运行的尝试按下述到期回收规则处理。玩家可以查看最初输入的全文并重试。重试沿用同一回合尝试、同一份建档资料和计算本轮所用的版本，换发执行编号 runId，清空上次执行暂存的行动裁定和写手正文。开局以 selectedOptionId 决定从哪一步恢复。选择前失败可重做开局推荐；选择后保留完整已选卡及稳定证据，用新执行编号为所选卡的公开依据重新分配资料编号，再调用写手生成开场。若玩家其间已推进，界面保留玩家最初输入的全文供重新发送。打开另一标签页可查看原页面的进展。刷新时先查已提交的版本号；仍在运行时检查执行期限。到期后在同一事务核对并回收中断的尝试，显示重试。另一个页面已接手时，拒绝旧执行编号返回的暂存、提交和释放占用请求。恢复时不自动发起模型调用。

## 5. 旧书、备份和调用方

- **书库升级。** 拟议 Dexie 12→13 直接建空游玩表；没有游玩记录的旧书首次进入显示“尚未开局”。本机逻辑表清单、浏览器旧库迁入本机的表白名单、备份表清单及存储 JSON Schema 同步登记四表。电脑已有其他书时逐书验证，升级不需要重新提取小说资产。[旧库迁入](../../../src/features/local-storage/migration.ts) · [运行时预检 Schema](../../../docs/v2/resources/v2.2/storage.schema.json)
- **整书导出。** 拟议整书备份格式 15→16。现有导出在读事务中取同一时点全书数据，每张业务表写入独立 JSON 并计算 SHA-256。新增四个游玩文件，即使没有存档也需有空数组。拟让整书导出和导入共用容量判定。编码器统计含 manifest.json 在内的全部条目及其 UTF-8 字节，按未压缩字节数统计，合计最多 256 MiB（1 MiB 为 1,048,576 字节）、条目最多 40000 个，压缩后再核对 ZIP 最多 128 MiB；三项均允许恰好等于上限。超出任一项即返回 SIZE，显示实际值及对应上限，结束本次导出，不交付文件。导入按相同计量检查。容量按完整资料计算，禁止为满足限额丢弃执行记录或正文。导出时恰有生成任务，只在备份副本中终止该未提交尝试，保留输入、上个有效版本及已记录的诊断信息，清除 activeAttemptId、ownerId 和执行期限 leaseUntil；原书继续运行。等待玩家选择开局卡时没有执行任务，原样保留 awaiting_selection 及候选证据，恢复后显示同一组卡片，玩家确认时核对从备份恢复的建档资料及节点内容校验值。[导出快照](../../../src/features/backup/service.ts) · [暂停备份副本和数据校验](../../../src/features/backup/data.ts)
- **整书导入。** 继续支持现有 4–15 版备份并按原版本规则校验，旧包缺四表时补空。16 版缺任意游玩文件、校验和不符、建档时保存的书中资料或所引字段的校验值不符、版本变更记录与父版前值冲突、有跨局父版、父链循环、轮序错误、找不到所指提交或生成版本与尝试不一致，预检返回具体表、记录和字段。成功后以新 bookId 写入新书并发布。保留这本书内的 saveId、runId、版本编号、资产编号及父版本引用，更新记录的所属书籍编号。备份格式要标明建档资料、历史请求和答复、实际采用的字段及提示词副本各自的位置。恢复时原样复制这些内容，即使文字中出现旧书编号也照原文保留。复制出的运行记录仅供回看，恢复不自动重发执行。[格式与恢复](../../../src/features/backup/codec.ts) · [新书发布](../../../src/lib/storage/importService.ts)
- **重建原著事件的专用副本和删书。** 现有 P3（原著事件整理）流程会在专用副本重新生成原著事件；拟在该专用副本内清空四表，原书游玩存档及正常的整书备份均保留。删书前的占用查询、删除服务的实际占用检查与游玩服务接受新请求时须共用书籍删除标记或互斥检查。删除已开始，游玩服务停止接受这本书的新请求；某局仍有有效执行，提示正在哪个存档运行。确认删除后四张表随该书清理。[P3 副本与删除占用](../../../src/features/backup/service.ts) · [删书事务](../../../src/lib/storage/importService.ts)
