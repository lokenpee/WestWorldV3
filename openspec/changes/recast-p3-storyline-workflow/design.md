# 第二阶段怎样把已审事件串成故事线（评审稿）

## 字段变化

故事线应让下一次处理事件的模型回答三个问题。全线追踪什么？前面的事件已经改变了什么？当前事件又改变了哪一步？建议继续在 `eventLines` 保存故事线，在原有 `eventIds` 上关联成员证据。

| 字段及处理 | 建议含义与赋值 | 读取与兼容 |
|---|---|---|
| 名称 `title`、概况 `summary`，沿用 | 新建时必填非空文本。名称指出能跟踪的事项，概况概括已发生的起点和主要变化 | 旧文直接保留，供列表、检索、候选卡及详情读取。已合入概况的旧起因、经过、结果随原文保存 |
| 贯穿问题 `throughline`，新增 | 必填非空文本。写明跨事件追踪的目标、冲突或关系变化，以及什么事实足以判断它告一段落。例如“东府被侵的公银能否查清并追回” | 候选筛选和复核都读。旧记录可缺，等逐线核对后补写 |
| 最新进展 `latestProgress`、待解决问题 `unresolved`，新增 | 处理当前事件时仅按已归成员更新。前者新建必填非空文本，后者为字符串，可空。记录全线仍缺的具体事实 | 搜索、候选卡、详情及回放读取。旧记录缺值表示尚未整理 |
| 关键线索 `clues`，替代单值 `coreClue` | 新写为去重字符串列表，允许空。优先写辨识度高的案名、证物、特定承诺。普通人物名可检索，单独命中不足以挂线 | 旧非空短语完整作为一项，未知旧长文亦原样保留，复核时再拆。兼容接口从新字段派生旧展示值，备份保存完整列表 |
| 故事线状态 `lineStatus`，沿用 | 新建明确提交 open（进行中）或 closed（已收束）。是否收束按本线贯穿问题的已有答案判断。已收束线只有出现直接改变该结论的新事实才重开 | 沿用已有两值及手工状态。旧默认 open 在首次逐线复核时核实。详情和检索使用同一中文含义 |
| 成员 `eventIds`，沿用；成员作用 `memberEvidence`，新增 | 成员 ID 去重且属于本书。建议在线内以事件编号为键保存一条记录，含非空 `contribution`（这件事怎样推动本线）及 `nodeIds`（至少一个来自该事件的依据节点）。新建或补挂时一并写入；共享时两条线分别写作用 | 现有成员数组为归属的唯一依据。旧成员没有依据时显示“待核对”。解除归属仅移除本线该成员及其依据；删除、替换或修改下层事件时同步清理失效引用并重开受影响项 |
| 节点、章节及时间范围，沿用派生值 | 按线内有效成员重算。可选主线、支线角色沿用原值。串联判断以各成员的贡献为依据 | 保持网络、统计、人物检索及旧节点直挂线兼容读取。迁移只在现有真实事件成员上补依据 |

以上文本字数只作写作提示。旧书、旧备份转入时保留原 ID、成员、顺序和已有文字，逐线复核依据原文补内容；机械转换不代填剧情结论。SQLite 与备份导入执行同一可重复转换，按新格式导出并做往返核对。成员作用与故事线同时修改版本。模型旧回包和历史任务保留原协议解释。

归线结论存入本次运行的 `pipelineRuns` 任务及回执，以事件编号、事件版本关联：已归线、保留独立、待核实。独立须给理由，待核实须记具体缺口和已查范围。已有单事件线另接受“保留此线”的复核结论。它与“事件保持独立”在界面可区分。

同一事件在 A 线有可靠归属、在 B 线仅有待查线索时，归线结论是“已归线”。工具将 B 线编号、疑问、已查范围、缺少的事实存入本次运行报告。工作台可同时显示“整理已完成”和该项疑点。正式归属仍以各线的成员表为准。后续证实 B 线的作用时补挂并更新报告。若事件连首次归属或独立理由都无法确定，或某条线本身无法复核，则需要补证才能完成。

## 数据流转

### 模型首轮收到什么

1. **当前事件。** 读第一阶段已审卡，提供编号、名称、概况、最新进展、遗留、线索、事件状态及已有归线。成员节点给编号、名称、章节和顺序，用于找回证据。长事件分页展示节点，返回总数和续读位置，节点详细经过、引文按需读取。
2. **接下来可能用得上的事件。** 按事件首个成员的原文位置给随后至多 3 件的名称、概况和起止位置，作为首版试验值。当前事件也给起止位置。两件事跨章交错或后文追述旧事时，以成员原文记载的事实判断事情发生的先后，章节位置用于找回依据。预览只解释当下行动的意义，不能提前挂入、确认后文事件或据此写出结局。
3. **候选故事线。** 先纳入当前已有归属；其余按事件线索和概况匹配线名、贯穿问题、线索、最新进展和遗留，结合成员事件的已知联系排序。复用现有关键词、向量、重排与本地降级，向量查询取当前事件的概况及实际进展，候选文本同时含贯穿问题与已知进展，已收束线也可召回。试验取最多 10 条检索候选，已有归属另外保证可见。每条给线卡、相关成员的名称和作用、总成员数、展开入口，注明是否列全库。只加载与本事件或候选有关的疑点。
4. **本轮任务。** 只确认一个当前事件。候选之外有明确线索时可补搜，前序独立事件可回查补挂。遇到上游事件混杂时记下编号、原文及影响，返回人工可定位的问题。

例如，人工参考大纲在 C34-N002 记载西府封住账簿，在 C34-N005 记载查抄赖宅，在 C35-N001 记载追缴赃银。假设阶段一的事件 E35 已收录这三个节点，S04 已有查账事件。查明账簿被封改变了追款路径后，在 S04 挂入 E35，成员作用写“封账使贾珩改查赖宅，查得可供追缴的财物”，依据记上述三个节点。此时最新进展写查抄所得，待解决问题可写财物尚待清点抵欠。C36-N002 的清点入库尚在后续事件时，只作预览。处理到该事件后，才据实更新。E35、S04 是本例用号，验收按副本内实际编号映射。[原文节点目录](../p3-persistent-story-outline/evidence/赖家线-134节点独立参考大纲.md)

### 工具与回执

| 任务 | 读工具 | 写入与确认 |
|---|---|---|
| 逐事件归线 | 复用 `get_detail` 按编号查线、事件或节点并分页。拟增 `search_storylines` 搜线、`search_prior_events` 搜前序事件。两者沿用现有分组关键词，返回编号、名称、简况及是否截断 | `edit_storylines` 归线模式只开放建线、改确有变化的字段、挂入当前或有证据的早期事件；在同一次事务可先建后挂。为每条归属提交作用及节点依据。`confirm` 校验当前事件的归属与依据，或接收独立理由、待核实事项 |
| 疑似故事线分界复核 | 读本组线卡、共享或疑似承接的成员事件，按 ID 展开至原文。允许全书检索事件、候选线、相关未归线事件 | 单次事务允许建、拆、并、迁移及清理空线。移动时同步来源线和目标线的依据及版本，删除须说明成员去向或独立原因。完成只核本组分界 |
| 逐线进展复核 | 读当前线完整成员时间表、逐条作用、事件起止位置、上轮疑点和分界意见，详情可续读 | 只修当前线文字、状态及已有成员的依据。发现错挂、漏件、重复线时提交相关线、事件、节点和理由转回分界复核。按实际版本逐线确认 |

初串写入示例：`attach_event(lineId=S04, eventId=E35, contribution=封账后改查赖宅并起赃, evidence_node_ids=[C34-N002,C34-N005,C35-N001])`，回执至少返回当前事件、实际加入的线号、已保存依据及是否已归线。转回或待核实须在工具参数和回执中有独立结果。已有归属也有疑点时同时展示该关系和问题。服务校验同一本书、事件成员、依据节点所属事件、已读资料版本、当前执行者及本任务允许的操作；写错编号则整批回滚，已确认计数不动。同调用重复时复用原回执。阶段二可读事件和节点正文，写入属于线的内容及兼容投影。

### 业务提示词样段

> 读当前事件，找出它带来了哪一种具体变化。逐条对照候选故事线：此前哪个事件留下了条件、承诺、阻碍或未解决的问题？当前事件使它往前走了哪一步？给出支持这一判断的成员节点。线索命中帮助你找到材料；人物同场、地点相同、发生在同一天，都还需要进一步证据。
>
> 两条线都受到影响时，分别写清这件事对每条线的作用。已有单个事件也能开线，条件是原文已经提出了可继续追踪的跨事件问题。事情已经自足，就保留为独立事件并说明理由。需要材料才能判断时，写下缺少哪一个事实。事件自身已闭环时，检查它的结果是否给其他事件创造了条件；故事线按全线的贯穿问题决定何时收束。

三种任务各维护一份完整中文正文。初串给建线、共享、独立、暂缺证据、前序补挂和交错事件的正反例。分界复核围绕“目标和收束条件能否分别成立”检查，除了共享成员，还要检索零共享但前后承接、一直独立或只有一个成员的情况。逐线复核须把已发生的进展定位到相应事件及节点。初串和复核分别试用低、高思考强度，计入同书费用对照。旧八份正文及示例按历史版本处理，活动清单、设置页测试和新请求同步切换。

## 触发逻辑

| 触发 | 处理与界面反馈 | 下游和失败恢复 |
|---|---|---|
| 第一阶段交接 | 第一阶段复核通过，保存已审事件及版本。在测试阻隔下显示等待归线。用户决定放行后才可进入新版 | 旧版停在归线之前的运行可从已有事件开始。已按旧协议写过线的运行在副本重建第二阶段，保留第一阶段结果及旧运行回放 |
| 逐件判断 | 当前卡有效，依次展示位置、候选和归属。保存后核对回执，确认仅计当前一件 | 独立可继续；待核实保存缺口，先推进其他事件，收尾前重查。后文出现新依据可补挂先前独立事件并重开其原结论 |
| 所有事件已有处理结果 | 按共享事件、独特线索与因果承接找疑似组；独立事件和单事件线也纳入回查。之后每条存续线按版本核一次 | 单线发现边界问题带证据转回；同版本同问题已有答复时展示意见，证据不足则转待核实，避免反复转回 |
| 编辑后尚未确认、暂停或改动上游 | 显示已保存的成员和未确认任务，按回执续接。校验相关线、成员事件和依据节点版本 | 事件或节点变化只重建受影响的材料及复核任务。取消保留已写成果，新运行按现有关系及依据重新核对。存在阻塞性缺证时停在对应项，报告列出已查范围 |

## 验收与接手

1. 从同一书籍副本固定已复核事件、节点、ID 与版本。准备两份起点相同的副本，使用相同整理模型及配置。在隔离测试入口分别运行旧归线、新归线；保存请求、工具回执、线卡、成员和费用。首次检查用例固定三类：赖家查账至查宅、清点的正例；范仪申冤、云光定罪、封爵同朝议的分界；同一事实确实影响两条线的共享例。根据实际事件划分标注，不能照抄旧参考大纲的事件编号。
2. 事先标注应接的事件对、应分开的事件对、允许独立和应共享的事件、哪一节点才足以收束。逐例列出漏接、误接、错收束、重复建线和无证据共享。候选没出现和候选出现后判错分别计数。记录每百件的请求数、输入输出 token、耗时和费用。固定判例逐项通过；其余分歧保留原文交给用户核对。
3. 模拟空线库、候选未列全、检索服务故障、前序独立事件被补挂、长卡分页、补挂较早事实、共享线解绑、仅有额外归属疑点仍可完成、首次归属无法判定时等待补证、写后中断、回执重放、旧书与备份恢复。详情、搜索、事件网络及整理报告应指向同一成员和依据，历史回放可读。
4. 当前核对环境为仓库工作树和本地 Vitest。2026-11-26 运行 `npm exec -- vitest run tests/narrative-v4.test.ts tests/event-workflow.test.ts tests/event-candidates.test.ts --maxWorkers=1`，3 个文件、34 项现状测试通过。新方案的模型质量、成本和用户自测均待实施后测量。
5. 同日补入两项用户决定后，工程方案核查 11 项齐全；`npm run openspec -- validate recast-p3-storyline-workflow --strict` 通过。静态核对了 4 个跨任务请求和 8 个补充样例的提示词路径、确认编号、成员与依据、两种疑点的收尾结果。全仓 `npm run governance:check` 仍报告 26 项既有问题，涉及其他变更的登记、历史验收链接及标题锚点。
