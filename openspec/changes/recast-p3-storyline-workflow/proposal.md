# REQ-032 第二阶段故事线串联方案（待确认）

## Why

2026-11-26，用户要求对比 P3 第一阶段事件串联与第二阶段故事线串联，重点评估故事线字段、模型输入、提示词、工具与完整处理流程。两者都要判断“当前材料对一个更大的叙事对象有什么贡献”。第一阶段已把事件从“一幕”改成可跨章的具体事项。同一件事的商议、行动和结果都可能在一张事件卡里。第二阶段现在需要识别的是**几件各自成立的事，怎样共同推进一个更大的问题**。

## 术语入口

P3 是工作台把已提取的剧情整理成大纲的步骤，REQ-032 是这一需求在仓库中的编号。事件记录一件有独立意义的事情，故事线追踪几件事情共同改变的目标、矛盾或关系。逐事件归线指程序每次交给模型一件已审事件，由模型判断它推进了哪条线。[项目统一术语](../../../docs/v2/00-阅读入口与术语.md#统一术语)

| 名称 | 在本方案中的用途 |
|---|---|
| 贯穿问题、成员作用、依据节点 | 前者写整条线要追踪什么，后两项分别写某件事在这条线中改变了什么、对应原文在哪里。一个事件可以在两条线中承担不同作用 |
| 候选、前瞻、重排 | 候选是本轮可能相关的已有线。前瞻是接下来少量事件的简况。重排是检索服务对初步找出的线重新排列相关程度 |
| 分界复核、逐线复核、转回 | 模型先检查几条线的成员有没有混放，再检查每条线的进展及结果。逐线检查发现归属问题时，把具体线号、事件和依据交回分界复核 |
| 版本、快照、回执 | 版本表示记录修改到了哪一版。快照保存模型这次收到的材料。回执保存一次工具调用实际写入的编号和内容，重试可以取回相同结果 |
| JSON、Markdown、SQLite、Vitest、token | JSON 用于传递有明确字段的数据，Markdown 保存可直接阅读的提示词，SQLite 是本机书库，Vitest 运行自动检查。token 是模型计量输入、输出及费用的文本单位 |
| 业务表、工具名及参数 | 工具与输出结果的原名、取值及中文含义见[读写契约](agent-contract.md#读取工具)。存储表名及本书编号之间的关联见[数据经过哪些表](agent-contract.md#数据经过哪些表)，线字段见[字段变化](design.md#字段变化) |

### 当前两阶段的差别

| 方面 | 第一阶段实际行为 | 现有第二阶段的设计及实现 | 对故事线的影响 |
|---|---|---|---|
| 工作单位 | 一次一个节点，给详细经过、最多五个后文节拍及最多十个候选事件 | 依最早成员位置排序，默认每组 20 件。可顺带处理并确认组外事件。每 10 组周期复核，收尾全书复核 | 同组的事件靠书中位置凑在一起。批界两侧真正相接的事件容易漏掉。同一目标上反复查证或修订也难定位到一件 |
| 首轮材料 | 候选卡直接列已知进展、待解决问题和完整成员编号及名称，关键词与语义检索后可重排 | 本组事件已有概况、线索、最新进展、待解决问题、状态。目录内的故事线只有编号、名称、成员编号。目录按 JSON 写成不含排版空格的文本后超过 2000 字符时保留各线及相关事件编号和名称。首轮还发当前会话全部活动疑点和运行参数 | 当前事件信息已经较全，欠缺的是候选线为何可能承接它。长书压缩以后尤其容易依赖线名，补查依靠模型自己翻目录 |
| 工具 | 按编号读事件、节点，能按词搜索候选和早期经过。初串只增补，有理由地保存，再读短回执确认 | 可按编号查字段、翻目录、登记疑点。归线组已可建线、改线、挂入、移出及删除故事线。建线与挂入可在一次事务完成。批次编辑缺少逐条必填的推进依据 | 可以没有证据说明便大幅改动旧归属。已经有原子编辑和成员增量操作，值得保留 |
| 完成条件 | 当前节点已归事件，或有明确的未归属理由 | 初串按实际存储检查组内每件，已有归线或关联活动的归属疑点才能通过。全书说明分段检查概况与单值核心线索均非空 | 确认机制鼓励把独立事件塞入某条线、建一条同名线，或把确定的“可以独立”登记为疑点 |
| 提示词与复核 | 串联正文有立件、回查、多归属及闭环判例。疑似组复核分界，逐件复核经过，可带证据转回 | 已有 1 份归线、3 份周期、4 份全书提示词。已有因果、共享和下层只读要求。归线正例“发现匪情、调兵、剿匪、善后”未交代哪些步骤已构成独立事件。复核按结构、疑点、未归属及单事件线、说明分段 | 同一串动作在两层都能被当作正例。说明中一个人物或地点就能充当核心线索，无法据此判定两线分界 |

实现依据见[事件规则](../../../docs/v2/resources/v2.2/prompts/active/p3-event-link.md)、[故事线规则](../../../docs/v2/resources/v2.2/prompts/active/p3-line-group.md)、[实际调度与首包](../../../src/features/story/narrativePlan.ts)、[工具声明](../../../src/features/story/narrativeToolSchema.ts)和[事件检索与工具契约](../../../docs/v2/项目技术说明.md)。

## What Changes

建议逐件归线，单独记录每件事在每条线中的作用。先让模型列出当前事件具体改变了什么，再与候选故事线的贯穿问题、已有成员和最新进展核对。根据证据接入已有线、新建、共享或保留独立。全部逐件处理后，按疑似组核对线与线的分界，再逐条核对全线进展与收束。复用第一阶段的检索服务、版本核对、同一次操作重复提交时取回原结果的做法，以及将归属问题交回分界复核的流程。两个层级各自维护判例、材料与写权限。

## 确认依据

2026-11-26 用户要求先对比两阶段，再“仿照事件串联优化故事线串联”，并确认了两项业务选择。

1. “原文已经提出可跨事件追踪的问题就允许开线，其余保留独立”。一件已审事件可以作为故事线起点，也可以带理由保持独立。
2. 一件事已证实推进 A 线，只有它是否也推进 B 线缺证时，“允许完成，在报告中保留 B 线疑点”。保存 A 线的成员和作用，B 线只在报告里记录疑问、已查范围及缺少的事实。全部必要复核通过后全书可以完成。

由用户决定何时解除第二阶段暂停。故事线任务只读已审事件和节点的业务内容。上述两次答复确认了开线与收尾规则，整套实施与验收范围待审阅。[第一阶段提案](../recast-p3-event-workflow/proposal.md)

## 讨论结论

建议采用逐件归线。小批归线可以减少模型调用，但仍要在同一轮处理多件的候选、冲突和失败。只重写提示词能够改善判例，却无法给模型补上候选证据，或让工具接受“有理由独立”。推荐方案增加逐件调用，缩短每次输入，按固定事件集对照质量与总费用后再决定上线。

最影响成品数量的取舍是单事件能否开线。建议允许已有明确跨事件问题的起点先开线，例如第一份指控已经引出了待追查的责任。整件事已经自足，或只能复述事件名称时，保留独立。后续事件提供了承接证据，再回挂早期事件。关系线按具体关系如何变化立线，普通同场或共同人物只作搜索线索。

## gstack 工程方案审查

2026-11-26 使用 gstack-plan-eng-review 核对本变更的提案、设计、两份差异规格、任务、三份拟装载的正文、工具契约及查宅样例。审查覆盖数据读写、重复提交、跨阶段恢复、验收方法、调用费用与可读性。当前环境未找到外部 Claude Code 审查程序，本记录只列本地核对的发现。

| 方面 | 发现与处理 |
|---|---|
| 调度与权限 | 原有归组工具同时开放建线、移出和删线。逐件使用限制后的编辑操作，分界任务才可迁移和删除，逐线只能修改当前线。展示的工具和执行端须同时限制。复用本书运行服务、新旧任务分开按版本派发。[当前声明](../../../src/features/story/narrativeToolSchema.ts) |
| 保存与恢复 | 原运行把工具名和参数连同调用编号一起保存。继续执行应先查已保存结果，补全缺失的工具回复，再确认当前件。引用格式统一为建线时传名字、同批挂入时在名字前加美元符号。写操作失败整批撤回。[写入与恢复](../../../src/features/story/narrativeTools.ts) |
| 时间与证据 | 章节排序足以定位证据，后文可能追述旧事。三个任务按已经发生的剧情判断进展，补挂早期依据不能倒退最新进展。检查后写回的节点必须属于对应事件。[第一阶段的进展要求](../../../docs/v2/resources/v2.2/prompts/active/p3-event-link.md) |
| 副本与验收 | 现有建立 P3 重建副本会执行 `tables.storyEvents = []`。实际对照应从已审完第一阶段的同一保存点生成两份副本，先比对事件、节点、版本及正文，再分别运行两个归线流程。复用当前导入、备份和事务；重建第二阶段只清副本内的线与第二阶段进度。原书仍可看旧结果。[现有副本入口](../../../src/features/backup/service.ts) |
| 检索与费用 | 候选先纳入既有归属，完整库已展示时跳过补搜；排序服务超时改用本地结果。用同一模型、相同事件量分别记录候选漏掉、模型误判、请求数、费用，未返回价格时标“费用未知”。3 件预览和 10 条候选是试验参数。 |
| 收尾条件 | 原设计混用了两类疑点。根据用户答复，首次归属或独立理由尚无法判定时保留待核任务，收尾时显示缺什么。一件事已经证实归线，另一条候选线缺证时，在确认该件的同一次写入中保存疑点，工作台可同时显示整理完成和报告里的待查线索。两种情况分别有请求与验收样例。 |
