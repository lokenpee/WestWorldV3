# P1 提示词与章节输入精简

## Why
REQ-024，中型需求，project-local。用户要求 P1 世界资产与叙事事件提示词讲清任务、铁律、字段和可用工具，删除 ID 分配、重复参数结构、自检及程序细节；文章消息只包含章节名称和正文。

## What Changes
两份 Markdown 按四部分重写，字段表只解释业务含义，类型、必填和枚举保留在工具 Schema。保留关系存在性与方向、同人异名和未具名人物、事件粒度与传闻来源要求；保留已确认的外貌说明。统一关系标签说明，取消“证据不足填未知”。P1 user 消息改为章节名称、空行、原文正文；公共文学资料说明仍由网关追加在 system 末尾。

请求示例由 scripts/sync-prompt-resources.mjs 同步 P1 正文、章节消息和工具 Schema；正文与运行时一样去掉文件头元数据，后续运行同步命令即可保持一致。

## Capabilities
### New Capabilities
无。
### Modified Capabilities
- extraction：增加 P1 提示词组织和章节消息约定，沿用 EXTRACT-02 失败修正。

## 确认依据
2026-11-13 用户提出两份 P1 提示词重构及纯净章节输入，要求先讲行动；在四项方案（四部分结构、清理内部说明、纯净章节消息、同步及固定响应验证）后明确回复“开始吧”，授权实施。

## 讨论结论
按已确认方案直接实施。原字段、存储、工具权限和校验约束保持，关系证据不足时省略整条关系，不以“未知”制造关系。失败修正沿用原工具错误及独立修正消息，原文章节内容保持不变。普通回复不替代 submit_result 的结构化提交。

## 字段变化
无业务字段变化：只改工具字段描述。Schema 类型、必填项、枚举、长度与默认值保持，旧记录及备份无需迁移。章节消息的 content 由提取服务组装，去掉额外章节编号和分隔标记；chapterIndex 仍存储在任务、来源和成功凭证中。

## 数据流转
chapters.chapterName 与 chapterTexts.text → extraction/service.ts 组装 user 消息 → 模型网关追加公共 system 说明并发送对应 submit_result Schema → 原提取校验 → 原资产/成功凭证/进度事务保存。

例：内部 chapterIndex=1、chapterName=码头、text=沈青收到来信。请求正文从“章节标识：1\n章节名：码头\n\n--- 正文开始 ---\n沈青收到来信。\n--- 正文结束 ---”改为“码头\n\n沈青收到来信。”；资产来源仍为第1章。
