# 人物关系、同名绑定与合并联动

## Why

人物关系目前保存在人物行中，以称呼表达目标；节点自动绑定只接受唯一命中。用户要求人物关系的来源端绑定具体原始人物，目标端及事件节点匹配全部同名条目，合并后按底层保留编号统一收敛，关系和事件引用保持一致。

## What Changes

| 需求编号 | 用户目标 | 当前行为 → 目标行为 |
|---|---|---|
| REQ-007 | 关系归属于具体提取人物并保留方向依据 | 称呼及方向标记 → 以原始人物编号确定来源，保存双方关系含义及原文依据 |
| REQ-008 | 目标及节点全部同名绑定 | 节点只绑定唯一候选、人物关系未绑定 → 关系来源按编号解析、目标按名称全命中；节点全命中并后续补齐 |
| REQ-009 | 合并只改底层资产，关联统一跟随编号 | 共用融合算法但提交逻辑分散 → 各入口共用底层合并及关联更新；旧编号重定向、关系去重、节点与事件线同步 |
| REQ-010 | 现有资料与备份能够继续使用 | 旧称呼关系和现有绑定 → 保留原记录并建立新结构，升级及恢复后可核对关系与引用 |

需求池：[四项需求及状态](../../需求池.md)。四项在同一变更内审核、按依赖交付，保持字段、事务和备份设计一致。

## Capabilities

### New Capabilities
- character-relations：具体人物的关系归属、目标全命中、有向关系汇总和引用维护。

### Modified Capabilities
- asset-management：人物匹配、节点涉及人物、手动合并与关联显示。
- extraction：关系方向及依据提取、成功提交后的名称绑定补齐。
- world-organization：机械、人工、AI合并共用底层结果处理。
- agent-session：人物详情中的关系返回、AI合并的共同事务及依赖校验。
- book-backup：新增关系数据、当前书库升级和备份兼容。

## 讨论结论

用户已经明确：

1. 每条人物关系只归属于提取它的原始人物编号；当前来源只能沿合并映射解析，不按同名分配给其他来源人物。
2. 目标端匹配本书全部同名条目；事件节点的涉及人物继续全部同名匹配。单条关系有N个有效非自身目标时生成2N条有向结果。
3. A1提取“父亲”、A2提取“杀母仇人”时分别保留归属；合并到同一来源后，同一有向人物对汇总去重标签。
4. 合并旧编号后，人物关系、事件节点涉及人物及事件线人物集合跟随保留编号；改成不同主名也继续连接保留资产。
5. 合并和绑定分开职责，共同依赖底层资产与编号映射。绑定处理与界面、模型选择保持独立。

采用以下实现方案供本次文档审核：原始关系放在独立关系表，来源为单一当前编号、目标为命中编号集合，方向线由两端编号生成；新增人物、修改名称、合并和删除统一调用绑定处理；合并及受影响绑定在同一事务完成。关系展示使用人物详情中的有向列表，事件线继续从节点汇总人物。

新旧条款的替换位置列在[规格差异](specs/asset-management/spec.md)。所有名称命中的范围、旧关系方向不足的处理、字段及迁移细节见设计，审核时一并确认。

## 确认依据

2026-11-03用户确认：“关系来源端只绑定提取这条关系的原始人物编号（originCharacterId），目标端仍然按照名称匹配所有同名人物”，并要求适配受影响需求。事件节点继续全部同名匹配；合并及绑定分别依赖底层资产与编号映射。

用户授权先拆分需求、列入需求池并撰写文档审核。本变更当前交付提案、设计、差异规格和任务；具体业务实施在本套材料审核后开始。
